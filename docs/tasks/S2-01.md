## Contexto

Primeira tarefa do Sprint 2 (Veículos, condutores e catálogo; RF-02 e RF-14). A partir deste sprint a plataforma guarda ficheiros: a foto do livrete (S2-03) e os documentos legais dos produtos (S2-04); nos sprints seguintes, KYC, vistorias, certificados e sinistros. ADR-005 (armazenamento atrás de uma porta, disco local e S3) e ADR-006 (`FileAccessPolicy`: o `document` guarda e serve, o módulo dono decide quem lê). Modelo transversal §1.1, §3 (`DocumentApi`) e §7 (limites, tipos, download).

Esta tarefa cria também, por ser a primeira de backend do sprint, a migração com **todas** as permissões do Sprint 2 (modelo transversal §5) e o mecanismo de dados de demonstração (`db/dev`, modelo transversal §7).

**Pressupõe** (Sprint 1 no `main`): `TenantContext`, `Scope`, `TenantSnapshot`, `@RunAsSystem` e `RunAsSystemUsageTest` (S1-01); `CurrentUser`, `SecurityConfig` com `BearerTokenResolver` que ignora o cabeçalho nos caminhos públicos (S1-02); `ErrorCodes`, `FieldErrorCodes`, `ErrorCodesExportTest` e `api/error-codes.json` (S1-02); `AuditService` (S0-03); papel `moseguros_app` e utilizador `moseguros_app_user` (S1-01); tabelas `identity.role_permission`, `identity.user_account`, `identity.customer_profile`, `identity.user_role`, `identity.invitation`, `organization.organization`, `organization.insurer_profile` (S1-01); `web/nginx.conf` e `infra/docker-compose.yml` (S0-07, S1-01, S1-03); traduções de erros na web (`web/src/i18n/locales/*.json`, S1-07) e na app (`mobile/lib/l10n/*.arb`, S1-09).

## Objectivo

Um módulo guarda ficheiros (disco local ou S3) com metadados em `document.file`, só aceita os tipos e tamanhos permitidos (confirmados pelo conteúdo), e serve-os em `GET /api/v1/files/{id}` apenas quando a `FileAccessPolicy` do módulo dono autoriza. Os ficheiros nunca ligados a um dono são limpos ao fim de 30 dias. As permissões do Sprint 2 existem na BD e o perfil `local` tem dados de demonstração.

## Especificação

### 1. Tabela `document.file`

Migração `V202612010100__document_file.sql`, corre como dono:

```sql
grant usage on schema document to moseguros_app;
alter default privileges in schema document grant select, insert, update on tables to moseguros_app;
```

Colunas obrigatórias do `AGENTS.md` §5 subentendidas.

| Coluna | Tipo | Regras |
| --- | --- | --- |
| `owner_type` | `varchar(30) not null` | `check (owner_type ~ '^[A-Z][A-Z_]{1,29}$')`; tipo do dono (`VEHICLE`, `PRODUCT_VERSION`, …). Não há lista fechada na BD: o código só aceita tipos com uma `FileAccessPolicy` registada (secção 4) |
| `owner_id` | `uuid not null` | id da entidade dona, noutro schema; sem FK |
| `purpose` | `varchar(40) not null` | `check (purpose ~ '^[A-Z][A-Z_]{1,39}$')`; finalidade dentro do dono (`REGISTRATION_DOC`, `GENERAL_CONDITIONS`…) |
| `insurer_id` | `uuid null` | seguradora a que o ficheiro pertence, quando houver (documentos de produto) |
| `uploaded_by_user_id` | `uuid null` | utilizador que enviou; `null` quando gerado pelo sistema |
| `uploaded_by_org_id` | `uuid null` | organização de quem enviou (staff) |
| `original_filename` | `varchar(200) not null` | nome já limpo pelo `FilenameSanitizer` |
| `content_type` | `varchar(40) not null` | `check in ('image/jpeg','image/png','image/heic','application/pdf')` |
| `size_bytes` | `bigint not null` | `check (size_bytes between 1 and 10485760)` |
| `sha256` | `varchar(64) not null` | hexadecimal minúsculo, `check (sha256 ~ '^[0-9a-f]{64}$')` |
| `storage_key` | `varchar(300) not null unique` | chave no armazenamento (secção 3) |
| `classification` | `varchar(10) not null` | `check in ('PUBLIC','PERSONAL','SENSITIVE')` |
| `linked_at` | `timestamptz null` | preenchido por `DocumentApi.markLinked`; `null` = órfão |
| `purged_at` | `timestamptz null` | preenchido quando a limpeza apaga o conteúdo; a linha fica |

Índices:

```sql
create index ix_file_owner on document.file (owner_type, owner_id);
create index ix_file_orphans on document.file (created_at) where linked_at is null and purged_at is null;
```

RLS (`enable row level security`; política `file_scope for all to moseguros_app using (…) with check (…)`, mesma expressão), com as abreviaturas do S1-01 e `i = nullif(current_setting('app.insurer_id', true), '')::uuid`:

```sql
s in ('SYSTEM','PLATFORM')
or (s = 'ORG' and (insurer_id = i or uploaded_by_org_id = o))
or (s = 'CUSTOMER' and uploaded_by_user_id = u)
```

- Sem `delete` para o papel da aplicação (a limpeza marca `purged_at`, não apaga a linha).
- O download (secção 5) lê a linha em `SYSTEM` através de `DocumentSystemLookups`, porque quem decide é a `FileAccessPolicy` e a leitura pode ser anónima (documentos de produtos publicados). As outras leituras e escritas correm no âmbito de quem chama, e o RLS aplica-se.
- Os sprints seguintes que precisem de outros âmbitos de escrita (ex.: perito a enviar fotos de um sinistro de outra seguradora) alteram esta política numa migração própria.

### 2. Contrato público do módulo (pacote `mz.co.moseguros.document`)

```java
public enum FileClassification { PUBLIC, PERSONAL, SENSITIVE }

public record StoreFileCommand(
    String ownerType,            // obrigatório; tem de ter FileAccessPolicy registada
    UUID ownerId,                // obrigatório
    String purpose,              // obrigatório
    FileClassification classification, // obrigatório
    UUID insurerId,              // opcional
    String originalFilename,     // opcional; null → "ficheiro"
    String declaredContentType,  // tipo indicado pelo cliente HTTP (pode ser application/octet-stream)
    Set<String> allowedContentTypes, // opcional; null = os quatro tipos; restringe (ex.: só application/pdf)
    byte[] content               // obrigatório
) {}

public record FileRef(UUID id, String ownerType, UUID ownerId, String purpose, String contentType,
                      long sizeBytes, String sha256, String originalFilename,
                      FileClassification classification, UUID insurerId,
                      Instant createdAt, boolean linked) {}

public record FileContent(FileRef ref, InputStream content) {}   // quem recebe fecha o stream

public interface FileAccessPolicy {
    boolean supports(String ownerType);
    boolean canRead(String ownerType, UUID ownerId, CurrentUser user);
}

public class DocumentApi {
    public FileRef store(StoreFileCommand cmd);
    public void markLinked(UUID fileId);       // acrescentado por esta ficha
    public FileContent open(UUID fileId);
    public FileRef metadata(UUID fileId);
    // renderPdf(...) chega no S4. Não existe delete.
}
```

**`store`** (`FileStoreService.store`, `@Transactional(propagation = REQUIRES_NEW)`), por esta ordem:

1. `ownerType` sem `FileAccessPolicy` registada → `IllegalArgumentException` (erro de programação, 500).
2. `content.length == 0` → `DomainException` `FILE_EMPTY` (400).
3. `content.length > 10 485 760` → `FILE_TOO_LARGE` (413).
4. Tipo real = `ContentSniffer.sniff(content)` (secção 6). Desconhecido, ou fora de `allowedContentTypes` quando este não é `null` → `FILE_TYPE_NOT_ALLOWED` (415). Nada é gravado.
5. Se `declaredContentType` não for `null`, vazio nem `application/octet-stream`, tem de ser igual ao tipo real (sem parâmetros, minúsculas); senão `FILE_TYPE_NOT_ALLOWED` (415).
6. `id = Ids.newId()`; `sha256` do conteúdo; `storage_key` (secção 3); `FileStorage.put(...)`.
7. Insere a linha com `uploaded_by_user_id = TenantContext.current().userId()`, `uploaded_by_org_id = …orgId()`, `linked_at = null`. Se a inserção falhar, apaga o conteúdo acabado de gravar (`FileStorage.delete`) e relança.
8. Devolve o `FileRef`.

Porque `REQUIRES_NEW`: a linha fica gravada mesmo que a transacção de quem chama falhe depois. Esse ficheiro fica órfão (`linked_at` nulo) e a limpeza trata dele (secção 7).

**`markLinked(fileId)`** (`propagation = REQUIRED`, na transacção de quem chama): `linked_at = agora` se ainda for `null`; idempotente. O módulo dono chama-o **na mesma transacção** em que grava a referência ao ficheiro (ex.: `vehicle.registration_doc_file_id`). Ficheiro não visível no âmbito actual → `FILE_NOT_FOUND` (404).

**`open(fileId)`** e **`metadata(fileId)`**: no âmbito de quem chama (RLS aplica-se); não verificam a `FileAccessPolicy` (quem chama é o próprio módulo dono). Inexistente ou `purged_at` preenchido → `FILE_NOT_FOUND`.

### 3. Armazenamento (`FileStorage`)

Interface interna do módulo (`document.infrastructure.storage`):

```java
interface FileStorage {
    void put(String key, InputStream content, long size, String contentType);
    InputStream get(String key);       // chave inexistente → StoredObjectMissingException
    boolean exists(String key);
    void delete(String key);           // idempotente; usado só pela limpeza e pelo passo 7 do store
}
```

O ADR-005 inclui `delete` na porta (decisão D26 da reconciliação); a limpeza de órfãos (modelo transversal §3) e o passo 7 do `store` usam-no. Não há `DocumentApi.delete`: os outros módulos nunca apagam ficheiros.

- **Chave:** `{aaaa}/{mm}/{dd}/{fileId}.{ext}` com a data UTC do envio e `ext` ∈ `jpg`, `png`, `heic`, `pdf`. Nunca contém o nome original nem dados pessoais. Excepção: os ficheiros de demonstração (secção 9) usam `dev-seed/{nome}`.
- Implementação escolhida por `moseguros.files.storage` (`filesystem` ou `s3`), sem valor por defeito: sem ela a aplicação não arranca.

**`FilesystemFileStorage`** (perfis `local` e `test`, e docker-compose):
- `moseguros.files.filesystem.base-dir`. No arranque cria a pasta se faltar; se não for gravável, a aplicação não arranca.
- Valida a chave com `^(\d{4}/\d{2}/\d{2}/[0-9a-f-]{36}\.(jpg|png|heic|pdf)|dev-seed/[a-z0-9._-]{1,100})$` antes de qualquer operação (impede `..`); inválida → `IllegalArgumentException`.
- `put` grava em `{chave}.part` e depois `Files.move(..., ATOMIC_MOVE)`.

**`S3FileStorage`** (staging e produção; AWS SDK v2, `S3Client` síncrono):

| Propriedade | Variável | Notas |
| --- | --- | --- |
| `moseguros.files.s3.bucket` | `MOSEGUROS_S3_BUCKET` | obrigatória |
| `moseguros.files.s3.region` | `MOSEGUROS_S3_REGION` | obrigatória |
| `moseguros.files.s3.endpoint` | `MOSEGUROS_S3_ENDPOINT` | opcional (serviços compatíveis com S3) |
| `moseguros.files.s3.path-style-access` | `MOSEGUROS_S3_PATH_STYLE` | `false` por defeito |

- Credenciais pela cadeia por defeito do SDK (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` ou papel da máquina). Nunca no `application*.yml`.
- `put` com `ServerSideEncryption.AES256` e `ContentType`.
- No arranque faz `headBucket`; falha → a aplicação não arranca, com mensagem clara (sem credenciais na mensagem).

### 4. `FileAccessPolicy`

- Cada módulo dono implementa uma política como bean Spring no seu pacote `application` (S2-03: `VEHICLE`; S2-04: `PRODUCT_VERSION` e `INSURER_LOGO`).
- A interface ganha um terceiro método, `Set<String> ownerTypes()` (os tipos que a política trata; `supports(t)` equivale a `ownerTypes().contains(t)`), para o registo poder verificar a configuração no arranque.
- `FileAccessPolicyRegistry` recolhe todas as políticas no arranque. Uma política com `ownerTypes()` vazio, ou dois beans com o mesmo tipo → a aplicação não arranca. O passo 1 do `store` e o passo 2 do download usam este registo.
- `canRead` corre no âmbito de quem pede (não em `SYSTEM`), dentro de uma transacção só de leitura.
- `CurrentUser.isAuthenticated()` (acrescentar ao S1-02; equivale a `token().isPresent()`): `false` para pedidos anónimos. Os outros métodos de `CurrentUser` continuam como no S1-02: sem token lançam `DomainException` `UNAUTHORIZED` (401). As políticas chamam `isAuthenticated()` antes de `id()`/`permissions()`.

### 5. Download

**`GET /api/v1/files/{id}`** — `operationId: downloadFile`, tag `Document`, público ou autenticado.

- `SecurityConfig`: `/api/v1/files/**` com `permitAll()`, mas **fora** da lista de caminhos em que o `BearerTokenResolver` ignora o cabeçalho (S1-02). Assim: sem token → anónimo; token válido → autenticado; token inválido ou expirado → 401 `UNAUTHORIZED` (o cliente renova e repete).
- Parâmetro opcional `download` (`boolean`, defeito `false`).
- Passos (`FileDownloadService`):
  1. `DocumentSystemLookups.find(id)` (`@RunAsSystem`, só leitura) → `FileRef` ou vazio; `purged_at` preenchido conta como vazio.
  2. Sem linha, sem política para o `owner_type`, ou `canRead = false` → 404 `FILE_NOT_FOUND`. Nunca 403: não se revela que o ficheiro existe.
  3. `FileStorage.get(storage_key)`; conteúdo em falta → log `ERROR` com o id (sem a chave) e 500 `FILE_STORAGE_ERROR`.
- Resposta 200, corpo binário, cabeçalhos:
  - `Content-Type`: o da linha; `Content-Length`: `size_bytes`;
  - `Content-Disposition: inline; filename="<ascii>"; filename*=UTF-8''<percent-encoded>` (`attachment` com `download=true`); `<ascii>` é o nome com os caracteres não ASCII trocados por `_`;
  - `Cache-Control: private, no-store`; `X-Content-Type-Options: nosniff`.
- OpenAPI: resposta `application/octet-stream`, `schema: { type: string, format: binary }`, para os clientes gerados lerem como `Blob` (web) e bytes (app).
- Não se grava auditoria de leitura nesta tarefa (leituras sensíveis: Sprint 11).

### 6. Validação do conteúdo (`ContentSniffer`, `FilenameSanitizer`)

| Tipo | Assinatura (bytes iniciais) |
| --- | --- |
| `image/jpeg` | `FF D8 FF` |
| `image/png` | `89 50 4E 47 0D 0A 1A 0A` |
| `application/pdf` | `25 50 44 46 2D` (`%PDF-`) |
| `image/heic` | bytes 4–7 = `ftyp` e bytes 8–11 ∈ `heic`, `heix`, `hevc`, `hevx`, `mif1`, `msf1` |

Qualquer outro conteúdo → desconhecido.

`FilenameSanitizer.clean(String raw, String contentType)`:
- fica só o nome base (tudo depois do último `/` ou `\`);
- caracteres fora de `[\p{L}\p{N} ._()-]` passam a `_`; espaços repetidos passam a um;
- corta a 200 caracteres mantendo a extensão;
- nome vazio → `ficheiro`;
- a extensão é sempre a do tipo real (`foto.png` com conteúdo JPEG → `foto.jpg`).

### 7. Limpeza de órfãos (`OrphanFileCleanupJob`)

- `document.application.OrphanFileCleanupJob`, `@RunAsSystem`, `@Scheduled(cron = "0 30 3 * * *", zone = "Africa/Maputo")`.
- Selecciona `linked_at is null and purged_at is null and created_at < agora − 30 dias`, em lotes de 500, cada lote na sua transacção. Para cada linha: `FileStorage.delete(storage_key)` e `purged_at = agora`.
- Log estruturado `INFO` com início, fim, número de ficheiros limpos e de falhas. Uma falha num ficheiro não pára o lote (fica para a execução seguinte).
- ShedLock só chega no S6: até lá corre numa só instância (local e testes).
- `SchedulingConfig` (`shared.scheduling`): `@EnableScheduling` só quando `moseguros.jobs.enabled` é `true` (defeito `true`; `false` em `application-test.yml`). Os testes chamam o método do job directamente.
