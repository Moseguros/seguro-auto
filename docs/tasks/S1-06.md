## Contexto

Histórias 1 e "completar perfil" do Sprint 1. O cliente já entra por OTP (S1-03); agora completa os seus dados pessoais (necessários para comprar no Sprint 3) e gere os contactos verificados. Documentos e NUIT são cifrados (S1-01).

## Objectivo

O cliente vê e altera o seu perfil, acrescenta ou troca o telemóvel ou o e-mail com verificação por OTP, e a resposta indica se o perfil está completo.

## Especificação

Todos os endpoints: tag `Identity`, utilizador autenticado. Os de `/me/profile` e `/me/contacts` exigem `self:profile` (só clientes; staff → 403).

### 1. `PUT /api/v1/me` (`updateMe`)

`{ displayName?, preferredLanguage }` → 200 `MeResponse` (S1-02).
- `preferredLanguage`: `pt` ou `en`, obrigatório.
- `displayName`: 2–120; só para staff. Para clientes é ignorado (o nome está no perfil).

### 2. Perfil

**`GET /api/v1/me/profile`** (`getMyProfile`) → 200:

```json
{
  "fullName": "Ana Maria Mussa",
  "birthDate": "1990-05-14",
  "idDocType": "BI",
  "idDocNumberMasked": "*********345A",
  "nuitMasked": "*****6789",
  "address": "Av. Julius Nyerere, 1234",
  "province": "MAPUTO_CITY",
  "complete": true,
  "version": 3
}
```

- Os valores cifrados nunca saem em claro.
- Máscara do documento: todos os caracteres menos os últimos 4 trocados por `*`.
- Máscara do NUIT: `Nuit.masked()`.
- Campos por preencher saem `null` (omitidos).

**`PUT /api/v1/me/profile`** (`updateMyProfile`) → 200, mesma resposta.

| Campo | Obrigatório | Regras (`errors[].code` entre parênteses) |
| --- | --- | --- |
| `fullName` | sim | 2–120; letras (incluindo acentuadas), espaços, `'` e `-`; pelo menos duas palavras (`INVALID_NAME`) |
| `birthDate` | sim | data ISO; idade ≥ 18 anos à data de hoje em `Africa/Maputo` (`UNDERAGE`); ≤ 120 anos (`INVALID_DATE`) |
| `idDocType` | sim | `BI`, `PASSPORT`, `DIRE` |
| `idDocNumber` | se ainda não existir, ou se `idDocType` mudar | maiúsculas sem espaços, `^[A-Z0-9]{5,20}$` (`INVALID_DOCUMENT_NUMBER`); `null` mantém o actual; um valor substitui o actual |
| `nuit` | se ainda não existir | `Nuit` (`INVALID_NUIT`); `null` mantém o actual; um valor substitui o actual (o cliente pode corrigi-lo) |
| `address` | não | ≤ 300 |
| `province` | sim | código `Province` |
| `version` | sim | diferente da gravada → 409 `CONCURRENT_MODIFICATION` |

- Erros de validação → 400 `VALIDATION_ERROR` com `errors[]`.
- `idDocNumber` em falta quando é obrigatório → código `REQUIRED`.
- Auditoria `CUSTOMER.PROFILE_UPDATE`. O antes e o depois levam só os valores mascarados, nunca os cifrados nem os em claro.

### 3. Contactos

**`GET /api/v1/me/contacts`** (`listMyContacts`) → `{ "contacts": [ { "type": "MSISDN", "value": "+258841234567", "verified": true }, { "type": "EMAIL", "value": "ana@exemplo.co.mz", "verified": true } ] }`.
- O próprio cliente vê os seus contactos completos.
- Só aparecem os contactos que existem.

**`POST /api/v1/me/contacts`** (`startContactVerification`) `{ type, value, channel? }` → 202 `{ challengeId, channel, resendAfterSeconds, expiresAt, fallbackUsed }`.
- Normaliza o valor como no S1-03.
- Já pertence a outra conta de cliente → 409 `CONTACT_ALREADY_IN_USE`. Esta verificação precisa de ver as outras contas, que o âmbito `CUSTOMER` esconde: usa `SystemLookups.customerContactTaken(type, value, exceptUserId)` (`@RunAsSystem`; o bean é definido no S1-04 — se esta tarefa for feita antes, cria-o aqui com este método e o S1-04 acrescenta os seus).
- É igual ao contacto actual e já verificado → 409 `CONTACT_ALREADY_VERIFIED`.
- Senão cria um desafio `purpose = VERIFY_CONTACT`, `user_id` do cliente, e envia-o com as mesmas regras de canal, alternativa e limites do S1-03. Reutiliza o `OtpService` (`requestForContact`, `@RunAsSystem`), sem duplicar. Para reenviar, o ecrã chama de novo este mesmo endpoint.

**`POST /api/v1/me/contacts/verify`** (`verifyContact`) `{ challengeId, code }` → 200 `{ contacts: [...] }`.
- Mesmas validações do `verifyOtp` (expirado, errado, tentativas…).
- O desafio tem de ter `purpose = VERIFY_CONTACT` e o mesmo `user_id`, senão 404 `OTP_CHALLENGE_NOT_FOUND`.
- Volta a confirmar `CONTACT_ALREADY_IN_USE` (com `SystemLookups`), porque outra conta pode ter ficado com ele entretanto; o índice único é a última defesa, e uma violação dele também se traduz em 409 `CONTACT_ALREADY_IN_USE`, nunca em 500.
- Grava o novo valor no lugar do anterior do mesmo tipo, com `verified = true`.
- Auditoria `CUSTOMER.CONTACT_CHANGE`, com valores mascarados.

**`DELETE /api/v1/me/contacts/{type}`** (`removeMyContact`) → 204.
- Não pode ficar sem nenhum contacto verificado → 400 `LAST_CONTACT`.
- Auditoria `CUSTOMER.CONTACT_REMOVE`.

### 4. Códigos de erro novos

`CONTACT_ALREADY_IN_USE` (409), `CONTACT_ALREADY_VERIFIED` (409), `LAST_CONTACT` (400). Os `errors[].code` da tabela do perfil não são códigos de topo.
