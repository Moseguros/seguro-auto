## Contexto

Sprint 11, parte "Auditoria" (RF-32; `AGENTS.md` §6). A tabela `audit.audit_event` (S0-03) passa a ser só de inserção também na BD, regista as leituras de dados pessoais completos (documento de identificação e NUIT de pessoas singulares, ficheiros `SENSITIVE`) além das escritas, e ganha pesquisa e exportação para a plataforma e para cada seguradora (só os seus eventos). ADR-005 já previa que os descarregamentos passassem pelo backend para este registo.

O código de auditoria está em `mz.co.moseguros.shared.audit` (S0-03). Os endpoints ficam também aí (`shared.audit.api`, tag `Audit`): o `shared` é o dono do schema `audit`. O nome de quem fez a acção vem do `identity` por uma interface (secção 5), porque o `shared` não depende de nenhum módulo.

**Pressupõe:**
- `audit.audit_event`, `AuditService`, `AuditRecord`, `ActorType` (S0-03); grants do S1-01 (`select, insert` ao `moseguros_app`).
- Permissão `audit:read` (migração `V202704150100` do S11-01; se esta tarefa for feita antes, cria-a com o conteúdo exacto da secção 1 do S11-01).
- `GET /api/v1/files/{id}` e `document.file.classification` (`PUBLIC`, `PERSONAL`, `SENSITIVE`) (S2-01, ADR-005).
- `CurrentUser` (S1-02), `TenantContext` e `TenantSnapshot` (S1-01). O IP da coluna `ip` vem hoje de `AuditService.currentIp()` (estático, S0-03), que usa o primeiro valor de `X-Forwarded-For` sem verificar se o pedido veio de um proxy de confiança; o `shared.web.ClientIpResolver` com `moseguros.web.trusted-proxies` (decisão D15) **não existe no código do S0/S1** (ver "Questões").
- `IdentityApi.staffDisplayNames(Set<UUID>) → Map<UUID,String>` (criado no S8-05, decisão D10; corre no âmbito de quem chama).

## Objectivo

`UPDATE`, `DELETE` e `TRUNCATE` em `audit.audit_event` falham para todos; cada leitura de um documento de identificação, NUIT ou ficheiro sensível feita por staff fica registada como `READ_SENSITIVE`; o administrador da plataforma pesquisa e exporta todos os eventos, e o gestor da seguradora só os da sua.

## Especificação

### 1. Migração (`V202704150600__shared_audit_append_only.sql`)

```sql
alter table audit.audit_event
  add column access_type varchar(16) not null default 'WRITE'
  check (access_type in ('WRITE','READ_SENSITIVE'));

-- a aplicação só lê e insere
revoke all on audit.audit_event from public;
revoke update, delete, truncate, references, trigger on audit.audit_event from moseguros_app;
grant select, insert on audit.audit_event to moseguros_app;

-- ninguém altera nem apaga, nem o dono
create function audit.reject_mutation() returns trigger language plpgsql as $$
begin
  raise exception 'audit.audit_event is append-only' using errcode = '42501';
end $$;
create trigger audit_event_no_update_delete before update or delete on audit.audit_event
  for each row execute function audit.reject_mutation();
create trigger audit_event_no_truncate before truncate on audit.audit_event
  for each statement execute function audit.reject_mutation();

create index ix_audit_occurred  on audit.audit_event (occurred_at desc);
create index ix_audit_actor     on audit.audit_event (actor_id, occurred_at desc);
create index ix_audit_action    on audit.audit_event (action, occurred_at desc);
create index ix_audit_sensitive on audit.audit_event (occurred_at desc) where access_type = 'READ_SENSITIVE';

alter table audit.audit_event enable row level security;
create policy audit_event_insert on audit.audit_event for insert to moseguros_app with check (true);
create policy audit_event_select on audit.audit_event for select to moseguros_app
  using (current_setting('app.scope', true) in ('SYSTEM','PLATFORM')
         or (current_setting('app.scope', true) = 'ORG'
             and insurer_id = nullif(current_setting('app.insurer_id', true), '')::uuid));
```

- O "papel só de inserção" do modelo §2 é o `moseguros_app` com `select, insert` apenas; o gatilho protege também contra o dono.
- Qualquer âmbito insere (clientes também geram eventos); só `SYSTEM`, `PLATFORM` e a seguradora do evento lêem.
- Desligar o gatilho exige o dono e fica no registo de DDL do PostgreSQL; está escrito no `infra/README.md` numa linha "a auditoria só se altera com intervenção do DBA".

### 2. Leituras sensíveis (`AccessType.READ_SENSITIVE`)

```java
public record SensitiveReadRecord(UUID insurerId, String entityType, String entityId, Set<String> fields, String route) {}
// AuditService
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void recordSensitiveRead(SensitiveReadRecord r);
```

Regras:
1. Regista-se quando o **actor é `STAFF`** e lê, por um endpoint, um valor em claro de documento de identificação ou NUIT de pessoa singular, ou descarrega um ficheiro `SENSITIVE`. Leituras do próprio cliente sobre os seus dados não se registam.
2. `action = "<ENTIDADE>.READ_SENSITIVE"` (entidade em maiúsculas com `_`, ex.: `CUSTOMER_PROFILE.READ_SENSITIVE`, `FILE.READ_SENSITIVE`), `access_type = READ_SENSITIVE`, `before_state = null`, `after_state = { "fields": ["idDocNumber","nuit"], "route": "GET /api/v1/insurer/kyc/{id}" }` (padrão da rota, nunca os valores).
3. `insurer_id` = `TenantContext.current().insurerId()` de quem lê (não `TenantContext.insurerId()`, que lança `TENANT_REQUIRED` quando é `null`), ou o `insurer_id` do ficheiro; `null` na plataforma.
4. `REQUIRES_NEW` porque as leituras correm em transacções só de leitura. O registo fica mesmo que a resposta falhe depois.
5. **Sem registo não há leitura:** se `recordSensitiveRead` falhar, o pedido responde 500 e não devolve os dados.
6. **Endpoints:** anotação `@SensitiveRead(entityType = "CustomerProfile", entityId = "#id", fields = {"idDocNumber", "nuit"})` no método do controlador (`entityId` em SpEL sobre os argumentos). O `SensitiveReadAspect` (`@Around`) chama `recordSensitiveRead` depois de o método devolver e antes de a resposta ser escrita; se lançar, a excepção propaga-se.
7. **Ficheiros:** o serviço de descarga do `document` (S2-01), para `classification = SENSITIVE` e actor `STAFF`, chama `recordSensitiveRead(file.insurerId, "File", fileId, {"content"}, "GET /api/v1/files/{id}")` antes de abrir o conteúdo.

### 3. Escritas

`AuditService.record(AuditRecord)` não muda (grava `access_type = WRITE`; continua `@Transactional(propagation = MANDATORY)` e devolve o `UUID` do evento, S0-03). O contrato do `AuditRecord` (S0-03: `actorType`, `actorId` ≤ 64, `insurerId`, `action` ≤ 80, `entityType` ≤ 60, `entityId` ≤ 64, `beforeState`, `afterState`) não muda. O `AUDIT.EXPORT` da secção 6 é gravado por um método do `AuditExportService` com `REQUIRES_NEW` que chama `record` (o `record` exige uma transacção aberta).

### 4. Cobertura das leituras sensíveis (`SensitiveReadCoverageTest`)

Teste por reflexão sobre todos os métodos de `@RestController` em `mz.co.moseguros..api..`:
- percorre o tipo de retorno (desembrulha `ResponseEntity`, `Page`, `List`, `Optional`, `Set`, e componentes de `record` até 5 níveis);
- se encontrar um componente `String` (ou `Nuit`, o value object do S0-03 que `OrganizationResponse` e `OrganizationSummaryResponse` usam) chamado `idDocNumber`, `idDocumentNumber`, `documentNumber`, `licenceNumber` ou `nuit`, o método tem de ter `@SensitiveRead`;
- excepções, numa lista no próprio teste com o comentário "NUIT de pessoa colectiva (público, AGENTS.md §6)": `OrganizationResponse`, `OrganizationSummaryResponse` (S1-04), o DTO de `searchIntermediaries` (S11-01) e o DTO da frota (S7-06, NUIT da empresa). Acrescentar outra excepção exige justificação no PR.
- Os campos mascarados (`idDocNumberMasked`, `nuitMasked`, como no `CustomerProfileResponse` do S1-06) não contam.

O teste corre nesta tarefa e encontra os endpoints dos sprints anteriores que devolvem estes valores em claro (pelo menos a revisão de KYC do S4-01, cuja resposta tem `idDocNumber`; o detalhe da proposta para a seguradora do S4-05/S4-07, se devolver o documento ou o NUIT do tomador em claro; a declaração amigável e a carta de condução do S8-02/S9-04, se algum DTO de staff as devolver em claro); cada um recebe `@SensitiveRead` nesta tarefa. O número da carta de condução (cifrado, D9) conta como documento: acrescentar `licenceNumber` à lista de nomes de componentes do teste.

### 5. Nome de quem fez a acção (`ActorNameResolver`)

```java
public interface ActorNameResolver { Map<String, String> displayNames(Set<String> actorIds); }
```

- Implementada no `identity` (`AuditActorNameResolver`, sem `@RunAsSystem`: a regra do S1-01 só o permite em `…Listener`, `…Job` e `…SystemLookups`): converte os ids que são UUID e delega em `IdentityApi.staffDisplayNames` (S8-05), no âmbito de quem pesquisa. ### 6. Endpoints (tag `Audit`)

Todos exigem `audit:read`.
- Âmbito `PLATFORM`: todos os eventos; pode filtrar por `insurerId`.
- Âmbito `ORG` de seguradora: só os da sua seguradora (RLS e filtro no serviço). `insurerId` de outra → 403 `FORBIDDEN`.
- Outros âmbitos → 403.

**`GET /api/v1/audit-events`** (`searchAuditEvents`)

| Parâmetro | Regras |
| --- | --- |
| `from`, `to` | instantes ISO; por defeito os últimos 7 dias; `to ≥ from` (`DATE_BEFORE_START`); intervalo ≤ 366 dias (`OUT_OF_RANGE`) |
| `actorId` | exacto |
| `actorType` | `CUSTOMER`, `STAFF`, `SYSTEM`, `SERVICE` |
| `action` | exacto, ou prefixo terminado em `*` (`POLICY.*`) |
| `entityType`, `entityId` | exactos |
| `accessType` | `WRITE`, `READ_SENSITIVE` |
| `insurerId` | só `PLATFORM` |
| `page`, `size` | `size` ≤ 100 |
| `sort` | só `occurredAt,asc` ou `occurredAt,desc` (defeito) |

→ página de:

```json
{ "id": "…", "occurredAt": "2027-04-20T09:12:03Z", "actorId": "0193…", "actorType": "STAFF",
  "actorDisplayName": "Joana Subscritora", "insurerId": "…", "action": "CUSTOMER_PROFILE.READ_SENSITIVE",
  "accessType": "READ_SENSITIVE", "entityType": "CustomerProfile", "entityId": "…",
  "ip": "196.28.10.4", "traceId": "4bf92f3577b34da6" }
```

**`GET /api/v1/audit-events/{id}`** (`getAuditEvent`) → o mesmo, mais `beforeState` e `afterState` (objectos JSON tal como gravados). De outra seguradora ou inexistente → 404 `AUDIT_EVENT_NOT_FOUND`.

**`GET /api/v1/audit-events/export`** (`exportAuditEvents`) — os mesmos filtros; `from` e `to` obrigatórios.
- Conta primeiro; mais de `moseguros.audit.export-max-rows` (100 000) → 400 `AUDIT_EXPORT_TOO_LARGE`.
- Grava `AUDIT.EXPORT` (`entityType = "AuditEvent"`, `entityId = "export"`, `after_state = { filtros, rowCount }`) com `REQUIRES_NEW` antes de começar a enviar.
- Resposta CSV em fluxo (`StreamingResponseBody`, lido em páginas de 1 000 por `occurred_at`): UTF-8 com BOM, separador `;`, `\r\n`, cabeçalho `occurred_at;actor_type;actor_id;actor_display_name;insurer_id;action;access_type;entity_type;entity_id;ip;trace_id;before_state;after_state`; JSON entre aspas, com as aspas duplicadas.
- `Content-Disposition: attachment; filename="auditoria_<from>_<to>.csv"` (datas `Africa/Maputo`), `Cache-Control: private, no-store`.

A pesquisa e a leitura de eventos não geram eventos (os eventos já têm os dados mascarados); só a exportação.

## Critérios de aceitação

- [ ] `AuditAppendOnlyIT`:
  - ligado como `moseguros_app_user`: `update audit.audit_event set action = 'X'` → SQLState `42501`; `delete` → `42501`; `insert` funciona;
  - ligado como dono: `update` e `delete` → erro do gatilho ("append-only"); `truncate` → erro.
- [ ] `AuditRlsIT`: evento da seguradora A visível em `ORG` de A, invisível em `ORG` de B e em `CUSTOMER`; em `CUSTOMER` a inserção funciona.
- [ ] `SensitiveReadIT`:
  - um `UNDERWRITER` descarrega um ficheiro `SENSITIVE` → um evento `FILE.READ_SENSITIVE` com `insurer_id`, `fields = ["content"]` e sem valores pessoais;
  - o cliente descarrega o seu ficheiro → nenhum evento;
  - um endpoint de teste com `@SensitiveRead` numa transacção só de leitura grava o evento;
  - com o `AuditService` a falhar (bean de teste), a resposta é 500 e o corpo não tem o valor.
- [ ] `SensitiveReadCoverageTest` passa; a lista de métodos anotados nesta tarefa está no PR.
- [ ] `AuditSearchIT`: filtros por actor, acção exacta e por prefixo, entidade, tipo de acesso e período; paginação; `actorDisplayName` preenchido para staff e `null` para cliente (e, para o gestor da seguradora, `null` para o staff da plataforma); o gestor da seguradora A só vê eventos de A e com `insurerId` de B → 403; intervalo de 400 dias → 400; cliente, mediador e `UNDERWRITER` → 403; evento de B por id → 404.
- [ ] `AuditExportIT`: o CSV tem o cabeçalho e as linhas filtradas; fica um evento `AUDIT.EXPORT`; com o limite a 10 no teste e 11 eventos → 400 `AUDIT_EXPORT_TOO_LARGE`.
- [ ] `AuditServiceIT` (S0-03) adaptado e a passar; `ModularityTest` (o `shared` não depende de nenhum módulo; o `identity` implementa `ActorNameResolver`); `api/openapi.yaml`, `api/error-codes.json` e traduções em dia.

## Questões

- 02/11/2026 — **Prazo de conservação dos eventos de auditoria.** Sem valor legal conhecido; nada se apaga. Não bloqueia.
- 02/11/2026 — **Leituras pelo próprio cliente** não se registam (regra 1 da secção 2). Confirmar com o encarregado de protecção de dados. Não bloqueia.
- 02/11/2026 — **`ClientIpResolver` (D15) não existe.** O S0-03 implementou o IP da auditoria como `AuditService.currentIp()` estático, que aceita o primeiro `X-Forwarded-For` de qualquer origem (um cliente pode escrever o IP que quiser na auditoria). As fichas S4-04, S6-08, S11-06 e S12-01 pressupõem `shared.web.ClientIpResolver` e `moseguros.web.trusted-proxies`. Se, quando esta tarefa começar, nenhuma ficha anterior os tiver criado, esta tarefa cria-os (`X-Forwarded-For` só quando o endereço remoto está em `trusted-proxies`, senão o endereço remoto) e o `AuditService` passa a usá-los; confirmar no modelo transversal (§7) qual ficha é a dona. Não bloqueia.
