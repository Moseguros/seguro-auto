## Contexto

ADR-003. O backend emite e valida os seus próprios JWT. Esta tarefa cria a emissão de tokens (usada pelo OTP no S1-03 e pelo login de staff no S1-05), a renovação com rotação, o logout, a validação dos pedidos, o preenchimento do `TenantContext` a partir do token, e `GET /me`.

## Objectivo

Um pedido com um JWT válido é autenticado, as permissões do token chegam ao `@PreAuthorize`, o `TenantContext` fica preenchido, e o par de tokens pode ser renovado e revogado.

## Especificação

### 1. Chaves e configuração

```yaml
moseguros:
  security:
    jwt:
      issuer: https://api.moseguros.co.mz
      audience: moseguros-api
      access-token-ttl: PT15M
      customer-refresh-ttl: P60D        # deslizante: cada renovação dá mais 60 dias
      staff-refresh-ttl: PT12H          # absoluto: a sessão de staff acaba 12 h depois do login
      key-id: ${MOSEGUROS_JWT_KEY_ID:dev}
      private-key: ${MOSEGUROS_JWT_PRIVATE_KEY:}   # PEM PKCS#8, RSA 2048
```

- Com `private-key` vazio: nos perfis `local` e `test` gera-se um par RSA 2048 no arranque e regista-se um aviso (`WARN`, sem a chave); noutros perfis a aplicação **não arranca**.
- A chave pública deriva-se da privada. `GET /.well-known/jwks.json` (público, `operationId: getJwks`, tag `Identity`) devolve o JWKS com `kid`, `kty`, `alg: RS256`, `use: sig`, `n`, `e`.

### 2. Token de acesso

JWT RS256 com cabeçalho `kid`. Claims:

| Claim | Conteúdo |
| --- | --- |
| `iss`, `aud`, `iat`, `exp`, `jti` | normais; `exp = iat + 15 min`; `jti` UUID v7 |
| `sub` | `user_account.id` |
| `type` | `CUSTOMER` ou `STAFF` |
| `orgId` | id da organização ou ausente |
| `orgType` | tipo da organização ou ausente |
| `roles` | lista de códigos de perfil |
| `permissions` | lista de permissões (união das permissões dos perfis, ordenada) |

- `TokenService.issue(UserAccount, String deviceInfo)` devolve `TokenPair(accessToken, refreshToken, expiresIn)`; `expiresIn` em segundos (900).
- O `orgType` vem do módulo `organization`: `identity` chama `OrganizationApi.findSummary(UUID)` → `Optional<OrganizationSummary(UUID id, OrganizationType type, OrganizationStatus status, String displayName)>`. Criar `mz.co.moseguros.organization.OrganizationApi` e o record `OrganizationSummary` nesta tarefa (só leitura), no pacote raiz do módulo, junto dos enums `OrganizationType` e `OrganizationStatus` (S1-01). A dependência é só `identity → organization`; `organization` nunca depende de `identity`.

### 3. Refresh token e sessões

- Valor opaco: 32 bytes aleatórios (`SecureRandom`) em Base64 URL sem `=`. Grava-se só o SHA-256 em hexadecimal.
- Login (OTP ou staff) cria uma família nova (`family_id = Ids.newId()`).
  - Cliente: `expires_at = agora + 60 dias`, `session_expires_at = null`.
  - Staff: `expires_at = session_expires_at = agora + 12 h`.
- **`POST /api/v1/auth/refresh`** (público; `operationId: refreshToken`) `{ "refreshToken": "..." }` → 200 `TokenResponse { accessToken, refreshToken, expiresIn }`:
  - token desconhecido, expirado, ou conta não `ACTIVE` → 401 `REFRESH_TOKEN_INVALID`;
  - token já revogado com razão `ROTATED` (reutilização) → revoga **toda a família** com `REUSE_DETECTED` e responde 401 `REFRESH_TOKEN_REUSED`;
  - token revogado por outra razão → 401 `REFRESH_TOKEN_INVALID`;
  - staff cuja organização está `SUSPENDED` → revoga a família (`ORG_SUSPENDED`) e 401 `REFRESH_TOKEN_INVALID`;
  - caso normal: revoga o actual (`ROTATED`, `replaced_by_id`), cria um novo na mesma família. Cliente: `expires_at = agora + 60 dias`. Staff: `expires_at = session_expires_at` (não se estende). Os perfis e permissões são lidos de novo da BD (uma mudança de perfis vale na renovação seguinte).
  - A linha do token é lida com `PESSIMISTIC_WRITE` para que dois pedidos simultâneos com o mesmo token não gerem dois sucessores: o segundo vê-o revogado e cai na regra de reutilização.
- **`POST /api/v1/auth/logout`** (público; `operationId: logoutSession`) `{ "refreshToken": "..." }` → 204 sempre (mesmo com token desconhecido); se existir, revoga a família com `LOGOUT`. O token de acesso continua válido até expirar (≤ 15 min); é aceite.
- `SessionService.revokeAllForUser(userId, reason)` revoga todas as famílias activas do utilizador (usado por S1-05).
- Todas estas operações correm com `@RunAsSystem` (não há utilizador autenticado).

### 4. Validação dos pedidos

- `SecurityConfig`: `oauth2ResourceServer().jwt()` com `NimbusJwtDecoder` pela chave pública local, validando `iss`, `aud`, `exp` (tolerância 30 s).
- `JwtClaimsConverter`: autoridades = cada entrada de `permissions` tal e qual (`otp-settings:manage`) + cada perfil com prefixo `ROLE_` (`ROLE_PLATFORM_ADMIN`). Autorização sempre por permissão: `@PreAuthorize("hasAuthority('organization:manage')")`.
- Ligar `@EnableMethodSecurity`.
- Caminhos públicos: os do S0-02, mais `/api/v1/auth/**` e `/.well-known/jwks.json`. As tarefas seguintes acrescentam os seus (S1-03 os recibos de entrega).
- **Nos caminhos públicos o cabeçalho `Authorization` é ignorado.** Sem isto, o resource server responde 401 a um token de acesso expirado mesmo num caminho `permitAll`, e a renovação (que é chamada precisamente quando o token expirou) falharia sempre. Implementar com um `BearerTokenResolver` que devolve `null` para os caminhos públicos e delega no `DefaultBearerTokenResolver` nos outros. Os clientes web e mobile também não enviam o cabeçalho para `/api/v1/auth/**` (S1-07, S1-09).
- Token inválido ou ausente em caminho protegido → 401 `UNAUTHORIZED` (já existe); sem a permissão → 403 `FORBIDDEN`.
- `CurrentUser` (componente): `id()`, `type()`, `orgId()`, `orgType()`, `hasPermission(String)`, lidos do `Jwt` no `SecurityContext`.

### 5. Âmbito a partir do token (`TenantContextFilter`)

Filtro depois da autenticação. Com `Jwt` presente:

| Token | `TenantSnapshot` |
| --- | --- |
| `type = CUSTOMER` | `CUSTOMER`, `userId = sub` |
| `type = STAFF`, sem `orgId`, com perfil `PLATFORM_ADMIN` | `PLATFORM`, `userId` |
| `type = STAFF`, com `orgId` | `ORG`, `userId`, `orgId`, `insurerId = orgId` se `orgType = INSURER` |
| outro caso | `NONE` |

Sem token: `NONE`. O filtro limpa o `TenantContext` no `finally`. O `AuditorAware` do S0-03 passa a devolver o `sub`.

### 6. `GET /api/v1/me`

`operationId: getMe`, tag `Identity`, qualquer utilizador autenticado. Resposta `MeResponse`:

```json
{
  "id": "0192f0c4-…",
  "type": "CUSTOMER",
  "displayName": "Ana Mussa",
  "msisdn": "+258841234567",
  "msisdnVerified": true,
  "email": null,
  "emailVerified": false,
  "preferredLanguage": "pt",
  "organization": null,
  "roles": ["CUSTOMER"],
  "permissions": ["self:profile"],
  "profileComplete": false
}
```

- `organization` (staff): `{ "id", "type", "displayName" }`.
- `displayName`: staff → `display_name`; cliente → `full_name` do perfil (ou `null`).
- `profileComplete`: só clientes (`CustomerProfile.isComplete()`); `null` para staff (omitido pelo `non_null`).
- `PUT /me` fica no S1-06.

## Questões

- 02/11/2026 — **`GlobalExceptionHandler` sem precedência:** com `spring.mvc.problemdetails.enabled`, o `ProblemDetailsExceptionHandler` do Spring Boot também trata `MethodArgumentNotValidException` e ganhava ao nosso, devolvendo 400 sem `code` nem `errors[]` (só se via em pedidos reais; os testes do S0 usavam `standaloneSetup`). Acrescentei `@Order(HIGHEST_PRECEDENCE)` ao `GlobalExceptionHandler`. Não bloqueia.
- 02/11/2026 — **`FieldErrorCodes`:** tem os códigos dos value objects (que continuam também em `ErrorCodes`, porque o domínio os lança como erro de topo, ex.: `Organization` com telefone inválido) e o `NOT_BLANK` do `@NotBlank` do `RefreshTokenRequest` (o `GlobalExceptionHandler.codeOf` converte o nome da restrição: `@Size` → `SIZE`, não `TOO_SHORT` como no exemplo do §8). Os códigos das definições de OTP ficam em `ErrorCodes` até o S1-03 os passar. As traduções `errors.REFRESH_TOKEN_INVALID`, `errors.REFRESH_TOKEN_REUSED` e `validation.NOT_BLANK` foram acrescentadas na web e na app (pt e en). Não bloqueia.
- 02/11/2026 — **`GET /me`:** `roles` e `permissions` vêm do token (são os que a API aplica até à renovação seguinte); a conta, o perfil e a organização lêem-se da BD no âmbito do próprio pedido (RLS). Um staff sem organização e sem `PLATFORM_ADMIN` fica em `NONE`, não vê a própria conta e recebe 401. Se a intenção for ler os perfis da BD, muda-se no `MeService`. Não bloqueia.
- 02/11/2026 — **Pormenores decididos:** o `JwtDecoder` usa o `Clock` da aplicação (os testes controlam o tempo também na validação); na renovação, staff cuja organização já não existe é tratado como suspensa (`ORG_SUSPENDED`); `POST /auth/logout` aceita corpo vazio (204); as claims ficam em `shared.security.JwtClaims`; o `TokenPair` está no pacote raiz de `identity` (é devolvido pelo `IdentityApi`); o endpoint de teste é `/api/v1/test-probes/**` (só no perfil `test`, `@Hidden`, fora do contrato). Não bloqueia.
- 02/11/2026 — **Cobertura:** o relatório JaCoCo do `verify` só junta os testes unitários (`jacoco.exec`); a cobertura dos `*IT` (`jacoco-it.exec`) não entra. Acrescentei `SessionServiceTest` e `MeServiceTest` para a camada `application` ficar acima de 80% só com unitários. Juntar os dois relatórios fica para o S0-08/CI, se se quiser. Não bloqueia.
