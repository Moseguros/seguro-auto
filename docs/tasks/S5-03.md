## Contexto

O adaptador M-Pesa (S5-04) é a implementação real; em desenvolvimento e testes aponta para um simulador que se comporta como a API M-Pesa da Vodacom Moçambique (`AGENTS.md` §9 regra 9). O simulador permite testar todos os resultados (sucesso, cancelamento, saldo insuficiente, timeout, duplicado, falha) sem dinheiro nem credenciais reais.

**A fonte de verdade é a documentação oficial em `developer.mpesa.vm.co.mz`.** Os caminhos, portas, campos e códigos abaixo vêm do plano. Antes de fechar a tarefa, quem implementa abre a documentação oficial (secções C2B, *Query Transaction Status* e *Reversal*, e a tabela de códigos de resposta) e confirma cada linha das tabelas desta ficha; o que for diferente regista-se em "Questões" com a versão correcta, e o simulador segue a documentação oficial.

**Pressupõe:** S0-07 (padrão de Dockerfile e de mock do `sms-mock`, projecto Maven autónomo com `mvnw` próprio, alargado no S1-03; `scripts/images.txt`). Não usa nada do backend.

## Objectivo

`docker compose up` sobe o `mpesa-mock` nas portas 18352, 18353 e 18354; um pedido C2B com um token válido devolve o resultado definido pelos últimos dígitos do número; a consulta e a reversão funcionam sobre as transacções registadas; uma página mostra as transacções.

## Especificação

### 1. Portas e caminhos

| Operação | Método | Porta | Caminho |
| --- | --- | --- | --- |
| C2B (cliente paga) | `POST` | 18352 | `/ipg/v1x/c2bPayment/singleStage/` |
| Consulta de estado | `GET` | 18353 | `/ipg/v1x/queryTransactionStatus/` |
| Reversão | `PUT` | 18354 | `/ipg/v1x/reversal/` |
| Apoio (só do simulador) | vários | 18352 | `/__mock/**` e `/` |
| Actuator (`health`) | `GET` | 18350 | `/actuator/health` |

- Tomcat com o conector principal em 18352 e conectores adicionais em 18353 e 18354 (`TomcatServletWebServerFactory.addAdditionalTomcatConnectors`); `management.server.port: 18350`.
- `PortGuardFilter`: cada caminho só responde na sua porta; noutra porta → 404.
- O caminho aceita-se com e sem a barra final.

### 2. Autenticação (todas as operações, excepto `/__mock` e `/`)

Cabeçalhos esperados: `Content-Type: application/json` (C2B e reversão), `Authorization: Bearer <token>`, `Origin: <origem>`.

1. `token` = Base64 de `RSA/ECB/PKCS1Padding(apiKey)` cifrado com a chave pública do simulador. O simulador decifra com `keys/mock-private.pem`; resultado diferente de `MOCK_API_KEY`, token ausente ou mal formado → **INS-2**.
2. `Origin` diferente de `MOCK_ALLOWED_ORIGIN` ou ausente → **INS-26** (a confirmar na documentação).
3. `input_ServiceProviderCode` diferente de `MOCK_SERVICE_PROVIDER_CODE` → **INS-13**.

Par de chaves: RSA 2048 gerado uma vez com `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048` (comando completo no `README.md`), PKCS#8 PEM para a privada; a pública em PEM (`mock-public.pem`) e em Base64 DER numa linha (`mock-public.b64`, o formato em que a Vodacom entrega a chave). Os três ficheiros começam com o comentário (ou ficam acompanhados no `README.md`, para o `.b64`) **"Chave só para o simulador. Nunca usar fora do desenvolvimento."**

### 4. C2B — `POST :18352/ipg/v1x/c2bPayment/singleStage/`

Corpo:

| Campo | Regra no simulador (falha → código) |
| --- | --- |
| `input_TransactionReference` | obrigatório (INS-20); `^[A-Za-z0-9]{1,20}$` (INS-21) |
| `input_CustomerMSISDN` | obrigatório; `^258(84|85)[0-9]{7}$` (INS-21) |
| `input_Amount` | obrigatório; texto `^[0-9]+(\.[0-9]{1,2})?$` e > 0 (INS-21) |
| `input_ThirdPartyReference` | obrigatório; `^[A-Za-z0-9]{1,20}$` (INS-21); já usado noutro pedido → INS-10 |
| `input_ServiceProviderCode` | obrigatório; secção 2 (INS-13) |

Ordem das verificações: autenticação (secção 2, passos 1 e 2) → campos em falta (INS-20) → formato (INS-21) → código de serviço (INS-13) → duplicado (INS-10) → comportamento.

**Comportamento pelos três últimos dígitos de `input_CustomerMSISDN`:**

| Final | Resposta do C2B | Estado registado (para a consulta) |
| --- | --- | --- |
| `000` | INS-0 depois de `MOCK_DELAY_000_SECONDS` | `Pending` durante a espera, depois `Completed` |
| `001` | INS-5 (cancelado pelo cliente) depois de 2 s | `Cancelled` |
| `002` | INS-2006 (saldo insuficiente) depois de 2 s | `Failed` |
| `003` | INS-0 só depois de `MOCK_SLOW_DELAY_SECONDS` (força o timeout do cliente) | `Pending` durante a espera, depois `Completed` (mesmo que o cliente já tenha desistido) |
| `004` | INS-10 imediatamente | `Cancelled` |
| `005` | INS-6 (transacção falhou) depois de 2 s | `Failed` |
| outro | INS-0 depois de `MOCK_DEFAULT_DELAY_SECONDS` | `Pending`, depois `Completed` |

Resposta (JSON, sempre com estes campos):

```json
{
  "output_ConversationID": "f02d0f7f6b2a4d4c9b0c1e2d3f4a5b6c",
  "output_ResponseCode": "INS-0",
  "output_ResponseDesc": "Request processed successfully",
  "output_ThirdPartyReference": "ABC123XYZ",
  "output_TransactionID": "5C1400CVRO"
}
```

- `output_TransactionID`: 10 caracteres `[0-9A-Z]` aleatórios; `output_ConversationID`: 32 hexadecimais. Em erros de autenticação e de campos, `output_TransactionID` vem vazio.
- A transacção fica registada (excepto nos erros de autenticação, campos e código de serviço) com: `transactionId`, `conversationId`, `thirdPartyReference`, `transactionReference`, `msisdn`, `amount`, `status`, `responseCode`, `createdAt`, `completedAt`.
- A espera não bloqueia outros pedidos (Tomcat com 200 threads; cada pedido espera na sua thread).

### 5. Consulta — `GET :18353/ipg/v1x/queryTransactionStatus/`

Parâmetros de consulta: `input_QueryReference` (o `TransactionID` **ou** a `ThirdPartyReference` do C2B original), `input_ServiceProviderCode`, `input_ThirdPartyReference` (nova, desta consulta). Mesma autenticação. Em falta → INS-20.

```json
{
  "output_ConversationID": "…",
  "output_ResponseCode": "INS-0",
  "output_ResponseDesc": "Request processed successfully",
  "output_ResponseTransactionStatus": "Completed",
  "output_ThirdPartyReference": "<a desta consulta>"
}
```

- `output_ResponseTransactionStatus`: o estado registado (`Pending`, `Completed`, `Cancelled`, `Failed`, `Reversed`).
- Referência desconhecida → INS-0 com estado `N/A` (a confirmar na documentação).

### 6. Reversão — `PUT :18354/ipg/v1x/reversal/`

Campos: `input_TransactionID`, `input_SecurityCredential`, `input_InitiatorIdentifier`, `input_ThirdPartyReference`, `input_ServiceProviderCode`, `input_ReversalAmount` (opcional; ausente = total). Mesma autenticação.

| Situação | Código |
| --- | --- |
| campo obrigatório em falta | INS-20 |
| `input_InitiatorIdentifier ≠ MOCK_INITIATOR_IDENTIFIER` | INS-24 (a confirmar) |
| `input_SecurityCredential ≠ MOCK_SECURITY_CREDENTIAL` | INS-25 |
| transacção desconhecida ou não `Completed` | INS-18 (a confirmar) |
| `input_ReversalAmount` maior que o montante original | INS-15 |
| sucesso | INS-0, `output_TransactionID` novo; a original passa a `Reversed` |

### 8. Endpoints de apoio (porta 18352, sem autenticação)
