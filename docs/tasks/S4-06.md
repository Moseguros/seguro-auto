## Contexto

O corretor ou agente cota para um cliente identificado pelo telemóvel (S3, `quote:create-for-client`) e agora transforma essa cotação numa proposta, completa-a com o cliente (tomador, declarações, adequação, vistoria), faz a assinatura assistida (o código chega ao telemóvel do cliente, que o diz ao mediador) e submete. O cliente vê a proposta na sua área e também a pode completar e assinar sozinho. Plano: "`/mediador/propostas` para criar e submeter em nome do cliente (o cliente assina por OTP no seu telemóvel)"; "mediador não vê propostas de outros mediadores".

**Pressupõe:**
- S4-01: permissão `proposal:create-for-client` (`BROKER`, `AGENT`); `IdentityApi.customer(UUID)`.
- S4-02: `createProposal` e as suas regras; `PUT /proposals/{id}` (regra do tomador quando `channel ≠ BROKER`); RLS `s = 'ORG' and broker_org_id = o`; colunas `channel`, `broker_org_id`, `broker_name`, `created_by_user_id`; os endpoints de declarações e adequação aceitam já `proposal:create-for-client`.
- S4-03: endpoints de vistoria aceitam já `proposal:create-for-client`.
- S4-04: `requestProposalSignature`/`confirmProposalSignature`, `SignOtpRequest.assistedByName`, colunas `sign_request_assisted_by_user_id`, `signature.assisted_by_*`, mensagem `otp.sign-assisted.sms`.
- S4-05: `submitProposal` (aceita `proposal:create-for-client`), regras e decisão, `ProposalNotifier`.
- S3-02: a cotação feita pelo mediador tem `QuoteView.brokerOrgId` = organização do mediador e `QuoteView.userId` = conta `CUSTOMER` do cliente (criada ou encontrada pelo telemóvel no S3-02). Se o S3-02 não guardar a organização do mediador na cotação, pare e pergunte.
- S1-02: `CurrentUser.orgId()`, `orgType()`.

## Objectivo

Um mediador cria a proposta a partir da sua cotação para o cliente, preenche o tomador se o perfil do cliente estiver incompleto, completa os passos com o cliente, pede o código de assinatura (que chega ao telemóvel do cliente), confirma-o e submete. Outro mediador não vê nem altera essa proposta.

## Especificação

### 1. Coluna nova (`V202701010600__proposal_broker.sql`)

`alter table proposal.proposal add column policyholder_source varchar(10) not null default 'PROFILE' check (policyholder_source in ('PROFILE','BROKER'));`

- `PROFILE`: o tomador é copiado do perfil do cliente (S4-02).
- `BROKER`: o tomador foi preenchido pelo mediador porque o perfil do cliente estava incompleto. Os dados ficam **só na proposta**: o perfil do cliente (`identity.customer_profile`) não é alterado pelo mediador.

### 2. Quem é mediador

Todos os endpoints `/api/v1/broker/**` exigem `proposal:create-for-client` **e** âmbito `ORG` com `orgType` `BROKER` ou `AGENT` (senão 403 `FORBIDDEN`). Nos endpoints partilhados `/proposals/{id}/…` (S4-02 a S4-05), o mediador só actua sobre propostas com `broker_org_id` = a sua organização (RLS + serviço; senão 404 `PROPOSAL_NOT_FOUND`). Dois utilizadores da mesma corretora vêem e trabalham as mesmas propostas.

### 3. Endpoints (tag `Proposal`)

**`POST /api/v1/broker/proposals`** (`createProposalForClient`) → 201 `ProposalResponse` + `Location`.

```json
{
  "quoteId": "0193…",
  "policyholder": {
    "fullName": "João Carlos Sitoe", "birthDate": "1985-11-02", "idDocType": "BI",
    "idDocNumber": "110100765432B", "nuit": "123456789",
    "address": "Bairro da Machava, Q. 12", "province": "MAPUTO"
  }
}
```

Passos, por ordem:
1. `RatingApi.quote(quoteId)`; não existe ou `brokerOrgId ≠` organização actual → 404 `QUOTE_NOT_FOUND`.
2. As regras 2–4 do `createProposal` (S4-02): `PROPOSAL_ALREADY_EXISTS`, `QUOTE_NOT_AVAILABLE`, `QUOTE_EXPIRED`, `INSURER_NOT_ACTIVE`.
3. Tomador:
   - perfil do cliente completo (`IdentityApi.customer(quote.userId).profileComplete`) → copia-o (`policyholder_source = PROFILE`); se o pedido trouxer `policyholder` → 400 campo `policyholder` `NOT_ALLOWED`;
   - perfil incompleto → `policyholder` obrigatório (`REQUIRED`), com as regras do S1-06 para cada campo (`INVALID_NAME`, `UNDERAGE`, `INVALID_DATE`, `INVALID_DOCUMENT_NUMBER`, `INVALID_NUIT`, `TOO_LONG`, província válida); todos obrigatórios excepto `address`; `policyholder_source = BROKER`. Telemóvel e e-mail do tomador vêm da conta do cliente (não do pedido).
4. Grava como no S4-02 com `channel = BROKER`, `broker_org_id`, `broker_name` (nome da organização actual), `created_by_user_id` = utilizador do mediador. Auditoria `PROPOSAL.CREATE` (`actorType = STAFF`; o tomador só com valores mascarados).
5. E-mail ao cliente, se tiver e-mail verificado: `proposal.created-by-broker` (secção 6).

**`GET /api/v1/broker/proposals`** (`listBrokerProposals`) — filtros `status` (repetível), `q` (número exacto ou nome do tomador), paginação, por defeito `createdAt,desc` → página de `BrokerProposalSummaryResponse { id, number, status, customerName, customerMsisdnMasked, insurer: { id, displayName }, productName, total, createdAt, expiresAt, checklist }`.

**`PUT /api/v1/broker/proposals/{id}`** (`updateBrokerProposal`) `{ "startDate": "2027-01-10", "policyholder": { … }, "version": 3 }` → 200 `ProposalResponse`.
- Proposta editável → senão 409 `PROPOSAL_NOT_EDITABLE`; `version` → 409.
- `startDate`: regras do S4-02.
- `policyholder`: só permitido com `policyholder_source = BROKER` (com `PROFILE` → `NOT_ALLOWED`); mesmas validações; `idDocNumber` e `nuit` podem vir `null` para manter os actuais (como no S1-06).
- `content_revision + 1`, `Proposal.contentChanged()`, `expires_at`; auditoria `PROPOSAL.UPDATE`.

Regra do `PUT /api/v1/proposals/{id}` (S4-02) quando o **cliente** altera uma proposta `BROKER`: com `policyholder_source = PROFILE`, copia de novo o perfil como no S4-02; com `BROKER`, mantém o tomador preenchido pelo mediador e altera só a data. Uma proposta `BROKER` só se cria por `createProposalForClient`.

### 4. Assinatura assistida

No `requestProposalSignature` (S4-04), quando quem pede é um mediador (âmbito `ORG` da organização da proposta):
- o código vai para o **telemóvel da conta do cliente** (regras de destino do S4-04; o mediador nunca indica outro número);
- `SignOtpRequest.assistedByName` = nome da organização do mediador → texto `otp.sign-assisted.sms` do S4-04;
- grava `sign_request_assisted_by_user_id` = utilizador do mediador.

No `confirmProposalSignature`:
- se o pedido em curso foi assistido, só o mesmo mediador (ou outro utilizador da mesma organização) ou o próprio cliente podem confirmar; o cliente que confirma um pedido assistido conta como assinatura não assistida;
- `signature.assisted_by_user_id` e `assisted_by_org_id` preenchidos quando quem confirma é o mediador; `signature.assisted = true` no `ProposalResponse`.

O signatário é sempre o cliente (`signer_user_id = customer_user_id`).

### 5. `ProposalResponse` (acrescentar)

- `broker`: `{ "id": "…", "displayName": "Corretora Demo" }` com `channel = BROKER`, senão `null`.
- `policyholderSource`: `PROFILE` ou `BROKER`.
- Para o mediador, `policyholder` sai como para o cliente (valores mascarados).

### 6. Mensagem ao cliente

```properties
proposal.created-by-broker.email.subject={1} preparou uma proposta de seguro para si
proposal.created-by-broker.email.body=Olá {2},\n\n{1} preparou a proposta {0} da {3}, com o prémio total de {4}.\n\nPode vê-la, completá-la e assiná-la na aplicação MoSeguros ou em {5}. Se não conhece este mediador, não assine e contacte-nos.\n\nEquipa MoSeguros
```

`{0}` número, `{1}` mediador, `{2}` primeiro nome do cliente (ou "cliente"), `{3}` seguradora, `{4}` total formatado, `{5}` `{moseguros.web.base-url}/cliente/propostas/{id}`. Versão `en`: "{1} has prepared an insurance proposal for you" / "Hello {2},\n\n{1} has prepared proposal {0} from {3}, with a total premium of {4}.\n\nYou can view, complete and sign it in the MoSeguros app or at {5}. If you do not know this intermediary, do not sign it and contact us.\n\nThe MoSeguros team".

Os e-mails de decisão do S4-05 vão para o cliente como em qualquer proposta; o mediador acompanha pela lista.

### 7. Códigos de erro

Nenhum código de topo novo. Usa `FORBIDDEN`, `QUOTE_NOT_FOUND`, `PROPOSAL_NOT_FOUND`, `PROPOSAL_NOT_EDITABLE` e os códigos de campo do S1-06 e do S4-02.

## Critérios de aceitação

- [ ] `BrokerProposalIT` (Testcontainers; cotação de mediador criada pelo S3-02 ou preparada pelo teste):
  - cliente com perfil completo: criar com `policyholder` → 400 `NOT_ALLOWED`; sem ele → 201, `channel = BROKER`, `policyholderSource = PROFILE`, `broker` preenchido;
  - cliente com perfil incompleto: sem `policyholder` → 400 `REQUIRED`; com NUIT inválido → `INVALID_NUIT`; válido → 201, `policyholderSource = BROKER`, e o `customer_profile` do cliente continua igual na BD;
  - cotação feita pelo próprio cliente (sem `brokerOrgId`) → 404 `QUOTE_NOT_FOUND`;
  - o mediador grava declarações e adequação, envia a vistoria, assina (secção 4) e submete; a proposta é aceite ou vai para análise como no S4-05;
  - `GET /me/proposals` do cliente mostra a proposta e o cliente consegue abri-la;
  - `PUT /broker/proposals/{id}` com `policyholder` numa proposta `PROFILE` → `NOT_ALLOWED`.
- [ ] `AssistedSignatureIT`: o pedido do mediador envia o código para o telemóvel da conta do cliente com o texto `otp.sign-assisted.sms` (canal falso); confirmar com o código → `signature.assisted = true`, `assisted_by_org_id` = organização do mediador; um mediador de outra organização não confirma (404); o cliente pode confirmar o mesmo pedido na sua sessão.
- [ ] `BrokerProposalIsolationIT` (plano: "mediador não vê propostas de outros mediadores"): o mediador da corretora B não lista nem abre, altera, assina ou submete (404) propostas da corretora A; um utilizador de seguradora não usa `/broker/proposals` (403); um cliente → 403; um `ORG_ADMIN` de uma oficina com a permissão atribuída à força no teste → 403 (tipo de organização errado); sem token → 401.
- [ ] Os logs não têm o número do documento nem o NUIT do tomador (captura de logs).
- [ ] `api/openapi.yaml`, `api/error-codes.json` e clientes regenerados; `ModularityTest` passa.
