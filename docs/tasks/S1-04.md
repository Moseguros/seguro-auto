## Especificação

### 1. Organizações (módulo `organization`, tag `Organization`, permissões `organization:read` / `organization:manage`)

**`POST /api/v1/organizations`** (`createOrganization`, `organization:manage`) → 201 `OrganizationResponse` + cabeçalho `Location`.

| Campo | Regras |
| --- | --- |
| `type` | obrigatório; valores do S1-01 |
| `legalName` | obrigatório, 2–200 |
| `tradeName` | opcional, ≤ 120 |
| `nuit` | obrigatório, `Nuit`; único → 409 `NUIT_ALREADY_IN_USE` |
| `licenseNumber` | ≤ 40; obrigatório para `INSURER`, `BROKER`, `AGENT` → 400 `LICENSE_NUMBER_REQUIRED` |
| `contactEmail` | obrigatório, e-mail |
| `contactPhone` | opcional, `^\+?[0-9]{9,15}$` sem espaços |
| `address` | opcional, ≤ 300 |
| `province` | opcional, código `Province` |
| `insurerProfile` | obrigatório se `type = INSURER`; proibido nos outros (`VALIDATION_ERROR`, campo `insurerProfile`, código `NOT_ALLOWED`). Campos: `shortCode` (`^[A-Z0-9]{2,10}$`, único → 409 `SHORT_CODE_ALREADY_IN_USE`), `complaintsEmail` (obrigatório), `ombudsmanOrganizationId` (opcional; tem de existir e ser `OMBUDSMAN` → 400 `OMBUDSMAN_INVALID`) |

`OrganizationResponse`: `{ id, type, legalName, tradeName, displayName, nuit, licenseNumber, status, contactEmail, contactPhone, address, province, insurerProfile?, version, createdAt, updatedAt }`. `displayName = tradeName ?? legalName`.

**O primeiro gestor não vai neste pedido.** O ecrã de criação (S1-07) chama a seguir `POST /organizations/{id}/users` (secção 2) com o perfil de gestor. Assim o erro "e-mail já em uso" aparece no momento, e o módulo `organization` não depende de `identity`. Uma organização sem gestor é possível e o ecrã de detalhe avisa.

**`GET /api/v1/organizations`** (`listOrganizations`, `organization:read`) — filtros `type`, `status`, `q` (procura em `legal_name`, `trade_name` sem diferenciar maiúsculas, ou `nuit` exacto), paginação `AGENTS.md` §4, ordenação por `createdAt` ou `legalName` → página de `OrganizationSummaryResponse { id, type, displayName, nuit, status, createdAt }`.

**`GET /api/v1/organizations/{id}`** (`getOrganization`, `organization:read`) → `OrganizationResponse`; não existe → 404 `ORGANIZATION_NOT_FOUND`.

**`PUT /api/v1/organizations/{id}`** (`updateOrganization`, `organization:manage`) — os mesmos campos do POST excepto `type` (não muda), mais `version` → 200. `version` diferente → 409 `CONCURRENT_MODIFICATION`.

**`POST /api/v1/organizations/{id}/suspend`** (`suspendOrganization`) `{ "reason": "..." }` (obrigatório, ≤ 500) e **`POST /api/v1/organizations/{id}/reactivate`** (`reactivateOrganization`) → 200 `OrganizationResponse`. Transição inválida → 409 `INVALID_STATE_TRANSITION`. Publicam `OrganizationSuspended(organizationId, reason)` e `OrganizationReactivated(organizationId)`.

- `identity.OrganizationEventsListener` (`@ApplicationModuleListener`, `@RunAsSystem`) recebe `OrganizationSuspended` e revoga todas as sessões dos utilizadores dessa organização (`ORG_SUSPENDED`). A dependência continua `identity → organization`.
- Auditoria: `ORGANIZATION.CREATE`, `ORGANIZATION.UPDATE`, `ORGANIZATION.SUSPEND`, `ORGANIZATION.REACTIVATE` com antes e depois.

### 2. Convites (módulo `identity`, tag `Identity`)

**Âmbito de quem convida:**
- staff da plataforma: `POST /api/v1/admin/users` (`invitePlatformUser`) — exige `org-user:manage` **e** âmbito `PLATFORM`, senão 403 `FORBIDDEN`;
- staff de uma organização: `POST /api/v1/organizations/{orgId}/users` (`inviteOrganizationUser`) — exige `org-user:manage`. Âmbito `PLATFORM` pode convidar para qualquer organização; âmbito `ORG` só para a sua (outra → 404 `ORGANIZATION_NOT_FOUND`). Organização `SUSPENDED` → 409 `ORGANIZATION_NOT_ACTIVE`.

Pedido `{ fullName (2–120), email, roleCodes (1+) }` → 201 `InvitationResponse { id, email, fullName, organizationId, roleCodes, status, expiresAt, createdAt }`, onde `status` é calculado: `REVOKED` se `revoked_at`; `ACCEPTED` se `accepted_at` (preenchido só na activação); `EXPIRED` se `expires_at` passou; senão `PENDING`.

Regras:
- Cada perfil tem de ser permitido no tipo da organização (`role.org_types` contém o tipo; para a plataforma, só perfis com `org_types = null`, excepto `CUSTOMER`) → 400 `ROLE_NOT_ALLOWED_FOR_ORGANIZATION`.
- E-mail já usado por uma conta de staff:
  - conta `PENDING_ACTIVATION` da **mesma** organização (ou da plataforma, num convite da plataforma) → o convite novo liga-se a essa conta (`invitation.user_id`) e a activação actualiza-a;
  - qualquer outra conta de staff, de qualquer organização → 409 `EMAIL_ALREADY_IN_USE`.
- Convites pendentes para o mesmo e-mail, em qualquer organização → são revogados e substituídos por este.
- **Estas duas verificações têm de ver todas as organizações**, e o âmbito `ORG` só vê a sua. Ficam num bean próprio, `identity.application.IdentitySystemLookups`, com métodos `@RunAsSystem` (S1-01), por exemplo `findStaffByEmail(email)` e `revokePendingInvitations(email)`. O resto do convite corre no âmbito de quem convida.
- Token: 32 bytes aleatórios, Base64 URL; grava-se o SHA-256. Validade 7 dias.
- Envia o e-mail com o link `{moseguros.web.base-url}/convite/{token}` (`moseguros.web.base-url`: `http://localhost:5173` em `local`, `http://localhost:3000` no compose).
- Auditoria `USER.INVITE`.

**Dois conceitos diferentes, com nomes diferentes:**

- `managerRoles` — os perfis que **fazem de alguém gestor**: `INSURER_ADMIN` numa seguradora; `ORG_ADMIN` nas outras organizações; `PLATFORM_ADMIN` na plataforma. Usado pela regra `LAST_MANAGER` (S1-05) e pelo aviso "sem gestor" (S1-08).
- `managerInviteRoles` — os perfis a **dar ao primeiro gestor** no ecrã de criação de organização: `INSURER` → `INSURER_ADMIN`; outros tipos → `ORG_ADMIN` mais o perfil operacional do tipo (`BROKER` → `BROKER`, `AGENT` → `AGENT`, `WORKSHOP` → `WORKSHOP`, `ASSESSOR` → `ASSESSOR`, `ASSISTANCE` → `ASSISTANCE_PROVIDER`, `OMBUDSMAN` → `OMBUDSMAN`, `REGULATOR` → `REGULATOR_VIEWER`, `POLICE` → `POLICE_OFFICER`, `CORPORATE_CLIENT` → `FLEET_MANAGER`). O backend expõe-no em `GET /roles` (abaixo) para o ecrã não o duplicar.

**`GET /api/v1/roles?organizationId={id}`** ou **`?scope=PLATFORM`** (`listAssignableRoles`, `org-user:read`) → `{ "roles": ["INSURER_ADMIN", …], "managerRoles": ["INSURER_ADMIN"], "managerInviteRoles": ["INSURER_ADMIN"] }`, com as mesmas regras de âmbito acima.

**`GET /api/v1/organizations/{orgId}/invitations`** (`listOrganizationInvitations`) e **`GET /api/v1/admin/invitations`** (`listPlatformInvitations`), `org-user:read`, filtro `status` → página de `InvitationResponse`.

**`POST /api/v1/invitations/{id}/resend`** (`resendInvitation`, `org-user:manage`) → 200: gera token novo (o anterior deixa de funcionar), validade nova de 7 dias, envia de novo. Só `PENDING` ou `EXPIRED`, senão 409 `INVALID_STATE_TRANSITION`.

**`POST /api/v1/invitations/{id}/revoke`** (`revokeInvitation`, `org-user:manage`) → 204. Só `PENDING` ou `EXPIRED`.

### 3. Activação pelo convidado (públicos, `@RunAsSystem`)

**`GET /api/v1/auth/invitations/{token}`** (`getInvitationByToken`) → 200 `{ email, fullName, organization: { displayName, type } | null, expiresAt }`. Token desconhecido, expirado, revogado ou já aceite → 404 `INVITATION_INVALID`.

**`POST /api/v1/auth/invitations/{token}/accept`** (`acceptInvitation`) `{ "password": "..." }` → 200 `{ totpSecret, otpauthUri }`.

- Aplica a política de palavras-passe (secção 4).
- `invitation.user_id` vazio → cria `user_account` `STAFF`, `PENDING_ACTIVATION`, `display_name = fullName`, `organization_id` do convite, `email_verified = false`, e grava o seu id em `invitation.user_id`.
- `invitation.user_id` preenchido (conta pendente reutilizada, ou reposição de acesso do S1-05) → actualiza essa conta.
- Grava `password_hash` (Argon2id: `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`) e um segredo TOTP novo cifrado (20 bytes aleatórios, Base32).
- `otpauthUri = otpauth://totp/MoSeguros:{email}?secret={secret}&issuer=MoSeguros&algorithm=SHA1&digits=6&period=30`.
- Pode ser chamado de novo até à activação: cada chamada substitui a palavra-passe e o segredo.

**`POST /api/v1/auth/invitations/{token}/activate`** (`activateInvitation`) `{ "totpCode": "123456" }` → 200 `TokenResponse`.

- `invitation.user_id` vazio, ou a conta ligada sem `password_hash` → 400 `INVITATION_NOT_ACCEPTED`.
- Código TOTP verificado com o `TotpService`: SHA-1, 6 dígitos, 30 s, aceita o passo anterior e o seguinte. Errado → `invitation.activation_attempts + 1` (gravado mesmo com a resposta de erro) e 400 `TOTP_INVALID`. Ao chegar a 5 o convite é revogado e a resposta passa a 404 `INVITATION_INVALID`.
- Certo → `status = ACTIVE`, `email_verified = true`, `last_totp_step`, perfis substituídos pelos do convite, `invitation.accepted_at`, auditoria `USER.ACTIVATE`, tokens de staff emitidos (S1-02).

### 4. Política de palavras-passe (`PasswordPolicy`)

Falha → 400 `PASSWORD_TOO_WEAK` com `errors[]` no campo `password` (ou `newPassword` no S1-05):

| Regra | `errors[].code` |
| --- | --- |
| menos de 12 caracteres | `TOO_SHORT` |
| mais de 128 caracteres | `TOO_LONG` |
| contém a parte local do e-mail (se tiver ≥ 4 caracteres), sem diferenciar maiúsculas | `CONTAINS_EMAIL` |
| está em `common-passwords.txt`, sem diferenciar maiúsculas | `TOO_COMMON` |

`common-passwords.txt`: as 10 000 palavras-passe mais comuns da lista pública *SecLists* (`Passwords/Common-Credentials/10k-most-common.txt`, licença MIT), uma por linha, com a origem e a licença num comentário no início.

### 5. Primeiro administrador da plataforma

- `PlatformAdminBootstrap` (`ApplicationRunner`, `@RunAsSystem`).
- Se `moseguros.bootstrap.platform-admin-email` estiver definido, não houver nenhuma conta `ACTIVE` com `PLATFORM_ADMIN` e não houver convite `PENDING` da plataforma para esse e-mail, cria um convite (`organization_id = null`, perfis `{PLATFORM_ADMIN}`, nome de `moseguros.bootstrap.platform-admin-name`, por defeito "Administrador") e envia o e-mail.
- Regista `INFO` com o e-mail mascarado; **nunca** o link nem o token.
- Compose: `MOSEGUROS_BOOTSTRAP_PLATFORM_ADMIN_EMAIL=admin@moseguros.local`. O e-mail aparece no Mailpit (`http://localhost:8025`).

### 6. E-mail do convite

`NotificationApi.sendEmail(String to, String templateKey, Object[] args, String language, String purpose, UUID correlationId) → DeliveryResult`, que regista em `outbound_message` (`purpose = INVITATION`) como no S1-03.

- `invitation.email.subject=Convite para a MoSeguros`
- `invitation.email.body=Olá {0},\n\nFoi convidado para usar a MoSeguros{1}. Para activar a sua conta, abra o link abaixo nos próximos 7 dias:\n\n{2}\n\nVai precisar de uma aplicação de autenticação no telemóvel (por exemplo, Google Authenticator ou Microsoft Authenticator).\n\nSe não esperava este convite, ignore esta mensagem.`
  - `{1}` = ` como membro de {organização}` ou vazio na plataforma.
- Versão `en` equivalente.
