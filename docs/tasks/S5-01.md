## Contexto

RF-04, RF-17 e RF-23 (parte de configuração). Cada seguradora configura os seus próprios dados para cada forma de pagamento (M-Pesa, e-Mola, cartão, entidade e referência); o dinheiro vai sempre directamente para a conta da seguradora (`AGENTS.md` §9 regra 10). Os segredos (chaves M-Pesa, credenciais SFTP, chaves do cartão) ficam só no cofre de segredos; a BD guarda a referência (`AGENTS.md` §6; modelo transversal §7, "Cofre de segredos"). É a primeira tarefa de backend do sprint: cria também a migração com **todas** as permissões do Sprint 5.

**Pressupõe:**
- S1: `identity.role_permission` e os perfis `INSURER_ADMIN`, `FINANCE`, `BROKER`, `AGENT`, `CUSTOMER`, `PLATFORM_ADMIN`; `TenantContext` com `Scope.ORG` e `app.insurer_id`; `@RunAsSystem` e o `RunAsSystemUsageTest`; `AuditService`; `ErrorCodes`/`FieldErrorCodes`; `CONCURRENT_MODIFICATION`, `INVALID_STATE_TRANSITION`.
- S1-04: `OrganizationApi.findSummary(UUID) → Optional<OrganizationSummary(id, type, status, displayName)>`.
- S2: os dados de demonstração `R__dev_seed_s2.sql` criam a seguradora "Seguradora Demo" (`insurer_profile.short_code = 'DEMO'`).
- Esta tarefa **não** precisa de nada do S4; depende dele só porque o modelo transversal manda começar o S5 com o S4 no `main`.

## Objectivo

O gestor ou o financeiro de uma seguradora vê as quatro formas de pagamento, preenche os dados de cada uma (os segredos são enviados uma vez e nunca mais devolvidos), testa a ligação e activa ou desactiva cada forma; outra seguradora nunca vê estes dados.

### 2. Cofre de segredos (`shared.secrets`)

```java
public interface SecretStore {
  void put(String path, String value);       // cria ou substitui
  Optional<String> get(String path);
  void delete(String path);
  boolean exists(String path);
}
public record SecretRef(String path) {}       // ex.: "secret/insurers/<uuid>/payments/MPESA/apiKey"
```

- **Caminhos:** `secret/insurers/{insurerId}/payments/{METHOD}/{campo}`, com `METHOD` em maiúsculas (`MPESA`, `EMOLA`, `CARD`, `BANK_REFERENCE`) e `campo` como na tabela da secção 4 (ex.: `sftp.password`). O primeiro segmento (`secret`) é o *mount* KV v2.
- **`VaultSecretStore`**: `VaultTemplate` + `VaultKeyValueOperations` em modo KV v2 (`KeyValueBackend.KV_2`). Cada segredo é guardado em `<mount>/data/<resto do caminho>` com os dados `{ "value": "<valor>" }`. `delete` apaga os metadados (todas as versões).
- **`InMemorySecretStore`**: `ConcurrentHashMap`; só nos perfis `test` e quando `moseguros.secrets.store=in-memory`.
- Configuração:

```yaml
moseguros:
  secrets:
    store: ${MOSEGUROS_SECRETS_STORE:vault}     # vault | in-memory
    vault:
      uri: ${VAULT_URI:http://localhost:8200}
      token: ${VAULT_TOKEN:}
      mount: secret
```

  - `application-test.yml`: `store: in-memory`. `application-local.yml`: `store: vault`, `token: dev-root-token` (comentário `# token só para o Vault em modo dev`).
  - Fora dos perfis `local` e `test`, `in-memory` ou `token` vazio → a aplicação **não arranca** (validação de `SecretStoreProperties`, mensagem clara). A autenticação no Vault de staging e produção (AppRole ou equivalente) decide-se com o alojamento (S6-08); nesta tarefa só há token.
- Vault indisponível → `DomainException` `SECRET_STORE_UNAVAILABLE` (503). Nunca se regista o valor do segredo nem o token; o caminho pode aparecer nos logs.
- Os valores dos segredos não passam por nenhum DTO de resposta, `toString()`, log ou auditoria. `InsurerPaymentMethod` não tem campos com valores secretos, só as referências.

### 4. Dados por método

`settings` é validado com o JSON Schema (draft 2020-12) `backend/src/main/resources/schemas/payment-method-{method em minúsculas}.json`. Os schemas têm `"additionalProperties": false` e um `default` em cada campo que o tenha. Os segredos **não** estão no schema: são campos à parte (`secrets`), definidos no enum `SecretField`.

| Método | `settings` (tipo e regra) | Segredos (`SecretField`) |
| --- | --- | --- |
| `MPESA` | `serviceProviderCode` string `^[0-9]{5,10}$` (obrigatório); `host` string `^https?://[A-Za-z0-9.-]+$`, sem porta nem caminho (obrigatório; ex.: `https://api.sandbox.vm.co.mz`, `https://api.vm.co.mz`, `http://mpesa-mock`); `ports` objecto `{ c2b, query, reversal }` inteiros 1–65535 (defeito 18352, 18353, 18354); `origin` string 1–100 (obrigatório; ex.: `developer.mpesa.vm.co.mz`); `initiatorIdentifier` string ≤ 60 (opcional; só reversões, S7); `c2bTimeoutSeconds` inteiro 30–180 (defeito 90) | `apiKey` (obrigatório), `publicKey` (obrigatório; Base64 DER ou PEM de uma chave RSA pública — inválida → campo `secrets.publicKey`, código `INVALID_PUBLIC_KEY`), `securityCredential` (opcional; reversões, S7) |
| `EMOLA` | `merchantCode` string 1–40 (obrigatório); `baseUrl` string `^https?://` (obrigatório); `timeoutSeconds` inteiro 10–120 (defeito 60). Campos **provisórios** até haver documentação da Movitel (ver "Questões") | `merchantSecret` (obrigatório) |
| `CARD` | `provider` string enum `["MOCK"]` (obrigatório; o adquirente real acrescenta-se com a documentação); `merchantId` string 1–40; `terminalId` string 1–40 (opcional); `checkoutBaseUrl` string `^https?://` (obrigatório); `currency` const `"MZN"` | `secretKey` (obrigatório), `callbackSigningKey` (obrigatório) |
| `BANK_REFERENCE` | `entity` string `^[0-9]{3,10}$` (obrigatório; formato provisório até ao S5-13); `referenceAlgorithm` string enum `["MOCK_SIMO_V1"]` (o S5-13 acrescenta o real); `referenceValidityHours` inteiro 1–720 (defeito 72); `sftp` objecto com `host` (obrigatório), `port` 1–65535 (defeito 22), `username` 1–64 (obrigatório), `authType` enum `PASSWORD`/`KEY` (obrigatório), `inboundDir`, `processedDir`, `errorDir` (obrigatórios, começam por `/` ou são relativos sem `..`), `filePattern` glob 1–100 (defeito `*`), `hostKeyFingerprint` string `^SHA256:[A-Za-z0-9+/]{43}=?$` (impressão digital da chave do servidor SFTP; obrigatória para activar fora dos perfis `local` e `test`, S5-09); `pollCron` string (obrigatório); `fileFormat` string enum `["MOCK_SIMO_V1"]` (o S5-14 acrescenta o real); `timezone` string IANA (defeito `Africa/Maputo`) | `sftp.password` (obrigatório se `authType = PASSWORD`), `sftp.privateKey` (obrigatório se `KEY`; PEM OpenSSH ou PKCS#8), `sftp.passphrase` (opcional, só com `KEY`) |

Regras que o JSON Schema não cobre (em `SettingsValidator`, erros de campo):

| Regra | `errors[].field` | `errors[].code` |
| --- | --- | --- |
| `pollCron` não é uma expressão cron de 6 campos do Spring (`CronExpression.parse`) | `settings.pollCron` | `INVALID_CRON` |
| as 10 execuções seguintes de `pollCron` têm algum intervalo < 5 min ou > 24 h | `settings.pollCron` | `CRON_FREQUENCY_OUT_OF_RANGE` |
| `timezone` não existe (`ZoneId.of`) | `settings.timezone` | `INVALID_TIMEZONE` |
| `inboundDir`, `processedDir` e `errorDir` não são todos diferentes | `settings.sftp.processedDir` (ou `errorDir`) | `DIRECTORY_CONFLICT` |
| `fileFormat` ou `referenceAlgorithm` que comece por `MOCK_` com o perfil `prod` (nos perfis `local`, `test` e `staging` é aceite; S5-07 §3) | `settings.fileFormat` / `settings.referenceAlgorithm` | `NOT_ALLOWED` |
| `minAmount > maxAmount` | `maxAmount` | `MIN_GREATER_THAN_MAX` |
| `enable` de `BANK_REFERENCE` sem `sftp.hostKeyFingerprint` fora dos perfis `local` e `test` | `settings.sftp.hostKeyFingerprint` | `REQUIRED` |

- Erro do JSON Schema → `errors[]` com `field = "settings." + caminho` (ex.: `settings.sftp.port`) e código: `REQUIRED` (campo em falta), `INVALID_FORMAT` (`pattern`, `format`, `enum`, `const`, tipo errado), `OUT_OF_RANGE` (`minimum`, `maximum`, `minLength`, `maxLength`), `NOT_ALLOWED` (`additionalProperties`).
- Os campos obrigatórios do schema só se exigem ao **activar** (secção 5, `enable`). Ao gravar (`PUT`) valida-se o que vier, para a seguradora poder gravar a meio.

### 5. Endpoints (módulo `payment`, tag `Payment`, âmbito `ORG` de uma seguradora)

Todos exigem `@PreAuthorize("hasAuthority('payment:configure')")` e `TenantContext` com `insurerId`; staff de organização que não é seguradora → 403 `FORBIDDEN`. A seguradora é sempre a do token (nunca vem no pedido).

**`GET /api/v1/insurer/payment-methods`** (`listInsurerPaymentMethods`) → 200, sempre com os quatro métodos pela ordem `MPESA`, `EMOLA`, `CARD`, `BANK_REFERENCE` (os que ainda não têm linha aparecem com `configured: false` e os valores por defeito):

```json
{
  "methods": [
    {
      "method": "MPESA",
      "configured": true,
      "enabled": false,
      "environment": "SANDBOX",
      "displayName": "M-Pesa Seguradora Demo",
      "settings": { "serviceProviderCode": "171717", "host": "http://mpesa-mock", "ports": { "c2b": 18352, "query": 18353, "reversal": 18354 }, "origin": "developer.mpesa.vm.co.mz", "c2bTimeoutSeconds": 90 },
      "settingsSchema": { "$schema": "https://json-schema.org/draft/2020-12/schema", "type": "object", "properties": { } },
      "secrets": {
        "apiKey": { "configured": true, "required": true, "updatedAt": "2027-01-15T08:00:00Z" },
        "publicKey": { "configured": true, "required": true, "updatedAt": "2027-01-15T08:00:00Z" },
        "securityCredential": { "configured": false, "required": false, "updatedAt": null }
      },
      "minAmount": { "amount": 100, "currency": "MZN" },
      "maxAmount": null,
      "intentValidityMinutes": 30,
      "sortOrder": 1,
      "lastTest": { "at": "2027-01-15T08:05:00Z", "result": "OK", "message": null },
      "lastError": null,
      "version": 3,
      "updatedAt": "2027-01-15T08:05:00Z"
    }
  ]
}
```

- `secrets.<campo>.required` segue a tabela da secção 4 (para `BANK_REFERENCE` depende de `settings.sftp.authType`).
- `updatedAt` de cada segredo: guardado em `secret_refs` como `{ "apiKey": { "path": "secret/…", "updatedAt": "…" } }`.
- `settingsSchema` é o conteúdo do ficheiro JSON do método (a web gera o formulário a partir dele, S5-12).

**`PUT /api/v1/insurer/payment-methods/{method}`** (`updateInsurerPaymentMethod`) → 200 com o item do método (mesmo formato da lista). Cria a linha se não existir (`enabled = false`).

| Campo | Obrigatório | Regras |
| --- | --- | --- |
| `environment` | sim | `SANDBOX` ou `PRODUCTION` |
| `displayName` | não | ≤ 60 |
| `settings` | sim | objecto; secção 4 |
| `secrets` | não | mapa `campo → valor`; só os campos de `SecretField` do método (outro → `secrets.<campo>` `NOT_ALLOWED`); valor vazio → `REQUIRED`; ≤ 8 000 caracteres (`OUT_OF_RANGE`). Campo ausente mantém o segredo actual; campo presente substitui-o |
| `minAmount`, `maxAmount` | não | `Money`; `amount > 0` |
| `intentValidityMinutes` | sim | 5–1440 |
| `sortOrder` | sim | 0–99 |
| `version` | sim na actualização, ausente na criação | diferente da gravada → 409 `CONCURRENT_MODIFICATION` |

- Ordem: validar tudo → gravar os segredos novos no cofre (`SecretStore.put`) → gravar a linha com as referências. Se o cofre falhar, nada é gravado na BD (503 `SECRET_STORE_UNAVAILABLE`).
- Se `BANK_REFERENCE` mudar `authType`, o segredo que deixa de se aplicar é apagado do cofre e de `secret_refs`.
- Mudar `settings` ou segredos de um método **activo** é permitido; a mudança vale no pedido seguinte (sem cache) e, para o worker, na leitura seguinte das fontes (S5-09).
- Auditoria `PAYMENT_METHOD.UPDATE` (`entityType = "InsurerPaymentMethod"`), antes e depois com `settings`, limites, `environment` e, para os segredos, só `{ "apiKey": "configured" }` / `"changed"`.

**`POST /api/v1/insurer/payment-methods/{method}/enable`** (`enableInsurerPaymentMethod`) e **`…/disable`** (`disableInsurerPaymentMethod`) `{ "version": 3 }` → 200 com o item.

- `enable`:
  - sem linha → 404 `PAYMENT_METHOD_NOT_FOUND`;
  - já activo → 409 `INVALID_STATE_TRANSITION`;
  - `settings` não cumpre o schema completo (com os obrigatórios) ou falta um segredo obrigatório → 409 `PAYMENT_METHOD_INCOMPLETE` com `errors[]` (mesmos campos e códigos da secção 4; segredo em falta → `secrets.<campo>` `REQUIRED`);
  - `BANK_REFERENCE` com o perfil `prod` e sem `ReferenceGenerator` real → 409 `BANK_REFERENCE_NOT_AVAILABLE` (regra do S5-07 §3; até o S5-02 e o S5-07 existirem, o `enable` de `BANK_REFERENCE` com o perfil `prod` dá sempre este erro);
  - sucesso → `enabled = true`, `enabled_at = agora`, auditoria `PAYMENT_METHOD.ENABLE`.
- `disable`: já inactivo → 409 `INVALID_STATE_TRANSITION`; sucesso → `enabled = false`, auditoria `PAYMENT_METHOD.DISABLE`. Intenções já criadas continuam o seu curso (S5-02).

**`POST /api/v1/insurer/payment-methods/{method}/test`** (`testInsurerPaymentMethod`) → 200 `{ "result": "OK" | "FAILED" | "NOT_SUPPORTED", "message": "API_KEY_REJECTED" | null, "testedAt": "…" }`.

- Usa os dados **gravados** (grave antes de testar).
- Delega no bean `PaymentMethodTester` com `method()` igual ao pedido:

```java
public interface PaymentMethodTester {
  PaymentMethod method();
  TestResult test(UUID insurerId, JsonNode settings, Function<String, Optional<String>> secret); // secret(campo) lê do cofre
}
```

- Sem tester para o método → `NOT_SUPPORTED`. Testers: `BANK_REFERENCE` nesta tarefa (abaixo); `MPESA` no S5-04; `EMOLA` e `CARD` no S5-05.
- **`BankReferenceConfigTester`**: valida `settings` com o schema completo e confirma que os segredos SFTP obrigatórios existem no cofre (`SecretStore.exists`). **Não liga ao SFTP**: as credenciais SFTP só são usadas pelo `payment-file-worker` (ADR-004). A ligação real aparece como "Última leitura" (S5-10, S5-12). `message`: `CONFIG_VALID`, ou o primeiro problema (`SETTINGS_INVALID`, `SECRET_MISSING`).
- Grava `last_test_at`, `last_test_result`, `last_test_message`; auditoria `PAYMENT_METHOD.TEST` (só o resultado).
- Timeout total do teste: 15 s (o tester respeita-o; ultrapassado → `FAILED`, `TIMEOUT`).

### 7. `PaymentSystemLookups` (`payment.application`, `@RunAsSystem`)

- `Optional<MethodConfig> enabledConfig(UUID insurerId, PaymentMethod method)` — filtra **sempre** por `insurerId` no próprio SQL;
