## Contexto

RF-01 (parcial), ADR-003. O cliente entra com telemóvel ou e-mail e um código enviado por SMS, WhatsApp ou e-mail, conforme a configuração que o administrador da plataforma define em `identity.otp_settings`. Os canais de envio ficam no módulo `notification`, porque no Sprint 6 as notificações reutilizam-nos.

## Objectivo

Um cliente pede um código, recebe-o pelo canal certo (com alternativa automática se o canal falhar), valida-o e recebe os tokens; o administrador muda os canais e a mudança vale no pedido seguinte, sem reiniciar.

## Especificação

### 1. Módulo `notification` (só o necessário para o OTP)

```java
// Channel é mz.co.moseguros.shared.domain.Channel (S1-01): SMS, WHATSAPP, EMAIL
public enum DeliveryStatus { PENDING, SENT, DELIVERED, FAILED }
public record DeliveryResult(UUID messageId, DeliveryStatus status, String failureReason) {}
public record OtpDeliveryFailed(UUID messageId, UUID correlationId, Channel channel) {}  // evento

public class NotificationApi {
  // envia já, de forma síncrona (timeout 5 s); nunca lança por falha do fornecedor: devolve FAILED
  public DeliveryResult sendOtp(Channel channel, String destination, String code,
                                int validityMinutes, String language, UUID correlationId);
}
```

- **Âmbito:** os métodos do `NotificationApi` delegam em serviços de `notification.application` anotados com `@RunAsSystem` (S1-01), porque `outbound_message` só é visível em `SYSTEM`. Podem ser chamados de qualquer âmbito, dentro ou fora de uma transacção.
- `OtpDeliveryChannel` (interface, uma implementação por canal): `Channel channel(); ProviderResult send(String destination, String text, Map<String,String> templateParams)`.
- Implementações nesta tarefa:
  - `MockSmsSender` → `POST {moseguros.notification.sms.mock-url}/sms` `{to, text}`;
  - `MockWhatsAppSender` → `POST {moseguros.notification.whatsapp.mock-url}/whatsapp` `{to, template: "moseguros_otp", params: {code}}`;
  - `EmailSender` → SMTP com `JavaMailSender` (`spring-boot-starter-mail`), texto simples.
- Escolha da implementação por propriedade `moseguros.notification.sms.provider: mock` (idem `whatsapp`). Os fornecedores reais de SMS e WhatsApp **não** fazem parte desta tarefa (ver "Questões").
- Erro HTTP, timeout ou excepção do fornecedor → `FAILED` com `failureReason` curto (sem dados pessoais).
- **Textos** (`notifications_pt.properties`):
  - `otp.sms=MoSeguros: o seu código é {0}. Válido por {1} min. Não o partilhe com ninguém.`
  - `otp.email.subject=O seu código MoSeguros`
  - `otp.email.body=Olá,\n\no seu código de acesso à MoSeguros é {0}. É válido durante {1} minutos.\n\nSe não pediu este código, ignore esta mensagem.`
  - WhatsApp usa o modelo aprovado `moseguros_otp` com o parâmetro `code`.
  - Versões `en` equivalentes.
- **`notification.outbound_message`** (colunas obrigatórias + as abaixo; RLS `s = 'SYSTEM'`; `grant usage on schema notification` e `select, insert, update` ao `moseguros_app`):

| Coluna | Tipo | Regras |
| --- | --- | --- |
| `channel` | `varchar(10) not null` | `SMS`, `WHATSAPP`, `EMAIL` |
| `purpose` | `varchar(30) not null` | `OTP` nesta tarefa |
| `destination_masked` | `varchar(254) not null` | `+258*****4567` ou `a***@exemplo.co.mz` |
| `destination_hash` | `varchar(64) not null` | SHA-256 do destino normalizado (para pesquisa sem guardar em claro) |
| `correlation_id` | `uuid null` | id do `otp_challenge` |
| `provider` | `varchar(30) not null` | `mock-sms`, `mock-whatsapp`, `smtp` |
| `provider_message_id` | `varchar(100) null` | |
| `status` | `varchar(12) not null` | `PENDING`, `SENT`, `DELIVERED`, `FAILED` |
| `failure_reason` | `varchar(200) null` | |
| `sent_at`, `delivered_at` | `timestamptz null` | |

  Nunca se grava o texto nem o código.
- **Recibos de entrega**: `POST /api/v1/integrations/delivery-receipts/{provider}`, onde `{provider}` é o valor da coluna `provider` (`mock-sms`, `mock-whatsapp`; valor desconhecido → 404 `NOT_FOUND`), (`operationId: receiveDeliveryReceipt`, tag `Notification`), público no `SecurityConfig` mas exige o cabeçalho `X-Webhook-Secret` igual a `moseguros.notification.webhook-secret` (comparação em tempo constante; errado → 401 `UNAUTHORIZED`). Corpo `{ "providerMessageId": "...", "status": "DELIVERED" | "FAILED", "reason": "..." }` → 204. Mensagem desconhecida (nenhuma linha com esse `provider` e `provider_message_id`) → 204 (ignora). O `provider_message_id` é o `id` devolvido pelo fornecedor no envio. Actualiza `outbound_message`; se `FAILED` e `purpose = OTP`, publica `OtpDeliveryFailed`.

### 2. Configuração do OTP (administração)

- **`GET /api/v1/admin/otp-settings`** (`getOtpSettings`, `otp-settings:read`) → `OtpSettingsResponse { enabledChannels, defaultChannel, customerCanChoose, fallbackOrder, codeLength, validitySeconds, maxAttempts, resendAfterSeconds, maxRequestsPerHour, version, updatedAt, updatedBy }`.
- **`PUT /api/v1/admin/otp-settings`** (`updateOtpSettings`, `otp-settings:manage`) com os mesmos campos editáveis mais `version`, todos obrigatórios → 200 `OtpSettingsResponse`. Validação → 400 `VALIDATION_ERROR` com `errors[]`:

| Regra | `errors[].field` | `errors[].code` |
| --- | --- | --- |
| `enabledChannels` vazio ou com repetidos | `enabledChannels` | `CHANNELS_EMPTY` / `CHANNELS_DUPLICATED` |
| `defaultChannel` fora de `enabledChannels` | `defaultChannel` | `DEFAULT_CHANNEL_NOT_ENABLED` |
| `fallbackOrder` não tem exactamente os mesmos canais de `enabledChannels` | `fallbackOrder` | `FALLBACK_ORDER_MISMATCH` |
| números fora dos limites do S1-01 | o campo | `OUT_OF_RANGE` |

  Grava auditoria `OTP_SETTINGS.UPDATE` com estado antes e depois. Concorrência: se `version` do pedido for diferente da gravada (alguém alterou entretanto) → 409 `CONCURRENT_MODIFICATION`.
- **`POST /api/v1/admin/otp-settings/test`** (`testOtpDelivery`, `otp-settings:manage`) `{ identifier, identifierType, channel }` → 200 `{ channel, deliveryStatus, messageId }`. Corre em `SYSTEM` (`OtpService.sendTest` com `@RunAsSystem`); a permissão é verificada antes pelo `@PreAuthorize`. Cria um desafio `purpose = TEST` (não serve para login), envia só pelo canal pedido (sem alternativa), mesmo que esse canal esteja desactivado (para o admin testar antes de activar). Canal incompatível com o identificador → 400 `OTP_CHANNEL_NOT_AVAILABLE`. Conta para o limite por hora.
- As configurações são lidas da BD em cada pedido (sem cache), por isso uma mudança vale logo no pedido seguinte.

### 3. Fluxo do cliente (endpoints públicos, tag `Identity`)

**`GET /api/v1/auth/otp/options`** (`getOtpOptions`) → 200:

```json
{
  "identifierTypes": ["MSISDN", "EMAIL"],
  "channels": { "MSISDN": ["SMS", "WHATSAPP"], "EMAIL": ["EMAIL"] },
  "defaultChannels": { "MSISDN": "SMS", "EMAIL": "EMAIL" },
  "customerCanChoose": true,
  "codeLength": 6,
  "resendAfterSeconds": 60
}
```

- `channels[tipo]`: canais activos compatíveis (`MSISDN` → `SMS`, `WHATSAPP`; `EMAIL` → `EMAIL`), pela ordem de `fallbackOrder`. Um tipo sem canais não aparece em `identifierTypes` nem nos mapas.
- `defaultChannels[tipo]`: `default_channel` se for compatível com o tipo; senão o primeiro de `channels[tipo]`.

**`POST /api/v1/auth/otp/request`** (`requestOtp`) `{ "identifier": "841234567", "identifierType": "MSISDN", "channel": "WHATSAPP" }` (`channel` opcional) → 202 `{ challengeId, channel, resendAfterSeconds, expiresAt, fallbackUsed }`.

Passos, por ordem:

1. Normalizar o identificador (`Msisdn` ou `Emails`). Inválido → 400 `VALIDATION_ERROR` com `errors[0] = { field: "identifier", code: "INVALID_MSISDN" | "INVALID_EMAIL" }`.
2. Escolher o canal:
   - se veio `channel` e `customer_can_choose = false` → 400 `OTP_CHANNEL_CHOICE_DISABLED`;
   - se veio `channel` e não está em `channels[tipo]` → 400 `OTP_CHANNEL_NOT_AVAILABLE`;
   - se não veio, `defaultChannels[tipo]`; se o tipo não tiver canais → 400 `OTP_CHANNEL_NOT_AVAILABLE` (o ecrã pede o outro tipo de identificador).
3. Limites (contam só desafios com `fallback_from_challenge_id is null`, `purpose in (LOGIN, TEST, VERIFY_CONTACT)`, pelo identificador):
   - mais de `max_requests_per_hour` na última hora → 429 `OTP_RATE_LIMITED`;
   - o último foi criado há menos de `resend_after_seconds` → 429 `OTP_RESEND_TOO_SOON`.
   - Ambos com a propriedade `retryAfterSeconds` no problema e o cabeçalho `Retry-After`.
4. Marcar como substituídos (`superseded_at`) os desafios anteriores não consumidos do mesmo identificador e finalidade (só o último código é válido).
5. Gerar o código: `code_length` dígitos com `SecureRandom` (pode começar por 0). Gravar o desafio (`expires_at = agora + validity_seconds`, `delivery_status = PENDING`, `root_challenge_id = id`).
6. Enviar com `NotificationApi.sendOtp(..., correlationId = challengeId)`.
   - Se o resultado for `FAILED`, criar um novo desafio no canal seguinte de `fallbackOrder` compatível com o tipo (código novo, `fallback_from_challenge_id` = anterior, mesmo `root_challenge_id`; o anterior fica `FAILED` e `superseded_at`), e tentar de novo. Repetir até um envio não falhar ou acabarem os canais compatíveis.
   - Nunca há alternativa de telemóvel para e-mail nem o contrário.
   - Sem nenhum canal com sucesso → 502 `OTP_DELIVERY_FAILED`.
7. Responder com o `challengeId` do **desafio raiz**, o `channel` efectivamente usado, `fallbackUsed = true` se mudou de canal.

- Não revela se já existe conta: a resposta é igual para identificadores novos e existentes.
- Perfil `local` (e só esse; `moseguros.security.otp.debug-header: true` só em `application-local.yml`, e o arranque falha se estiver ligado com o perfil `prod`): a resposta leva o cabeçalho `X-Debug-Otp` com o código.

**Alternativa por recibo de entrega**: `OtpFallbackListener` (`@ApplicationModuleListener` de `OtpDeliveryFailed`, `@RunAsSystem`): se o desafio correspondente ainda está activo (não consumido, não substituído, não expirado) e foi enviado há ≤ 30 s, faz o passo 6 a partir dele. Se passaram mais de 30 s, não faz nada.

**`GET /api/v1/auth/otp/challenges/{challengeId}`** (`getOtpChallenge`, público) — o ecrã consulta-o a cada 5 s durante 30 s, para saber se o canal mudou → 200 `{ channel, deliveryStatus, fallbackUsed, expiresAt }` do desafio activo da cadeia (pelo `root_challenge_id`). Desconhecido → 404 `OTP_CHALLENGE_NOT_FOUND`. Não devolve o identificador.

**`POST /api/v1/auth/otp/verify`** (`verifyOtp`) `{ "challengeId": "...", "code": "123456" }` → 200 `{ accessToken, refreshToken, expiresIn, isNewUser }`.

1. Encontrar o desafio activo da cadeia do `challengeId` (o mais recente com esse `root_challenge_id`), com `PESSIMISTIC_WRITE`. Não existe ou `purpose ≠ LOGIN` → 404 `OTP_CHALLENGE_NOT_FOUND`.
2. Já consumido → 400 `OTP_ALREADY_USED`; substituído por um pedido posterior → 400 `OTP_SUPERSEDED`; expirado → 400 `OTP_EXPIRED`; `attempts ≥ max_attempts` → 400 `OTP_ATTEMPTS_EXCEEDED`.
3. Comparar `HMAC-SHA256(pepper, challengeId + ":" + code)` com `code_hash` em tempo constante (`MessageDigest.isEqual`). `pepper` em `moseguros.security.otp.pepper` (variável `MOSEGUROS_OTP_PEPPER`; valor fixo de desenvolvimento em `local`/`test`; sem ele, fora desses perfis, não arranca).
4. Errado: `attempts + 1`, e responder 400 `OTP_INVALID` com a propriedade `attemptsRemaining`; se ficar a 0, a resposta é `OTP_ATTEMPTS_EXCEEDED`. **O incremento fica gravado mesmo com a resposta de erro** (transacção separada ou `noRollbackFor`).
5. Certo: `consumed_at = agora`. Procurar a conta `CUSTOMER` pelo identificador:
   - não existe → criar (`ACTIVE`, contacto verificado, `customer_profile` vazio, perfil `CUSTOMER`), `isNewUser = true`, auditoria `CUSTOMER.REGISTER`;
   - existe e `DISABLED` → 403 `ACCOUNT_DISABLED`;
   - existe → marcar o contacto como verificado se ainda não estava, `last_login_at = agora`.
6. Emitir tokens com o `TokenService` (S1-02); `device_info` do `User-Agent`.

Todo o fluxo corre com `@RunAsSystem`: os métodos públicos do `OtpService` (`request`, `verify`, `sendTest`, e os usados pelo S1-06) têm a anotação, e são chamados a partir dos controladores ou de outros beans (nunca da própria classe).

## Questões

- 01/11/2026 — Fornecedores reais: que agregador de SMS (e com que conta) e que conta do WhatsApp Business Platform se usam? Até haver resposta, ficam só os mocks; os adaptadores reais entram numa ficha própria quando o proprietário do produto indicar os fornecedores. **Não bloqueia esta tarefa.**
- 02/11/2026 — **Canal seguinte na alternativa:** interpretei "o canal seguinte de `fallbackOrder` compatível com o tipo" como o primeiro canal activo e compatível, pela ordem de `fallbackOrder`, que ainda não foi tentado na cadeia. Assim, um cliente que escolhe `WHATSAPP` (ordem `SMS, WHATSAPP, EMAIL`) e cujo envio falha recebe por `SMS`. E-mail e telemóvel nunca se misturam. Não bloqueia.
- 02/11/2026 — **Limites:** "mais de `max_requests_per_hour` na última hora" ficou como "o pedido número `max + 1` na última hora é recusado". O tempo de reenvio conta o último desafio raiz do identificador com finalidade `LOGIN`, `TEST` ou `VERIFY_CONTACT` (um teste do administrador também conta). O envio de teste só aplica o limite por hora, como diz a ficha. Não bloqueia.
- 02/11/2026 — **Recibos:** o segredo verifica-se antes do fornecedor (segredo errado e fornecedor desconhecido → 401). Os fornecedores conhecidos são os canais que aceitam recibos (`mock-sms`, `mock-whatsapp`); `smtp` → 404. `OtpDeliveryFailed` só se publica na passagem a `FAILED` (um recibo repetido não gera nova alternativa). Um recibo de falha depois dos 30 s, ou de um desafio já inactivo, não gera alternativa mas marca o desafio como `FAILED`. Um recibo `DELIVERED` só actualiza `outbound_message`: o `deliveryStatus` do desafio fica `SENT`, porque `notification` não pode chamar `identity`. Se o ecrã precisar de ver `DELIVERED`, acrescenta-se um evento numa ficha própria. Não bloqueia.
- 02/11/2026 — **Execução do `OtpFallbackListener`:** a aplicação não tem `@EnableAsync`, por isso o `@ApplicationModuleListener` corre logo depois do commit, na mesma thread do pedido do recibo: o 204 ao fornecedor só sai depois do reenvio (timeout de 5 s por canal). O evento fica no registo de publicações do Spring Modulith. Ligar `@EnableAsync` muda isto para toda a aplicação, por isso ficou para decisão. Não bloqueia.
- 02/11/2026 — **Pormenores decididos:** o `OtpDeliveryChannel` tem também `provider()` (vai para `outbound_message.provider`) e `acceptsDeliveryReceipts()`. O assunto do e-mail vai em `templateParams.subject`. Acrescentei `moseguros.notification.email.provider` (`smtp`) para os testes usarem canais falsos (`fake`) nos três canais. O idioma da mensagem é o `preferred_language` da conta, se existir; senão `pt`. O envio ao fornecedor fica fora de transacção no pedido; no recibo corre na transacção do listener. Um `PUT` sem alterações não incrementa a `version` (o Hibernate não vê alterações). Não bloqueia.
- 02/11/2026 — **Códigos de erro:** `CHANNELS_EMPTY`, `CHANNELS_DUPLICATED`, `DEFAULT_CHANNEL_NOT_ENABLED`, `FALLBACK_ORDER_MISMATCH` e `OUT_OF_RANGE` passaram para `FieldErrorCodes` (erros de campo, `FieldValidationException`). As traduções `errors.*` destes códigos ficaram na web e na app, onde não fazem mal. Acrescentei `NOT_NULL` (os campos numéricos e booleanos do `PUT /admin/otp-settings` são `@NotNull`) com as traduções `validation.NOT_NULL`. O `DomainException` passou a levar propriedades extra (`retryAfterSeconds` → também o cabeçalho `Retry-After`; `attemptsRemaining`), e o `GlobalExceptionHandler` converte `OptimisticLockingFailureException` em 409 `CONCURRENT_MODIFICATION`. Não bloqueia.
- 02/11/2026 — **`TokenServiceTest` (S1-02):** o teste validava os JWT com a hora real e um `NOW` fixo (02/11/2026 10:00 UTC), por isso começou a falhar às 10:15 de hoje. Corrigi-o para validar com o mesmo relógio fixo. Não bloqueia.
- 02/11/2026 — **Web e app:** nesta ficha só se regeneraram os clientes e se acrescentaram as traduções. Os ecrãs de login por código são do S1-07 (web) e do S1-09 (app). Não bloqueia.
