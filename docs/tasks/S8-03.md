## Contexto

História 4 do Sprint 8: o tomador participa o sinistro com fotos, documentos e (se houver) a declaração amigável, e recebe o número `SN-…`. Na submissão o sistema calcula o prazo de participação, faz a triagem, valida a cobertura à data do acidente e liga participações do mesmo acidente. Regras do plano (secção "Regras" do Sprint 8). ADR-002, ADR-006.

**Pressupõe:**

- S8-01: tabelas `claim.claim`, `claim.claim_party`, `claim.claim_document`, `claim.claim_event`; domínio `Claim` e transições; `ClaimTimelineService`; `ClaimNumbering`; `ClaimProperties`; eventos `ClaimReported`, `ClaimRejected`; permissão `self:claims`; códigos `CLAIM_NOT_FOUND`, `CLAIM_NOT_EDITABLE`, `CLAIM_DOCUMENT_LIMIT`, `CLAIM_PARTY_LIMIT`.
- S8-02: `claim.accident_statement`, `claim.statement_signature`, `both_signed`, `plates`.
- `PolicyApi.view(UUID) → PolicyView` (S6-01, secção 9; corre no âmbito de quem chama; inexistente ou invisível → `DomainException` `POLICY_NOT_FOUND`). Usa `id`, `number`, `insurerId`, `insurer.name`, `policyholderUserId`, `vehicle.plate`, `coverages`.
- `PolicyApi.coverAt(UUID policyId, Instant at) → CoverStatus` (S6-01, refinado no S7-01 para datas passadas; corre em `PolicySystemLookups`). **Coberto ⇔ `CoverStatus.COVERED`**; qualquer outro valor é "sem cobertura na data" e o nome do valor vai para `data.detail` do evento `COVER_CHECKED`. É o `policy` que decide o que é "activa e paga na data" (incluindo as prestações em atraso do S7-01); o `claim` não refaz essa regra.
- `OrganizationApi.findSummary(UUID)` (nome da seguradora).
- `DocumentApi.store(StoreFileCommand) → FileRef` (S2-01), com classificações `PERSONAL` e `SENSITIVE`.
- `NotificationApi.notify(...)`, `notification.template` (S6-04).

## Objectivo

O cliente cria um rascunho de sinistro sobre a sua apólice (também a partir da fila offline da app, sem duplicados), acrescenta fotos e documentos, e submete: recebe o número `SN-AAAA-NNNNNN`; o sinistro fica `REPORTED` com prioridade, prazo de tratamento e alerta de participação tardia; sem cobertura à data passa automaticamente a `REJECTED`; duas participações do mesmo acidente na mesma seguradora ficam ligadas.

```json
{
  "localUuid": "2d7c1f0e-8b4a-4c2e-9f61-7a0b3c5d9e21",
  "policyId": "0192f0c4-…",
  "type": "MATERIAL",

  "location": { "text": "Av. Eduardo Mondlane esq. Av. Vladimir Lenine, Maputo", "province": "MAPUTO_CITY", "lat": -25.969200, "lng": 32.573200, "accuracyM": 12 },
  "description": "Colisão lateral ao mudar de fila.",
  "policePresent": false,
  "policeReportNumber": null,
  "injuredCount": 0,
  "estimatedDamage": { "amount": 2500000, "currency": "MZN" },
  "accidentStatementId": "0193a1b2-…",
  "parties": [
    { "role": "THIRD_PARTY", "name": "Carlos Nhantumbo", "msisdn": "+258847654321", "plate": "MPM-45-67", "insurerName": "Outra Seguradora", "policyNumber": "AP-2027-000981" },
    { "role": "WITNESS", "name": "João Cossa", "msisdn": "+258821112233" }
  ]

```

| Campo | Obrigatório | Regras (`errors[].code`) |
| --- | --- | --- |
| `localUuid` | não | UUID |
| `policyId` | sim | `PolicyApi.view` não lança `POLICY_NOT_FOUND` e `policyholderUserId = sub`, senão 404 `CLAIM_POLICY_NOT_FOUND` (não revela se a apólice existe). Qualquer estado da apólice: a cobertura à data verifica-se depois da submissão |
| `type` | sim | `MATERIAL`, `BODILY`, `MATERIAL_AND_BODILY`, `THEFT`, `GLASS`, `FIRE`, `NATURE`, `OCCUPANTS` |
| `occurredAt` | sim, excepto com declaração | ≤ agora + 5 min (`DATE_IN_FUTURE`) |
| `location.text` | sim, excepto com declaração | 3–300 |
| `location.province`, `lat`, `lng`, `accuracyM` | não | como no S8-02 (`INVALID_COORDINATES`) |
| `description` | sim | 10–4000 (`TOO_SHORT`/`TOO_LONG`) |
| `policePresent` | não (`false`) | |
| `policeReportNumber` | não | ≤ 40; obrigatório na submissão se `type = THEFT` |
| `injuredCount` | não (0) | 0–50 (`OUT_OF_RANGE`) |
| `estimatedDamage` | não | `Money`, `amount ≥ 0` |
| `accidentStatementId` | não | regra 3 abaixo |
| `parties` | não | ≤ 20 (`CLAIM_PARTY_LIMIT`); `role` em `THIRD_PARTY`, `WITNESS`, `INJURED` (`INVALID_VALUE`); `name` 2–120 obrigatório; `msisdn` `Msisdn`; `plate` `PlateParser`; `insurerName` ≤ 120; `policyNumber` ≤ 30; `injuryDescription` ≤ 500, só `INJURED` |

Regras:

1. `localUuid` já usado por este cliente → 200 com o sinistro existente, **sem** o alterar (a fila offline repetiu o pedido). Primeira vez → 201 e cabeçalho `Location`.
2. O sinistro nasce `DRAFT` com `reporter_role = POLICYHOLDER`, `insurer_id`, `policy_number`, `policyholder_user_id` e `insured_plate` da apólice. Evento `CREATED`; auditoria `CLAIM.CREATE`.
3. Com `accidentStatementId`: a declaração tem de ser visível ao cliente (dono ou B) e `insured_plate` normalizada tem de estar em `plates` da declaração; senão 409 `STATEMENT_NOT_USABLE`. `occurredAt` e `location` que faltem copiam-se da declaração; se vierem, prevalecem os do pedido.
4. Um sinistro `DRAFT` não é visível à seguradora (RLS do S8-01).

**`updateMyClaim`** — os mesmos campos excepto `localUuid` e `policyId` (não mudam), mais `version` obrigatória (diferente da gravada → 409 `CONCURRENT_MODIFICATION`). Só em `DRAFT` (senão 409 `CLAIM_NOT_EDITABLE`). Substitui a lista de `parties`. Auditoria `CLAIM.UPDATE`.

### 3. Documentos

**`uploadClaimDocument`** — multipart: `file` (limites do S2-01: 10 MB, `image/jpeg`, `image/png`, `image/heic`, `application/pdf`) e `metadata` (JSON):

```json
{ "type": "PHOTO_DAMAGE", "localUuid": "a9e0…", "takenAt": "2027-03-05T11:52:13Z", "lat": -25.969180, "lng": 32.573240, "accuracyM": 9 }
```

- `type` obrigatório (`ClaimDocumentType`); o resto opcional.
- Permitido em `DRAFT`, `REPORTED` e `REGISTERED`; noutros estados → 409 `CLAIM_NOT_EDITABLE`.
- `localUuid` já existente no sinistro → 200 com o documento existente (não grava outro ficheiro).
- 31.º documento não removido → 409 `CLAIM_DOCUMENT_LIMIT`.
- `DocumentApi.store`: `ownerType = "CLAIM"`, `ownerId` = id do sinistro, `insurerId` do sinistro, classificação `SENSITIVE` para `DRIVING_LICENCE`, `MEDICAL_REPORT`, `DEATH_CERTIFICATE`; `PERSONAL` para os outros.
- Fora de `DRAFT` grava o evento `DOCUMENT_ADDED`. Auditoria `CLAIM.DOCUMENT_ADD` sempre.
- Resposta `ClaimDocumentResponse { id, type, fileId, contentType, sizeBytes, takenAt, lat, lng, accuracyM, uploadedAt }`.

**`removeClaimDocument`** — só em `DRAFT` (senão 409 `CLAIM_NOT_EDITABLE`); documento inexistente ou já removido → 404 `CLAIM_DOCUMENT_NOT_FOUND`. `removed_at = agora`; o ficheiro fica (nada se apaga). Auditoria `CLAIM.DOCUMENT_REMOVE`.

### 4. Submissão (`submitMyClaim`)

Sem corpo. Por esta ordem, numa transacção:

1. Sinistro do cliente (`reporter_user_id = sub`, pela RLS). Já `REPORTED` ou posterior **e** submetido por este cliente → 200 com o estado actual (repetição da fila). Outro estado que não `DRAFT` → 409 `INVALID_STATE_TRANSITION`.
2. **Completude** → 400 `CLAIM_INCOMPLETE` com `errors[]` (todos os que faltarem):

   | Condição | `errors[].field` | `errors[].code` |
   | --- | --- | --- |
   | `type` em `MATERIAL`, `MATERIAL_AND_BODILY`, `GLASS`, `FIRE`, `NATURE` sem nenhum `PHOTO_DAMAGE` não removido | `documents.PHOTO_DAMAGE` | `REQUIRED` |
   | `type = THEFT` sem `policeReportNumber` | `policeReportNumber` | `REQUIRED` |
   | `type` em `BODILY`, `MATERIAL_AND_BODILY`, `OCCUPANTS` com `injuredCount = 0` | `injuredCount` | `OUT_OF_RANGE` |

3. `number = ClaimNumbering.next()`, `reported_at = agora`.
4. **Partes vindas da declaração**: se houver declaração e não houver nenhuma parte `THIRD_PARTY` com a matrícula do outro veículo, acrescenta uma com `vehicles[outro].driver.name`, `driver.msisdn` (ou `policyholder.msisdn`), `plate`, `insurance.insurerName`, `insurance.policyNumber`. "Outro veículo" é o que não tem a matrícula `insured_plate`.
5. **`involved_plates`** = conjunto ordenado das matrículas normalizadas de `insured_plate`, das partes com `plate` e das `plates` da declaração.
6. **Prazo** (secção 5) → `report_deadline_at`, `late_report`.
7. **Triagem** (secção 6) → `priority`, `triage_reasons`, `sla_due_at`.
8. `Claim.submit(...)` → `REPORTED`. Eventos, por esta ordem: `SUBMITTED`, `STATEMENT_ATTACHED` (se houver declaração; `data.bothSigned`), `LATE_REPORT_FLAGGED` (se tardia), `TRIAGED`. Auditoria `CLAIM.SUBMIT`.
9. Publica `ClaimReported` (outbox).
10. `NotificationApi.notify(reporter, "CLAIM_REPORTED", { number, claimId, webPath: "/cliente/sinistros/{id}", deepLink: "moseguros://claims/{id}" }, NotificationCategory.CLAIM)`.

A validação da cobertura e a ligação correm a seguir, no `ClaimReportedListener` (secção 7), porque precisam de ver dados que o âmbito do cliente não vê.

### 5. Prazo de participação (`ReportDeadlineCalculator`)

Valores em `ClaimProperties` (S8-01), **provisórios** (ver "Questões"). Datas em `Africa/Maputo`.

**Tipos que não são `THEFT`:** `report_deadline_at` = início do dia (00:00, Maputo) de `data(occurred_at) + report-deadline-days + 1`. `late_report = reported_at ≥ report_deadline_at`. Ou seja: com 8 dias, é tardia a participação feita depois do 8.º dia de calendário a seguir ao acidente.

**`THEFT`** (48 horas úteis): conta-se o tempo a partir de `occurred_at`, só nos dias úteis (segunda a sexta que não estão em `public-holidays`, no formato `MM-dd`); cada dia útil vale 24 h; sábados, domingos e feriados não contam. `report_deadline_at` é o instante em que se completam 48 h. `late_report = reported_at > report_deadline_at`.

Casos de referência (`ReportDeadlineCalculatorTest`, horas de Maputo):

| Tipo | `occurred_at` | `reported_at` | `report_deadline_at` | `late_report` |
| --- | --- | --- | --- | --- |
| `MATERIAL` | 01/03/2027 23:00 | 09/03/2027 23:59 | 10/03/2027 00:00 | `false` |
| `MATERIAL` | 01/03/2027 23:00 | 10/03/2027 00:00 | 10/03/2027 00:00 | `true` |
| `THEFT` | sex 05/03/2027 18:00 | ter 09/03/2027 18:00 | ter 09/03/2027 18:00 | `false` |
| `THEFT` | sex 05/03/2027 18:00 | ter 09/03/2027 18:01 | ter 09/03/2027 18:00 | `true` |
| `THEFT` | sáb 13/03/2027 15:00 | — | qua 17/03/2027 00:00 | — |
| `THEFT` | ter 06/04/2027 10:00 (07/04 é feriado) | — | sex 09/04/2027 10:00 | — |

A participação tardia não bloqueia nem muda a prioridade: só marca `late_report`, grava `LATE_REPORT_FLAGGED` e aparece como alerta na fila da seguradora (S8-05, S8-06).

### 6. Triagem (`ClaimTriage`)

Entradas: `type`, `injuredCount`, `estimatedDamage`, `bothSigned` da declaração (falso sem declaração). Limiares em `ClaimProperties.triage` (**provisórios**): `high-estimate-amount` = 50 000 000 centavos, `low-estimate-amount` = 5 000 000 centavos.

Regras, pela ordem; a primeira que se aplica decide a prioridade, e `triage_reasons` junta **todos** os motivos verdadeiros:

| # | Condição | Prioridade | Motivo |
| --- | --- | --- | --- |
| 1 | `type` em `BODILY`, `MATERIAL_AND_BODILY`, `OCCUPANTS` ou `injuredCount > 0` | `HIGH` | `BODILY_INJURY` |
| 2 | `type` em `THEFT`, `FIRE` | `HIGH` | `THEFT_OR_FIRE` |
| 3 | `estimatedDamage ≥ high-estimate-amount` | `HIGH` | `HIGH_ESTIMATE` |
| 4 | `type = GLASS` | `LOW` | `GLASS_ONLY` |
| 5 | `type = MATERIAL`, `bothSigned`, `estimatedDamage` presente e `< low-estimate-amount` | `LOW` | `SIGNED_STATEMENT_LOW_ESTIMATE` |
| 6 | nenhuma das anteriores | `NORMAL` | — |

Motivos adicionais (não decidem): `NO_STATEMENT` se `type` em `MATERIAL`, `MATERIAL_AND_BODILY` sem declaração; `UNSIGNED_STATEMENT` se houver declaração sem `bothSigned`; `LATE_REPORT` se tardia.

`sla_due_at = reported_at + sla-hours[priority]` (provisório: `HIGH` 24 h, `NORMAL` 72 h, `LOW` 120 h).

### 7. Depois da submissão (`ClaimReportedListener`)

`@ApplicationModuleListener` de `ClaimReported`, `@RunAsSystem` (classe `…Listener` no pacote `application`). Procura o sinistro por `claimId` **e** `insurerId` do evento (filtro explícito no código, porque em `SYSTEM` o RLS deixa ver tudo). Idempotente: uma segunda entrega do mesmo evento não faz nada que já esteja feito.

**7.0 Tomador** (só se `policyholder_user_id` for nulo, caso dos sinistros de terceiro do S8-04): `PolicyApi.view(policyId).policyholderUserId` (em `SYSTEM` o `view` vê a apólice).

**7.1 Cobertura** (só se `cover_checked_at` for nulo e o estado for `REPORTED`):

1. `PolicyApi.coverAt(policyId, occurredAt)`.
2. `CoverStatus.COVERED` → `cover_status = COVERED`, `cover_checked_at`, evento `COVER_CHECKED` (`covered: true`).
3. Outro valor → `cover_status = NOT_COVERED`, evento `COVER_CHECKED` (`covered: false`, `detail` = nome do `CoverStatus`), `Claim.rejectAutomatically(NO_COVER_AT_DATE)`, `rejected_automatically = true`, evento `AUTO_REJECTED`, auditoria `CLAIM.AUTO_REJECT` (actor `SYSTEM`, `ClaimReportedListener`), publica `ClaimRejected(…, NO_COVER_AT_DATE, automatic = true)`, notifica o participante com `CLAIM_AUTO_REJECTED` (`{ number, claimId, policyNumber, occurredDate: LocalDate do acidente, webPath, deepLink }`, `NotificationCategory.CLAIM`).
4. A revisão humana desta rejeição faz-se na seguradora (`registerOverride`, S8-05).

**7.2 Ligação** (só se `linked_claim_id` for nulo; corre também para os rejeitados, para mostrar duplicados à seguradora):

Candidatos: sinistros com o **mesmo `insurer_id`**, `id` diferente, estado diferente de `DRAFT`, `involved_plates && <as deste>` (índice GIN), `|occurred_at − este.occurred_at| ≤ link.max-minutes-apart` (120 min, inclusive), e coordenadas nos dois. Para cada candidato:

- **Matrículas**: `|interseção| ≥ 2`, ou os dois conjuntos têm uma só matrícula e é a mesma.
- **Distância** (`GeoDistance.haversineMetres`), ≤ `link.max-distance-metres` (500, inclusive):

```
R  = 6 371 008,8 m (raio médio da Terra)
φ1, φ2 = latitudes em radianos;  Δφ = φ2 − φ1;  Δλ = (λ2 − λ1) em radianos
a  = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)
d  = 2 · R · asin(√a)
```

  Em `double`; compara-se `d ≤ 500,0` sem arredondar. Para o evento, `distanceM = round(d)` (`HALF_UP`).

Escolha: entre os candidatos que passam, o **principal** é `candidato.linked_claim_id ?? candidato.id`; escolhe-se o principal do candidato com `reported_at` mais antigo (empate: `number` menor). `este.link(principal)`; evento `LINKED` neste (`role = SECONDARY`) e no principal (`role = PRIMARY`), com `otherClaimId`, `otherNumber`, `distanceM`, `minutesApart` (inteiro, `HALF_UP`); auditoria `CLAIM.LINK`.

Sinistros de seguradoras diferentes **não** se ligam (cada seguradora só vê os seus; ver "Questões"). Sem coordenadas num dos dois, não há ligação automática.

## Critérios de aceitação

- [ ] `CustomerClaimIT`:
  - criar rascunho com a própria apólice → 201 `DRAFT`, sem `number`; a mesma chamada com o mesmo `localUuid` → 200 e um só sinistro;
