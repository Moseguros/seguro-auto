## Especificação

### 1. Dois utilizadores de base de dados

- O **Flyway** corre com o utilizador dono das tabelas: `spring.flyway.user: ${DB_OWNER_USERNAME:moseguros}`, `spring.flyway.password: ${DB_OWNER_PASSWORD:moseguros}`.
- A **aplicação** liga-se com `spring.datasource.username: ${DB_USERNAME:moseguros_app_user}` / `${DB_PASSWORD:moseguros_app}`, um utilizador sem `SUPERUSER`, sem `BYPASSRLS` e que não é dono de nenhuma tabela. Só assim o RLS se aplica a ele.
- Os scripts `init-roles.sql` (testes e compose, conteúdo igual) criam, antes das migrações:

```sql
create role moseguros_app nologin;
create role moseguros_app_user login password 'moseguros_app' in role moseguros_app;
```

- `TestcontainersConfiguration` deixa de usar `@ServiceConnection` e passa a: `new PostgreSQLContainer<>("postgres:16-alpine").withInitScript("db/init-roles.sql")` e um `@DynamicPropertySource`/`DynamicPropertyRegistrar` que define `spring.datasource.url/username/password` (utilizador da aplicação) e `spring.flyway.url/user/password` (utilizador do contentor, que é dono).
- Em staging e produção os papéis são criados pela equipa de operações; está escrito no `infra/README.md` (S0-07) numa secção "Base de dados — papéis".

**`V202611020900__shared_app_role.sql`** (corre como dono):

```sql
do $$ begin
  if not exists (select 1 from pg_roles where rolname = 'moseguros_app') then
    create role moseguros_app nologin;
  end if;
end $$;

-- schemas já criados em V202610311200
grant usage on schema audit, identity, organization to moseguros_app;
grant select, insert on audit.audit_event to moseguros_app;
grant select, insert, update on public.event_publication to moseguros_app;

alter default privileges in schema identity, organization grant select, insert, update on tables to moseguros_app;
```

Nenhuma tabela dos dois schemas dá `delete` ao papel da aplicação.

### 2. Âmbito da transacção (`TenantContext`)

```java
public enum Scope { NONE, SYSTEM, PLATFORM, ORG, CUSTOMER }
public record TenantSnapshot(Scope scope, UUID userId, UUID orgId, UUID insurerId) {}
```

- `TenantContext` guarda um `TenantSnapshot` num `ThreadLocal`; por defeito `Scope.NONE` (não vê nada). Métodos: `current()`, `set(TenantSnapshot)`, `clear()`, `insurerId()` (lança `DomainException` `TENANT_REQUIRED`, 500, se não houver).
- O preenchimento a partir do token é feito no S1-02. Nesta tarefa os testes preenchem-no à mão.
- **`TenantJpaTransactionManager extends JpaTransactionManager`**: em `doBegin`, depois do `super.doBegin`, executa na mesma ligação

```sql
select set_config('app.scope', ?, true),
       set_config('app.user_id', ?, true),
       set_config('app.org_id', ?, true),
       set_config('app.insurer_id', ?, true)
```

  com os valores do `TenantContext` (`''` quando `null`). O terceiro argumento `true` torna-os locais à transacção. É registado como o `transactionManager` principal em `TenantConfig`.
- **`@RunAsSystem`** (anotação de método) + `RunAsSystemAspect` com `@Order(Ordered.HIGHEST_PRECEDENCE)`, para correr **antes** do interceptor de transacções: guarda o contexto actual, define `Scope.SYSTEM` (mantendo `userId`), executa e repõe o anterior num `finally`. Se já houver uma transacção activa ao entrar, lança `IllegalStateException` (o âmbito tem de ser definido antes de a transacção começar).
- Só podem usar `@RunAsSystem` classes em `identity.application` e `notification.application`, e o arranque (`ApplicationRunner`) de `identity`. Um teste ArchUnit (`RunAsSystemUsageTest`) garante isto; acrescentar `com.tngtech.archunit:archunit-junit5` (1.3.x) em `test`.

### 3. Políticas de RLS

Em todas as tabelas com RLS: `alter table … enable row level security; alter table … force row level security;` e uma política `for all to moseguros_app using (<expr>) with check (<expr>)`. Abreviaturas usadas abaixo:

```sql
-- s  = current_setting('app.scope', true)
-- u  = nullif(current_setting('app.user_id', true), '')::uuid
-- o  = nullif(current_setting('app.org_id', true), '')::uuid
```

| Tabela | Expressão da política |
| --- | --- |
| `organization.organization` | `s in ('SYSTEM','PLATFORM') or (s = 'ORG' and id = o)` |
| `organization.insurer_profile` | `s in ('SYSTEM','PLATFORM') or (s = 'ORG' and organization_id = o)` |
| `identity.user_account` | `s in ('SYSTEM','PLATFORM') or (s = 'ORG' and organization_id = o) or (s = 'CUSTOMER' and id = u)` |
| `identity.customer_profile` | `s in ('SYSTEM','PLATFORM') or (s = 'CUSTOMER' and user_id = u)` |
| `identity.user_role` | `s in ('SYSTEM','PLATFORM') or (s = 'ORG' and exists (select 1 from identity.user_account a where a.id = user_id and a.organization_id = o)) or (s = 'CUSTOMER' and user_id = u)` |
| `identity.invitation` | `s in ('SYSTEM','PLATFORM') or (s = 'ORG' and organization_id = o)` |
| `identity.otp_settings` | `s in ('SYSTEM','PLATFORM')` |
| `identity.otp_challenge`, `identity.refresh_token`, `identity.password_reset` | `s = 'SYSTEM'` |

`identity.role` e `identity.role_permission` não têm RLS: são tabelas de referência, com `grant select` apenas (sem `insert`/`update` para a aplicação; os perfis mudam por migração).

### 6. Cifra de colunas (`CryptoService`)

- AES-256-GCM, IV aleatório de 12 bytes por valor, etiqueta de 128 bits.
- Formato gravado (`bytea`): `[versão da chave: 1 byte][IV: 12 bytes][texto cifrado + etiqueta]`. Versão actual `1`.
- Chave em `moseguros.crypto.data-keys` (mapa versão → Base64 de 32 bytes) e `moseguros.crypto.current-key-version`; em produção vem da variável de ambiente `MOSEGUROS_DATA_KEY_1` (cofre de segredos no Sprint 5). `application-local.yml` e `application-test.yml` têm uma chave de desenvolvimento fixa com o comentário `# chave só para desenvolvimento`. Sem chave, a aplicação não arranca (falha na validação de `CryptoProperties`).
- `EncryptedStringConverter implements AttributeConverter<String, byte[]>` usa o `CryptoService` (o conversor é um bean Spring; Hibernate 6 suporta injecção em conversores com o `SpringBeanContainer`, que o Spring Boot configura).
- `CryptoServiceTest`: cifrar duas vezes o mesmo valor dá resultados diferentes; decifrar devolve o original; alterar um byte faz falhar com `DomainException` `DECRYPTION_FAILED` (500); um valor cifrado com a versão 1 continua legível depois de se acrescentar a versão 2 como actual.

### 7. Entidades

- Todas estendem `BaseEntity` (S0-03), excepto `RolePermission` e `UserRole` (chave composta com `@IdClass` ou `@EmbeddedId`).
- Enums Java com os mesmos valores dos `check`, gravados com `@Enumerated(EnumType.STRING)`.
- Colunas `text[]` mapeadas com `@JdbcTypeCode(SqlTypes.ARRAY)` para `List<Channel>`/`List<String>`.
- `Msisdn` e e-mails com os conversores do S0-03; `CustomerProfile.idDocNumber` e `nuit` com `EncryptedStringConverter` (no Java são `String` em claro; `nuit` é validado com `Nuit` antes de gravar).
- Regras de domínio desta tarefa (com testes unitários): `UserAccount.newCustomer(Msisdn | email)`, `UserAccount.newStaff(email, displayName, organizationId)` (status `PENDING_ACTIVATION`), `Organization.create(...)` valida `license_number` obrigatório para `INSURER/BROKER/AGENT` (`LICENSE_NUMBER_REQUIRED`, 400), `Organization.suspend()` e `reactivate()` (transições `ACTIVE → SUSPENDED → ACTIVE`; repetir dá `INVALID_STATE_TRANSITION`, 409), `OtpSettings.update(...)` valida as regras da tabela (S1-03 usa).
