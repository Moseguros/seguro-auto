## Contexto

Antes de submeter, o tomador assina a proposta com uma assinatura electrónica simples: a plataforma gera o PDF da proposta, calcula o seu SHA-256 e envia um código OTP para o telemóvel do tomador; o código introduzido prova a assinatura daquele documento (plano: "OTP SMS sobre o hash do PDF da proposta"). Esta tarefa cria a geração de PDFs no módulo `document` (`DocumentApi.renderPdf`, modelo transversal §3 e §7), que o S6-02 reutiliza para o certificado, e o OTP com `purpose = SIGN` no `identity` (reutiliza o `OtpService` do S1-03).

**Pressupõe:**
- S1-03: `OtpService`, `OtpCodeHasher` (`HMAC-SHA256(pepper, challengeId + ":" + code)`), `identity.otp_challenge` (já aceita `purpose = 'SIGN'`), `identity.otp_settings`, alternativa de canal, limites por hora e de reenvio, códigos `OTP_*`; `NotificationApi.sendOtp`, `OtpDeliveryChannel`, mocks de SMS e WhatsApp.
- S4-01: `IdentityApi.customer(UUID)`; a conta do cliente tem `msisdn` e/ou e-mail.
- S4-02: `proposal.proposal` (`content_revision`, estados, regra de editável), `ProposalResponse` (blocos `signature` e `checklist.signature`), `api/proposal-questions.json`.
- S4-03: bloco `inspection` e o estado da vistoria.
- S2-01: `DocumentApi.store(StoreFileCommand) → FileRef` (`StoreFileCommand(ownerType, ownerId, purpose, classification, insurerId, originalFilename, declaredContentType, allowedContentTypes, content)`; o `FileRef` traz `sha256` e `sizeBytes`), `DocumentApi.markLinked(UUID)`, `FileAccessPolicy` (com `ownerTypes()`; o `store` recusa um `ownerType` sem política registada), `GET /api/v1/files/{id}`.
- S2-04/S2-05: `ProductVersionView.generalConditionsFileId`, `preContractInfoFileId`, `documents`; textos `coverage.<CODE>` (S2-05).
- S3-03: `formatMoney` da web (`466300` → `4 663,00 MT`, separador de milhares U+00A0).

## Objectivo

`POST /proposals/{id}/sign/request` gera o PDF da proposta, guarda-o com o seu SHA-256 e envia o código ao tomador; `POST /proposals/{id}/sign/confirm` com o código certo grava a assinatura ligada ao hash do PDF. Qualquer alteração posterior à proposta invalida a assinatura.

## Especificação

### 1. PDF no módulo `document`

**API** (pacote raiz `mz.co.moseguros.document`):

```java
public record PdfTarget(String ownerType, UUID ownerId, String purpose, UUID insurerId,
                        FileClassification classification, String fileName) {}

// assinatura do modelo transversal §3; o dono vai no modelo, na chave reservada "_target" (um PdfTarget)
public FileRef renderPdf(String templateCode, Map<String, Object> model, Locale locale);
// equivalente, com o dono explícito
public FileRef renderPdf(String templateCode, Map<String, Object> model, Locale locale, PdfTarget target);
```

**É este o mecanismo para ligar um PDF gerado ao seu dono** (o S5-02 e o S6-02 usam-no): o `PdfTarget` diz o dono, e o `renderPdf` guarda e liga o ficheiro numa só chamada. Na forma de 3 argumentos, `model.get("_target")` tem de ser um `PdfTarget` (senão `IllegalArgumentException`); a chave `_target` não chega ao modelo Thymeleaf.

- `PdfTemplates`: registo dos modelos; nesta tarefa só `proposal` → `templates/pdf/proposal.html`. Código desconhecido → `DomainException` `PDF_TEMPLATE_NOT_FOUND` (500).
- `ThymeleafPdfConfig`: um `SpringTemplateEngine` próprio (bean com nome `pdfTemplateEngine`) com `ClassLoaderTemplateResolver` (`prefix = "templates/pdf/"`, `suffix = ".html"`, `TemplateMode.XML`, UTF-8, cache ligada fora do perfil `local`) e um `MessageSource` só para `messages/pdf` (`pdf_pt.properties`, `pdf_en.properties`; sem alternativa para a língua do sistema; chave em falta → excepção, não texto vazio).
- Os modelos são XHTML válido (o Flying Saucer exige XML bem formado). CSS em `<style>` no `_layout.html`, tamanho A4, margens 18 mm, fonte Inter embebida com `@font-face` (`-fs-pdf-font-embed: embed; -fs-pdf-font-encoding: Identity-H`), cores da marca (`#142D4E` para títulos e linhas; sem laranja).
- `FlyingSaucerPdfRenderer`: `ITextRenderer` → `byte[]`; regista as fontes de `classpath:fonts/`. Erro de renderização → `DomainException` `PDF_RENDER_FAILED` (500), com o erro original no log (sem o conteúdo do modelo).
- `PdfRenderService.render(...)` (`@Transactional(propagation = MANDATORY)`: corre na transacção de quem chama): renderiza; chama `store(StoreFileCommand)` com os dados do `PdfTarget`, `originalFilename = fileName`, `declaredContentType = allowedContentTypes = application/pdf`; chama `markLinked(fileId)`; devolve o `FileRef` (com o `sha256` calculado pelo `document`, S2-01). Se a transacção de quem chama fizer rollback, a linha de `document.file` também desaparece (o ficheiro no armazenamento fica e o job de órfãos do S2-01 não o vê; aceita-se). O `Locale` escolhe as mensagens (`pt` ou `en`; outra → `pt`).
- `PdfFormatter`, disponível nos modelos como variável `fmt`:
  - `fmt.money(Money)`: pt igual ao `formatMoney` da web (S3-03 §9): `12 345,67 MT` com U+00A0 nos milhares, vírgula decimal, 2 casas; en `MZN 12,345.67`;
  - `fmt.date(Instant|LocalDate)`: pt `09/01/2027`; en `09 Jan 2027`; os `Instant` convertem-se para `Africa/Maputo`;
  - `fmt.dateTime(Instant)`: pt `09/01/2027 14:05`; en `09 Jan 2027 14:05`, em `Africa/Maputo`;
  - `fmt.percent(BigDecimal)`: pt `5,00 %`; en `5.00%`.

### 2. Hash do documento

- O hash é o **SHA-256 dos bytes exactos do PDF guardado**, em hexadecimal minúsculo (64 caracteres), o mesmo `sha256` do `document.file` (S2-01).
- Não se tenta tornar o PDF determinístico: dois PDFs da mesma proposta podem ter hashes diferentes (datas internas do PDF). A assinatura liga-se ao ficheiro concreto que o tomador pôde descarregar e cujo hash ficou gravado.
- Quem quiser verificar descarrega o PDF (`GET /api/v1/files/{documentFileId}`) e calcula `sha256sum`; tem de dar o `documentHash` da assinatura.

### 3. Conteúdo mínimo do PDF da proposta (`proposal.html`)

Por esta ordem. Textos das etiquetas em `pdf_{pt,en}.properties` (chaves `pdf.proposal.*`), na língua do tomador (`policyholder.preferredLanguage`).

1. **Cabeçalho**: logótipo MoSeguros (`docs/brand/logo.svg` convertido para PNG em `src/main/resources/templates/pdf/logo.png`), título "Proposta de seguro automóvel", número `PR-…`, data e hora de geração (Maputo), revisão (`content_revision`).
2. **Seguradora e produto**: nome da seguradora, produto e versão (`product_name`, `product_version_id`), tipo; canal; nome do mediador (se houver).
3. **Tomador e segurado**: nome, data de nascimento, tipo e **número completo** do documento, **NUIT completo**, morada, província, telemóvel e e-mail; "O segurado é o tomador." (Este PDF é classificado `SENSITIVE`.)
4. **Veículo**: matrícula, marca, modelo, ano, número do chassis, categoria, uso, lugares, valor comercial declarado (ou "—").
5. **Condutor habitual**: nome, data de nascimento, carta (`licenceNumberMasked`; o número em claro não sai do `vehicle`), categorias, data de emissão.
6. **Período**: "de {startDate} a {endDate}" (datas em Maputo, `endDate` = último dia coberto: "de 10/01/2027 a 09/01/2028"), duração em dias.
7. **Coberturas**: tabela com nome (`pdf.coverage.<CODE>`, os mesmos textos de `coverage.<CODE>` do S2-05), capital, franquia (`Sem franquia`, valor, ou percentagem) e prémio de cada cobertura.
8. **Prémio**: prémio comercial, cada encargo com o `labelPt`/`labelEn` guardado na proposta, o acerto de arredondamento (se ≠ 0), total.
9. **Declarações de risco**: cada pergunta (texto pt/en igual ao do S4-02, chaves `pdf.declaration.<CODE>`), resposta Sim/Não, e os seguimentos; o texto da confirmação de veracidade e a data de confirmação.
10. **Adequação**: cada pergunta e resposta (`pdf.suitability.<CODE>` e `pdf.suitability.answer.<VALUE>`), o resultado; com `WARNED`, cada aviso (`pdf.suitability.reason.<CODE>`, mesmos textos do S4-02) e "O tomador leu os avisos e confirmou que quer continuar em {data}."
11. **Vistoria** (só com `inspection_required`): modo, estado, número de fotografias, quilometragem e data de envio; ou as notas do pedido presencial.
12. **Documentos do produto**: "O tomador declara ter recebido e lido as Condições Gerais e a Informação Pré-contratual desta versão do produto." com o `fileId` de cada documento (do `CatalogApi.version`).
13. **Assinatura**: "Esta proposta é assinada electronicamente pelo tomador com um código enviado para {destino mascarado}. O registo da assinatura guarda a impressão digital (SHA-256) deste documento." (O hash não pode estar dentro do próprio documento.)
14. **Rodapé** em todas as páginas: "MoSeguros · {número} · Página {n} de {total}" (`counter(page)` e `counter(pages)` no CSS).

`ProposalPdfModelBuilder` monta o `Map` a partir da proposta (decifra o documento e o NUIT do tomador só para o modelo; nunca os regista em log).

`PdfMessagesCompletenessTest` lê `api/proposal-questions.json` e falha se faltar em `pdf_pt.properties` ou `pdf_en.properties` alguma chave de pergunta, resposta ou aviso, ou `pdf.coverage.<CODE>` de algum dos 12 códigos de cobertura.

### 4. OTP de assinatura (`identity`)

```java
public record SignOtpRequest(UUID signerUserId, UUID documentId, String documentHash, String documentRef,
                             String insurerName, Money total, String assistedByName, Channel preferredChannel) {}
public record SignOtpChallenge(UUID challengeId, Channel channel, String destinationMasked,
                               int resendAfterSeconds, Instant expiresAt, boolean fallbackUsed) {}
public record SignOtpVerification(UUID challengeId, Channel channel, String destinationMasked, Instant verifiedAt) {}

public SignOtpChallenge requestSignOtp(SignOtpRequest request);
public SignOtpVerification verifySignOtp(UUID signerUserId, UUID challengeId, String code, String documentHash);
```

Ambos `@RunAsSystem` (no `identity`). Regras:

1. **Destino**: o `msisdn` da conta do signatário (verificado ou não: a conta criada por um mediador pode ainda não o ter verificado); sem `msisdn`, o e-mail verificado; sem nenhum → 409 `SIGNER_CONTACT_MISSING`.
2. **Canal**: como no `requestOtp` do S1-03 para o tipo do destino (`MSISDN` → SMS/WhatsApp; `EMAIL` → e-mail), incluindo `customer_can_choose`, `defaultChannels` e a alternativa automática por `fallbackOrder` (síncrona e por recibo, `OtpFallbackListener`). `preferredChannel` é o `channel` do S1-03.
3. **Limites**: os do S1-03, contando também os desafios `SIGN` (a regra do passo 3 do S1-03 passa a `purpose in (LOGIN, TEST, VERIFY_CONTACT, SIGN)`). Excedidos → 429 `OTP_RATE_LIMITED` / `OTP_RESEND_TOO_SOON` com `Retry-After`.
4. **Desafio**: `purpose = SIGN`, `user_id = signerUserId`, `identifier` = destino normalizado. Desafios `SIGN` anteriores não consumidos do mesmo utilizador ficam `superseded_at`.
5. **Ligação ao documento**: para `SIGN`, `code_hash = HMAC-SHA256(pepper, challengeId + ":" + code + ":" + documentHash)`. Para os outros fins o cálculo do S1-03 não muda. Assim, um código só serve para o documento com aquele hash.
6. **Verificação**: as mesmas regras e códigos do `verifyOtp` do S1-03 (`OTP_CHALLENGE_NOT_FOUND`, `OTP_ALREADY_USED`, `OTP_SUPERSEDED`, `OTP_EXPIRED`, `OTP_ATTEMPTS_EXCEEDED`, `OTP_INVALID` com `attemptsRemaining`, incremento gravado mesmo com erro). Desafio que não é `SIGN` ou de outro `user_id` → 404 `OTP_CHALLENGE_NOT_FOUND`. Com sucesso: `consumed_at`; se o destino era o `msisdn` ainda não verificado, passa a `msisdn_verified = true` (o código prova a posse do número).
7. **Envio**: `NotificationApi.sendSignOtp(...)` (abaixo). No perfil `local`, a resposta do endpoint da proposta leva o cabeçalho `X-Debug-Otp` com o código, como no S1-03 (mesma propriedade e mesma proibição em `prod`).

**`NotificationApi`** (acrescentar; mesmo comportamento do `sendOtp`: síncrono, 5 s, nunca lança, devolve `FAILED`):

### 7. Endpoints (tag `Proposal`, `hasAnyAuthority('self:proposals','proposal:create-for-client')`)

**`POST /api/v1/proposals/{id}/sign/request`** (`requestProposalSignature`) `{ "documentsAcknowledged": true, "channel": "SMS", "version": 7 }` → 202:

```json
{ "challengeId": "0194…", "channel": "SMS", "destinationMasked": "+258*****4567",
  "resendAfterSeconds": 60, "expiresAt": "2027-01-06T08:35:00Z", "fallbackUsed": false,
  "documentFileId": "0194…", "documentHash": "9f2c…e1" }
```

Por esta ordem:
1. Proposta editável → senão 409 `PROPOSAL_NOT_EDITABLE`; `version` → 409 `CONCURRENT_MODIFICATION`.
2. `documentsAcknowledged ≠ true` → 400 campo `documentsAcknowledged` `MUST_BE_TRUE`. `channel` opcional.
3. `ProposalCompleteness` sem o item `SIGNATURE`; lista não vazia → 409 `PROPOSAL_INCOMPLETE` com a propriedade `missing` (ex.: `["SUITABILITY_ACKNOWLEDGEMENT","INSPECTION"]`).
4. Gera o PDF: `DocumentApi.renderPdf("proposal", model, locale, new PdfTarget("PROPOSAL", proposalId, "PROPOSAL_DOCUMENT", insurerId, SENSITIVE, number + "-r" + revision + ".pdf"))`.
5. `IdentityApi.requestSignOtp(...)` com `signerUserId = customer_user_id`, `documentId = file.id`, `documentHash = file.sha256`, `documentRef = number`, `insurerName`, `total`, `assistedByName` (S4-06; aqui `null`).
6. Grava `sign_request_*` com o ficheiro, o hash, o desafio e a revisão actual. Pedir de novo substitui o pedido anterior (o desafio anterior fica `superseded`). **Não** aumenta `content_revision`. Auditoria `PROPOSAL.SIGN_REQUEST` (depois: `documentFileId`, `documentHash`, `channel`).

**`POST /api/v1/proposals/{id}/sign/confirm`** (`confirmProposalSignature`) `{ "challengeId": "0194…", "code": "123456" }` → 200 `ProposalResponse`.
1. Proposta editável → senão 409 `PROPOSAL_NOT_EDITABLE`.
2. Sem pedido em curso, ou `challengeId ≠ sign_request_challenge_id` → 409 `SIGN_REQUEST_NOT_FOUND`.
3. `sign_request_revision ≠ content_revision` (a proposta mudou depois do pedido) → 409 `PROPOSAL_CHANGED_SINCE_SIGN_REQUEST`; o ecrã pede de novo.
4. `IdentityApi.verifySignOtp(customer_user_id, challengeId, code, sign_request_hash)`; os erros `OTP_*` passam tal e qual.
5. Grava `proposal.signature` (dados do pedido e da verificação, `ip` como no `AuditService`, `user_agent`), `current_signature_id`, limpa `sign_request_*`, `expires_at` (S4-02). Auditoria `PROPOSAL.SIGN` (depois: `signatureId`, `documentHash`, `channel`, `destinationMasked`).

**Invalidação.** Qualquer acção que aumente `content_revision` (S4-02 secção 6, S4-03, S4-06) e o pedido de informação da seguradora (S4-05) marcam a assinatura actual com `invalidated_at` e `invalidated_reason` (`CONTENT_CHANGED` ou `INFO_REQUESTED`), põem `current_signature_id = null` e limpam `sign_request_*`. Implementar num único método de domínio `Proposal.contentChanged()`, chamado por todos.

```json
             "documents": [ { "type": "GENERAL_CONDITIONS", "fileId": "…" }, { "type": "PRE_CONTRACT_INFO", "fileId": "…" } ] }
```

Os ids vêm de `CatalogApi.version(productVersionId).documents()` (só `GENERAL_CONDITIONS` e `PRE_CONTRACT_INFO`, na língua do tomador, ou em `pt` se não houver); a descarga usa `GET /api/v1/files/{id}` com a `FileAccessPolicy` `PRODUCT_VERSION` do S2-04 (públicos depois de publicados).

`ProposalView` (S4-02): `signedDocumentFileId` = `document_file_id` da assinatura válida (o S6-02 junta-o aos documentos da apólice).

### 9. Quem pode ler o PDF (`ProposalFileAccessPolicy`)

`ownerTypes() = {"PROPOSAL"}`. `true` se a proposta `ownerId` for visível no âmbito actual (RLS) **e**: âmbito `CUSTOMER`; ou âmbito `ORG` com `broker_org_id` = organização actual; ou âmbito `ORG` de seguradora com `submitted_at is not null` e `proposal:read`.

### 10. Códigos de erro novos

Topo: `PDF_TEMPLATE_NOT_FOUND` (500), `PDF_RENDER_FAILED` (500), `SIGNER_CONTACT_MISSING` (409), `PROPOSAL_INCOMPLETE` (409, com `missing`), `SIGN_REQUEST_NOT_FOUND` (409), `PROPOSAL_CHANGED_SINCE_SIGN_REQUEST` (409). Traduções na web e na app no mesmo PR:

| Código | pt-MZ | en |
| --- | --- | --- |
| `PDF_TEMPLATE_NOT_FOUND`, `PDF_RENDER_FAILED` | Não foi possível gerar o documento. Tente de novo. | We could not generate the document. Try again. |
| `SIGNER_CONTACT_MISSING` | Não há telemóvel nem e-mail verificado para enviar o código. | There is no phone number or verified e-mail to send the code to. |
| `PROPOSAL_INCOMPLETE` | Ainda faltam passos para concluir a proposta. | There are still steps to complete in this proposal. |
| `SIGN_REQUEST_NOT_FOUND` | Este código já não é válido. Peça um novo. | This code is no longer valid. Request a new one. |
| `PROPOSAL_CHANGED_SINCE_SIGN_REQUEST` | A proposta mudou depois de pedir o código. Peça um novo. | The proposal changed after the code was requested. Request a new one. |

Itens de `missing` (`proposal.missing.<ITEM>`, usados nos ecrãs): `DECLARATIONS` Declarações de risco / Risk declarations; `SUITABILITY` Questionário de adequação / Suitability questionnaire; `SUITABILITY_ACKNOWLEDGEMENT` Confirmar os avisos de adequação / Confirm the suitability warnings; `INSPECTION` Vistoria do veículo / Vehicle inspection; `START_DATE` Data de início / Start date; `SIGNATURE` Assinatura / Signature.
