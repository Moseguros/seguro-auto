## Contexto

Qualquer pessoa ou agente da PRM confirma em segundos se um veículo tem seguro válido, pela matrícula ou pelo QR do certificado, sem ver dados pessoais do tomador. Cobre RF-28 e RF-29 (verificação). Convenção do plano: limite de 60 pedidos por minuto e por IP na verificação pública. Modelo transversal §1 (`verification → policy, organization`), §2, §5, §7 (CAPTCHA), ADR-002 (adenda).

## Objectivo

`GET /api/v1/public/verifications/{token}` e `GET /api/v1/public/verifications?plate=…` (com CAPTCHA) devolvem uma resposta mínima calculada no momento; os agentes da polícia têm os mesmos pedidos sem CAPTCHA e o histórico das suas consultas; cada consulta fica em `verification.check_log` sem a matrícula nem o código em claro; o abuso é travado por limites de pedidos.

## Especificação

### 1. Tabela `verification.check_log` (`V202702010300__verification_check_log.sql`)

Colunas obrigatórias subentendidas. `grant usage on schema verification to moseguros_app`; `grant select, insert on verification.check_log to moseguros_app` (sem `update` nem `delete`: o registo só cresce).

| Coluna | Tipo | Regras |
| --- | --- | --- |
| `subject_type` | `varchar(5) not null` | `check in ('PLATE','TOKEN')` |
| `subject_hash` | `varchar(64) not null` | HMAC-SHA256 em hexadecimal (regra 4); nunca a matrícula nem o código em claro |
| `plate_masked` | `varchar(20) null` | `Matricula.masked()` (ex.: `ABC-***-MC`); `null` quando um código não corresponde a nenhuma apólice |
| `result` | `varchar(15) not null` | `check in ('VALID','NOT_YET_VALID','EXPIRED','SUSPENDED','CANCELLED','NOT_FOUND')` |
| `policy_id` | `uuid null` | apólice encontrada (estatísticas, S11) |
| `insurer_id` | `uuid null` | seguradora da apólice encontrada |
| `checker_type` | `varchar(10) not null` | `check in ('PUBLIC','POLICE')` |
| `checker_user_id` | `uuid null` | agente da polícia; `null` em `PUBLIC` |
| `checker_org_id` | `uuid null` | organização do agente |
| `ip_prefix` | `varchar(49) null` | IP truncado (regra 5) |
| `checked_at` | `timestamptz not null` | |

`check ((checker_type = 'POLICE') = (checker_user_id is not null))`.

Índices: `(checker_user_id, checked_at desc) where checker_user_id is not null`, `(subject_hash, checked_at desc)`, `(checked_at)`.

**RLS** — duas políticas, porque a consulta pública grava sem utilizador (âmbito `NONE`) e não pode ler:

```sql
alter table verification.check_log enable row level security;
create policy check_log_insert on verification.check_log for insert to moseguros_app with check (true);
create policy check_log_select on verification.check_log for select to moseguros_app using (
  current_setting('app.scope', true) in ('SYSTEM','PLATFORM')
  or (current_setting('app.scope', true) = 'ORG'
      and checker_user_id = nullif(current_setting('app.user_id', true), '')::uuid)
);
```

Assim, o serviço grava em qualquer âmbito sem `@RunAsSystem`, e um agente só lê as suas consultas.

### 2. Endpoints (tag `Verification`)

Todas as respostas: `Cache-Control: no-store`. Datas em UTC.

**Públicos** (sem autenticação; `/api/v1/public/**` entra nos caminhos públicos do `SecurityConfig`, por isso o `Authorization` é ignorado):

- **`GET /api/v1/public/verifications/config`** (`getVerificationConfig`) → 200 `{ "captchaProvider": "TURNSTILE", "captchaSiteKey": "0x4AAAA…" }` (`captchaProvider` `TURNSTILE` ou `NONE`; com `NONE`, `captchaSiteKey` omitido). Sem limite de pedidos.
- **`GET /api/v1/public/verifications/{token}`** (`verifyCertificateToken`) — do QR. Sem CAPTCHA (o código tem 128 bits e não se adivinha). `{token}` que não cumpre `^[A-Za-z0-9_-]{22}$` → 200 `NOT_FOUND` sem consultar a BD (mas grava o registo e conta para o limite).
- **`GET /api/v1/public/verifications?plate={matrícula}`** (`verifyPlate`) — cabeçalho `X-Captcha-Token` obrigatório quando o fornecedor não é `NONE`.
  - Sem cabeçalho → 400 `CAPTCHA_REQUIRED`; inválido → 400 `CAPTCHA_INVALID`; fornecedor indisponível → 503 `CAPTCHA_UNAVAILABLE`. A verificação do CAPTCHA é feita **antes** de ler a matrícula.
  - `plate` em falta ou que o `PlateParser` não aceita → 400 `VALIDATION_ERROR`, `errors[0] = { field: "plate", code: "INVALID_PLATE" }` (não grava registo).

Resposta pública (`PublicVerificationResponse`):

```json
{
  "status": "VALID",
  "plateMasked": "ABC-***-MC",
  "insurerName": "Seguradora Demo",
  "validFrom": "2027-02-10T08:31:00Z",
  "validTo": "2028-02-10T08:31:00Z",
  "coverageType": "MTPL_ONLY",
  "certificateStatus": "CURRENT",
  "checkedAt": "2027-03-01T09:15:02Z"
}
```

- `status = NOT_FOUND` → só `status`, `plateMasked` (só nas consultas por matrícula) e `checkedAt`.
- `certificateStatus` (`CURRENT` ou `REVOKED`) só nas consultas por código: diz se o certificado mostrado (papel ou ecrã) ainda é o actual; o `status` é sempre o da apólice **agora**.
- Nunca: nome, telefone, documento, NUIT ou morada do tomador; número da apólice ou do certificado.

**Polícia** (âmbito `ORG`, `@PreAuthorize("hasAuthority('verification:police')")`; sem CAPTCHA):

- **`GET /api/v1/police/verifications?plate=…`** (`verifyPlateAsPolice`)
- **`GET /api/v1/police/verifications/{token}`** (`verifyCertificateTokenAsPolice`)

  Resposta `PoliceVerificationResponse` = a pública mais `policyNumber`, `certificateNumber`, `vehicleMake`, `vehicleModel` (para o agente confirmar que a matrícula corresponde ao veículo). Continua sem dados pessoais do tomador.

- **`GET /api/v1/police/check-history`** (`listMyPoliceChecks`) — filtros `from`, `to` (datas `yyyy-MM-dd`, `Africa/Maputo`, inclusivas; por defeito os últimos 30 dias); paginação, ordenação por `checkedAt desc` → página de `{ id, checkedAt, subjectType, plateMasked, result }`. Só as do próprio agente (RLS + filtro por `checker_user_id` no serviço).

### 3. Cálculo do resultado (`VerificationService`)

1. Consulta pela cache (secção 6) → `PolicyApi.findLatestByPlate(plate.value(), agora)` ou `PolicyApi.findByCertificateToken(token)`.
2. Sem apólice → `NOT_FOUND`.
3. Com apólice, `CoverStatus` calculado com `agora` a partir do `PolicyCoverView` (mesma tabela do S6-01, secção 4), e convertido:

| `CoverStatus` | `status` da resposta |
| --- | --- |
| `COVERED` | `VALID` |
| `NOT_STARTED` | `NOT_YET_VALID` |
| `ENDED`, `LAPSED` | `EXPIRED` |
| `SUSPENDED` | `SUSPENDED` |
| `CANCELLED` | `CANCELLED` |

4. `insurerName` = `OrganizationApi.insurerProfile(insurerId)` → `displayName` (cache de 10 minutos).
5. `plateMasked` = `Matricula.restore(...)`/`PlateParser` sobre a matrícula da apólice (ou a pedida, em `NOT_FOUND`) → `masked()`.
6. Grava `check_log` (regra 4) numa transacção própria e incrementa `moseguros_verification_checks_total{checker_type, subject_type, result}`.
7. O estado é calculado em cada pedido: um certificado de uma apólice anulada mostra `CANCELLED` mesmo que o papel diga válido.

### 4. Regras do registo

1. `subject_hash = HMAC-SHA256(chave, subject_type + ":" + valor)`, em hexadecimal minúsculo; `valor` = matrícula formatada (`Matricula.value()`) ou o código tal como veio.
2. A chave é `moseguros.verification.hash-key` (variável `MOSEGUROS_VERIFICATION_HASH_KEY`, Base64 de 32 bytes). `application-local.yml` e `application-test.yml` têm uma chave fixa com `# chave só para desenvolvimento`; sem chave, fora desses perfis, a aplicação não arranca.
3. Um SHA-256 simples não chega: o espaço de matrículas é pequeno e daria para inverter por força bruta.
4. Os logs da aplicação levam só `plateMasked`, `subjectType`, `result` e o `subject_hash` truncado a 12 caracteres; nunca a matrícula completa nem o código.
5. `ip_prefix`: IPv4 → os três primeiros octetos + `.0/24` (`41.220.15.0/24`); IPv6 → os primeiros 48 bits + `::/48`. O IP completo usa-se só em memória, para o limite de pedidos.

### 5. IP do cliente e limites de pedidos

**IP do cliente:** `shared.web.ClientIpResolver.resolve(request)` do S0-03 (decisão D15), sem alterações: usa o primeiro valor de `X-Forwarded-For` só quando o endereço remoto está em `moseguros.web.trusted-proxies`; senão o endereço remoto.
- Por defeito a lista está vazia; esta tarefa põe em `application-local.yml` e no compose `127.0.0.1/32,::1/128,172.16.0.0/12,10.0.0.0/8,192.168.0.0/16` (o nginx da web, S0-07).
- Como o `ClientIpResolver` usa o **primeiro** valor, o nginx tem de **substituir** o cabeçalho que vem do cliente, e não acrescentar-lhe: `proxy_set_header X-Forwarded-For $remote_addr;` (e `X-Real-IP $remote_addr`). Com `$proxy_add_x_forwarded_for`, o primeiro valor seria o que o cliente escreveu, e qualquer pessoa contornaria o limite por IP. Em staging e produção, o *proxy* de entrada à frente do nginx segue a mesma regra (S6-08).

**`VerificationRateLimiter`** (Bucket4j em memória; *buckets* numa cache Caffeine que os expira 10 minutos depois do último uso):

| Quem | Chave | Limite (propriedade) | Abrange |
| --- | --- | --- | --- |
| público | IP | `moseguros.verification.rate-limit.public-per-minute: 60` | `verifyCertificateToken` e `verifyPlate`, juntos |
| polícia | `user_id` | `moseguros.verification.rate-limit.police-per-minute: 300` | os três endpoints da polícia |

- Recarga gradual (`refillGreedy`) com capacidade igual ao limite.
- Excedido → 429 `RATE_LIMITED` com a propriedade `retryAfterSeconds` e o cabeçalho `Retry-After`; métrica `moseguros_verification_rate_limited_total{checker_type}`. O pedido recusado não grava `check_log`.
- O limite conta antes do CAPTCHA (um CAPTCHA errado também gasta um pedido).
- O limite é por instância; com N instâncias o limite efectivo é N × 60. Aceitável até ao Sprint 12 (revisão com os testes de carga).

### 6. Cache (`PolicyLookupCache`)

- Duas caches Caffeine: por matrícula formatada e por código; `expireAfterWrite` de `moseguros.verification.cache-ttl: PT60S`, `maximumSize` 50 000 cada. Guardam o `Optional<PolicyCoverView>` (também os vazios). O `status` não fica em cache: é sempre calculado com `agora` (secção 3).
- `PolicyCacheListener` (`@ApplicationModuleListener` de `PolicyIssued`, pacote `application`; não acede à BD, por isso não precisa de `@RunAsSystem`): retira da cache a entrada da matrícula da apólice.
- O S7 acrescenta o mesmo para `PolicyStatusChanged`. Noutras instâncias da aplicação a entrada antiga dura no máximo 60 s; é isto que garante a regra do S7 "a verificação pública reflecte a anulação no minuto seguinte".

### 7. CAPTCHA (`shared.captcha`, modelo §7)

```java
public interface CaptchaVerifier {
  CaptchaProvider provider();                       // TURNSTILE ou NONE
  Optional<String> siteKey();
  CaptchaResult verify(String token, String clientIp); // VALID, INVALID, UNAVAILABLE
}
```

- Escolha por `moseguros.captcha.provider: none | turnstile`. `none` → `AlwaysValidCaptchaVerifier` (devolve `VALID` sempre; o cabeçalho deixa de ser exigido). Com o perfil `prod`, `none` faz a aplicação não arrancar; com `staging`, regista `WARN` no arranque.
- **`TurnstileCaptchaVerifier`**: `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` (`application/x-www-form-urlencoded`: `secret`, `response`, `remoteip`), com `RestClient`, timeout 3 s e circuit breaker Resilience4j `captcha`.
  - `success = true` e `hostname` em `moseguros.captcha.turnstile.allowed-hostnames` → `VALID`.
  - `success = false` ou outro `hostname` → `INVALID`.
  - Timeout, erro de rede, 5xx ou circuito aberto → `UNAVAILABLE` (falha fechada: sem CAPTCHA confirmado não há consulta por matrícula).
  - `siteKey` em `moseguros.captcha.turnstile.site-key`; o segredo no cofre, em `secret/platform/captcha/turnstile` (`SecretStore.get`), nunca no `application.yml` nem nos logs.
- Métrica `moseguros_captcha_results_total{result}`.
- Nos testes, um `CaptchaVerifier` falso do perfil `test` devolve `INVALID` para o token `"invalid"`, `UNAVAILABLE` para `"down"` e `VALID` para os outros. `TurnstileCaptchaVerifierTest` usa um servidor HTTP falso (WireMock ou `MockRestServiceServer`).

- [ ] `PublicVerificationIT` (Testcontainers):
  - código de uma apólice activa → `VALID` com `insurerName`, datas, `coverageType`, `certificateStatus = CURRENT`;
  - apólice terminada → `EXPIRED`; apólice com início futuro → `NOT_YET_VALID`;
  - certificado `REVOKED` de uma apólice activa → `status = VALID`, `certificateStatus = REVOKED`;
  - código desconhecido e código com formato errado → `NOT_FOUND`;
  - por matrícula, com CAPTCHA válido → `VALID`; sem cabeçalho → `CAPTCHA_REQUIRED`; `"invalid"` → `CAPTCHA_INVALID`; `"down"` → 503 `CAPTCHA_UNAVAILABLE`; matrícula inválida → 400 `INVALID_PLATE`;

  - depois de `PolicyIssued`, uma matrícula antes `NOT_FOUND` passa a `VALID` sem esperar pelo fim da cache;
  - cada consulta grava uma linha em `check_log` com `subject_hash` e sem a matrícula em claro (consulta SQL directa a todas as colunas).
- [ ] `PoliceVerificationIT`: 401 sem token; 403 para cliente e para staff sem `verification:police`; agente → resposta com `policyNumber` e `vehicleMake`, sem CAPTCHA; `listMyPoliceChecks` mostra só as consultas do próprio agente (as de outro agente da mesma organização não aparecem).
