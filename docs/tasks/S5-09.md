## Contexto

ADR-004 e ADR-007. Os pagamentos por entidade e referência (rede Ponto24) são confirmados pelos ficheiros de movimentos (MEPS ou BMEPS, `docs/specs/interbancos/`) que o banco deposita no SFTP de cada seguradora. Cada seguradora indica o servidor SFTP e as credenciais (S5-01); a frequência de envio é combinada entre a seguradora e o banco, por isso o worker fica **sempre em escuta**: lê cada fonte continuamente, com um intervalo curto configurável, para reflectir o pagamento o mais depressa possível. Os nomes dos ficheiros podem ser ignorados, mas **um ficheiro nunca é lido nem processado duas vezes** (decisões do proprietário do produto, 18/11/2026). Um executável à parte, o `payment-file-worker`, lê-os, valida-os e publica cada pagamento no RabbitMQ. Fica fora do backend para isolar as credenciais SFTP e o processamento de ficheiros da API pública. Tem projecto Maven, base de dados (schema `payment_worker`) e histórico Flyway próprios (modelo transversal §2 e §6).

Esta tarefa cria também, no backend, o **token de serviço** (*client credentials*) com que o worker se autentica e o endpoint interno que lhe dá as fontes activas. Implementa o contrato dos parsers (`PaymentFileParser`, `ParserRegistry`, `FileValidator`; o S5-08 §1 reproduz o contrato). Os leitores reais `MEPS` e `BMEPS` e o simulador `ponto24-mock` entram no S5-08. Até ao S5-08, os testes desta tarefa usam um `TestStubParser` só em `src/test` (formato `TEST_STUB`, uma linha `H;<entidade>;<id do ficheiro>;<id do anterior ou vazio>`, linhas `D;<referência>;<centavos>;<yyyy-MM-dd'T'HH:mm:ss>`, `T;<n>;<total>`).

**Pressupõe:**
- S5-06: *reactor* Maven na raiz (comandos `./mvnw -B -pl <módulo> -am verify` na raiz, decisão D18), RabbitMQ 4.1 (decisão D19), `payment-contracts` (`ReferencePaymentReceived`, `PaymentFileProcessed`, `PaymentFileRejected`, `PaymentSourcePolled`, `FileSourceDescriptor`, `FileSourceList`, `MessageIds`, `PaymentsTopology`, `MessageHeaders`, `PollErrorCode`, `FileRejectionReason`), serviços `rabbitmq`, `sftp`, `vault` no compose, imagens em `scripts/images.txt`.
- S5-01: configuração `BANK_REFERENCE` (`entity`, `fileFormat`, `bmepsCompanyId`, `bmepsProfileId`, `sftp.*` com `moveAfterProcessing` e `hostKeyFingerprint`; sem frequência nem fuso; segredos `sftp.password`, `sftp.privateKey`, `sftp.passphrase` no Vault em `secret/insurers/{insurerId}/payments/BANK_REFERENCE/{campo}`, dados `{ "value": … }`), `PaymentSystemLookups`, dados de demonstração.
- S5-08 §1 (contrato que esta tarefa cria): `PaymentFileParser` (`format()`, `parse`), `ParseContext`, `FileHeader` (com `formatFileId` e `previousFormatFileId`), `ParsedRecord`, `FileTrailer`, `ParserRegistry`, `FileValidator`.
- S5-02/S5-07: `payment.reference_payment` (`status`, `insurer_id`), para o endpoint interno saber que fontes inactivas ainda têm referências por pagar.
- S1-02: chaves RS256 do backend, `JwtClaimsConverter` (autoridades a partir de `permissions`), `TenantContextFilter` (tipo de token desconhecido → `Scope.NONE`), `BearerTokenResolver` dos caminhos públicos.
- S1-01: padrão dos dois utilizadores de BD (dono para o Flyway, utilizador sem privilégios para a aplicação) e `init-roles.sql`.

## Objectivo

Com `docker compose up`, o worker obtém um token de serviço, lê as fontes do backend e consulta cada uma de minuto a minuto (`poll-interval`); um ficheiro de teste colocado em `inbound` do SFTP da Seguradora Demo é lido, validado, publicado registo a registo no RabbitMQ com *publisher confirms* e movido para `processed`; o mesmo ficheiro outra vez (com o mesmo ou outro nome, mudado de pasta ou não) não publica nada de novo; um ficheiro com rodapé errado vai para `error`; duas instâncias nunca tratam a mesma fonte ao mesmo tempo.

## Especificação

### 1. Token de serviço no backend

**Clientes de serviço** (configuração; não há tabela):

```yaml
moseguros:
  security:
    service-clients:
      payment-file-worker:
        secret: ${MOSEGUROS_SERVICE_CLIENT_PAYMENT_FILE_WORKER_SECRET:}
        scopes: [ "payments:file-sources" ]
    jwt:
      internal-audience: moseguros-internal
```

- `application-local.yml`: `secret: local-worker-secret` (comentário `# só desenvolvimento`); `application-test.yml`: valor fixo de teste.
- Fora de `local` e `test`: segredo vazio → o cliente fica desactivado (`WARN` no arranque); segredo com menos de 32 caracteres → a aplicação não arranca. Em staging e produção o valor vem do cofre de segredos (S6-08).

**`POST /internal/v1/auth/token`** (`issueServiceToken`, tag `Identity`, fora do `api/openapi.yaml`). Segue o RFC 6749 §4.4, para o worker poder usar um cliente OAuth2 normal; por isso os erros usam o formato do RFC 6749 (`{"error": "…"}`) e **não** `application/problem+json` (excepção a `AGENTS.md` §4, só neste endpoint).

- Pedido: `Content-Type: application/x-www-form-urlencoded`, `Authorization: Basic base64(clientId:clientSecret)`, corpo `grant_type=client_credentials&scope=payments:file-sources` (`scope` opcional; ausente = todos os do cliente).
- Resposta 200: `{ "access_token": "<jwt>", "token_type": "Bearer", "expires_in": 900, "scope": "payments:file-sources" }`.
- Erros: cliente desconhecido, desactivado ou segredo errado → 401 `{"error":"invalid_client"}` com `WWW-Authenticate: Basic realm="moseguros-internal"`; `grant_type` diferente → 400 `unsupported_grant_type`; âmbito não permitido → 400 `invalid_scope`; corpo mal formado → 400 `invalid_request`.
- Comparação do segredo em tempo constante (`MessageDigest.isEqual` sobre SHA-256 de cada lado). Falhas registadas em `WARN` com o `clientId`, nunca o segredo.
- Token: JWT RS256 com a chave do S1-02; `iss` igual; `aud = moseguros-internal`; `sub = payment-file-worker`; `type = SERVICE`; `scope = "payments:file-sources"`; `permissions = ["payments:file-sources"]`; `exp = iat + 15 min`; `jti` UUID v7.

**Validação (`InternalSecurityConfig`)**: `SecurityFilterChain` com `@Order(1)` e `securityMatcher("/internal/**")`:
- `/internal/v1/auth/token` sem autenticação JWT (a autenticação Basic é verificada no controlador);
- o resto exige um JWT validado por um `NimbusJwtDecoder` com a mesma chave pública, `iss`, `exp` e **`aud = moseguros-internal`**, e `type = SERVICE` (validador próprio); autoridades pelo `JwtClaimsConverter` do S1-02.
- A cadeia do S1-02 (`/api/**`) continua a exigir `aud = moseguros-api`: um token de serviço em `/api/**` dá 401, e um token de utilizador em `/internal/**` dá 401.
- `TenantContextFilter`: `type = SERVICE` → `Scope.NONE` (já é o caso "outro" do S1-02).
- `/internal/**` não é servido pelo nginx da web (só faz *proxy* de `/api/`). Em staging e produção o *proxy* de entrada também não o encaminha (escrever no `infra/README.md`; S6-08).

**`GET /internal/v1/payment-file-sources`** (`listInternalFileSources`, `@PreAuthorize("hasAuthority('payments:file-sources')")`) → 200 `FileSourceList` (S5-06):
- `PaymentSystemLookups.activeFileSources()` (`@RunAsSystem`): todas as linhas `BANK_REFERENCE` com `enabled = true`, **mais** as inactivas cuja seguradora ainda tem referências `ACTIVE` (`exists (select 1 from payment.reference_payment r where r.insurer_id = m.insurer_id and r.status = 'ACTIVE')`: o banco continua a aceitar pagamentos dessas referências e os ficheiros têm de ser lidos), de todas as seguradoras; `enabled` no descritor diz qual é o caso;
- `sourceId` = `insurer_payment_method.id`; `version` = `version` da linha; `secretRefs` = os caminhos de `secret_refs` (nunca os valores);
- uma linha cujo `settings` não cumpra o schema completo é omitida e regista `ERROR` (não deveria acontecer: o `enable` valida).

### 4. Fontes e agendamento

- **`ServiceTokenProvider`**: pede o token (secção 1) com `RestClient` e Basic; guarda-o até `expires_in − 60 s`; um 401 de um pedido autenticado força um token novo e repete uma vez.
- **`BackendSourceClient.fetch()`**: `GET {backend-base-url}/internal/v1/payment-file-sources` → `FileSourceList`. Timeout 10 s.
- **`SourceRegistry`**: no arranque e a cada `sources-refresh-interval`:
  - fonte nova, ou com `version` diferente → (re)agenda no `ThreadPoolTaskScheduler` (`poolSize 4`, prefixo `source-`) com `scheduleWithFixedDelay(…, poll-interval)` (a leitura seguinte começa `poll-interval` depois do fim da anterior; a primeira logo a seguir ao agendamento). Não há frequência por fonte: a frequência real é a que o banco combinou com a seguradora, e a plataforma fica sempre em escuta (ADR-007);
  - fonte que deixou de vir → cancela o agendamento;
  - backend inaccessível → mantém os agendamentos actuais, `WARN`, tenta no ciclo seguinte; no arranque sem resposta tenta a cada 30 s.
- Cada execução agendada corre `SourcePoller.poll(descriptor)` dentro de `LockingTaskExecutor.executeWithLock` com o nome **`source:{sourceId}`**, `lockAtMostFor` e `lockAtLeastFor` das propriedades. Sem o *lock* → não faz nada (`DEBUG`).

### 5. Uma leitura (`SourcePoller.poll`)

1. `startedAt`. Parser para `fileFormat` no `ParserRegistry`; não há → resultado `ERROR` `UNSUPPORTED_FORMAT` (passo 6).
2. Segredos com o `SecretReader` (`VaultSecretReader`: KV v2, `secret/data/<resto do caminho>`, campo `value`). Em falta → `ERROR` `SECRET_NOT_FOUND`.
3. Sessão SFTP (`DefaultSftpSessionFactory` do Spring Integration; *timeout* 30 s; palavra-passe ou chave privada com *passphrase*).
   - Chave do servidor: `FingerprintHostKeyVerifier` compara o SHA-256 da chave apresentada (formato `SHA256:<base64 sem =>`) com `sftp.hostKeyFingerprint`; diferente → `SFTP_HOST_KEY_MISMATCH`. Sem impressão digital: aceita só com `allow-unknown-host-keys = true` (`local`/`test`); senão `SFTP_HOST_KEY_MISMATCH`.
   - Autenticação recusada → `SFTP_AUTH_FAILED`; ligação impossível → `SFTP_UNREACHABLE`; `inboundDir` inexistente → `SFTP_DIRECTORY_NOT_FOUND`.
4. Lista `inboundDir`: só ficheiros regulares cujo nome corresponde a `filePattern` (defeito `*`; `FileSystems.getDefault().getPathMatcher("glob:" + filePattern)`), ignorando os que acabam em `.part` ou começam por `.` (ficheiros a meio de envio), por ordem de data de modificação e depois de nome, no máximo `max-files-per-run`. Para cada um, `FileProcessor.process` (secção 6). Um erro num ficheiro não pára os seguintes.
5. Apaga os ficheiros temporários de `work-dir`.
6. Publica `PaymentSourcePolled` (`outcome` `OK` se não houve erro de fonte nem de publicação; ficheiros rejeitados por conteúdo **não** tornam a leitura `ERROR`), com as contagens. Falha a publicar este resumo → `WARN`, sem mais efeitos.

### 6. Um ficheiro (`FileProcessor.process`)

| Passo | O que faz |
| --- | --- |
| a0 | Já tratado sem descarregar? Existe `processed_file` desta fonte com o mesmo `file_name`, `size_bytes` e `remote_mtime` em `DONE` ou `ERROR` → com `moveAfterProcessing` tenta de novo mudar de pasta (`processedDir` ou `errorDir`) e termina; sem mudança de pasta, termina logo (`DEBUG`). Assim um SFTP só de leitura não faz descarregar o mesmo ficheiro a cada minuto |
| a | Tamanho na listagem > `max-file-size` → move para `errorDir` (se `moveAfterProcessing`) e publica `PaymentFileRejected` `FILE_TOO_LARGE` (`sha256` = SHA-256 de `fileName + "|" + size + "|" + mtime`, porque o ficheiro não é descarregado), uma só vez por esse `sha256` |
| b | Descarrega para `work-dir` e calcula o SHA-256 |
| c | Procura `processed_file (source_id, sha256)` (**deduplicação por conteúdo**, qualquer que seja o nome): `DONE` → só move para `processedDir` (se `moveAfterProcessing`; foi posto outra vez ou a mudança anterior falhou) e termina, **sem publicar nada**; `ERROR` → move para `errorDir` (se `moveAfterProcessing`) e termina, **sem publicar nada** (um erro de conteúdo repete-se sempre; um ficheiro corrigido tem outro SHA-256); `PARSED` ou `PUBLISHED` → retoma no passo g; não existe → insere `RECEIVED` com `remote_mtime` |
| d | `parser.parse(...)` com `ParseContext(entity, bmepsCompanyId, bmepsProfileId, Africa/Maputo, fileName)`; excepção → `ERROR` com o código da excepção |
| e | `FileValidator` (S5-08 §1); falha → `ERROR` com o código |
| e2 | **Deduplicação pelo identificador do ficheiro no formato:** grava `file_format`, `format_file_id`, `previous_format_file_id`. Já existe outro `processed_file` desta fonte, fora de `ERROR`, com o mesmo `format_file_id` (e outro SHA-256) → `ERROR` `DUPLICATE_FILE_ID` (o banco reenviou o mesmo ficheiro com conteúdo diferente: não se processa sem uma pessoa ver; `alert=PAYMENT_FILE_DUPLICATE_ID`) |
| e3 | **Sequência** (só aviso, nunca rejeita): MEPS com `previous_format_file_id` diferente do `format_file_id` do último ficheiro `DONE` desta fonte (e já houve algum) → `WARN` `alert=PAYMENT_FILE_SEQUENCE_GAP`; BMEPS com ID do ficheiro diferente do último + 1 → o mesmo. A seguradora pede ao banco o ficheiro em falta |
| f | Numa transacção: grava os `file_record` (`message_id` com `MessageIds`, S5-06: por ficheiro e linha), `record_count`, `total_amount`, `status = PARSED` |
| g | Publica, por ordem de `line_no`, cada registo com `published_at is null` (secção 7). Uma falha pára este ficheiro: fica `PARSED` e a leitura termina com `PUBLISH_FAILED`; a leitura seguinte retoma só os que faltam |
| h | Todos confirmados → `status = PUBLISHED` → com `moveAfterProcessing`, move o ficheiro para `processedDir` (`rename`; se já existir um com o mesmo nome, acrescenta `.<yyyyMMddHHmmss>`) → publica `PaymentFileProcessed` → `status = DONE`, `completed_at` |
| ERROR | `error_code`, `error_message` (sem conteúdo do ficheiro além do número da linha), move para `errorDir` (se `moveAfterProcessing`; mesma regra de nomes) e publica `PaymentFileRejected` com `reason`, `detail`, `lineNo` e `formatFileId` (se já lido). Uma vez por SHA-256 |

- Se a mudança de pasta falhar no passo h, o ficheiro continua em `inboundDir` com `status = PUBLISHED`; na leitura seguinte o passo c encontra-o, não publica registos de novo e volta a tentar o passo h. O `PaymentFileProcessed` repetido tem o mesmo `messageId` (o backend ignora a repetição, S5-10).
- Um ficheiro com zero registos e rodapé a zeros é válido: `DONE` e `PaymentFileProcessed` com `recordCount = 0`.
- **Nunca duas vezes:** um ficheiro só gera `ReferencePaymentReceived` uma vez, seja reposto com o mesmo nome, com outro nome, ou deixado em `inboundDir` (SFTP só de leitura): pelo SHA-256 (passos a0 e c) e pelo `format_file_id` (passo e2). Se, por um erro técnico, uma mensagem for republicada, o backend ignora-a pelo `messageId` (S5-10).

### 7. Publicação (`RecordPublisher`)

- Declara o exchange `payments.events` (`topic`, durável), igual ao do backend (S5-06). Não declara filas.
- Cada mensagem: `RabbitTemplate.convertAndSend(exchange, routingKey, message, postProcessor, correlationData)` com as propriedades de `MessageHeaders` (S5-06); chave `reference.paid.{insurerId}` (ou a do tipo); espera por `correlationData.getFuture()` até `publish-confirm-timeout`.
- Confirmado (`ack`) e não devolvido → `published_at = agora` (actualizações em lotes de 100). `nack`, devolvida (`mandatory`, sem fila ligada) ou sem resposta no tempo → falha (secção 6, passo g).
- O worker nunca considera um registo publicado sem `ack`.

### 8. Métricas, saúde e logs

- Micrometer: `worker.files` (contador; etiquetas `source`, `outcome` = `done`/`error`/`skipped`), `worker.records.published` (`source`), `worker.polls` (`source`, `outcome`), `worker.last.success` (gauge com o *epoch* em segundos da última leitura `OK`, por `source`).
- `/actuator/health`: base de dados e RabbitMQ (automáticos) e um indicador `sources` (`UP` com o número de fontes agendadas; `DOWN` se o backend não respondeu há mais de 15 min).
- Logs: `sourceId`, `insurerId`, nome do ficheiro, os primeiros 12 caracteres do SHA-256, contagens, códigos de erro. Nunca segredos, token, conteúdo de linhas nem referências completas em `INFO` (referências em `DEBUG`).

## Questões

- 02/11/2026 — **Operação do SFTP de cada seguradora:** quem coloca os ficheiros do banco no SFTP, com que frequência, se o mesmo ficheiro pode ser reenviado e quanto tempo fica no servidor (riscos do plano). **Resolvida em 18/11/2026** pelo proprietário do produto: cada seguradora indica o servidor SFTP e as credenciais onde o banco deposita os ficheiros (`.txt`); a frequência é combinada entre a seguradora e o banco; o worker fica sempre em escuta; os nomes podem ser ignorados; um ficheiro nunca é processado duas vezes.
- 18/11/2026 — Decisão (a validar): **intervalo de leitura global** (`moseguros.worker.poll-interval`, defeito 60 s) em vez de um `pollCron` por fonte (ADR-007). Com dezenas de seguradoras, 60 s e 4 *threads* chegam; se um banco limitar ligações, aumenta-se o intervalo. **Não bloqueia.**
- 18/11/2026 — Decisão (a validar): **mesmo identificador de ficheiro com outro conteúdo é rejeitado** (`DUPLICATE_FILE_ID`) e fica visível como ficheiro rejeitado (S5-12); nunca se processa sozinho. **Não bloqueia.**
- 18/11/2026 — Decisão (a validar): **falhas na sequência dos ficheiros só geram aviso** (`PAYMENT_FILE_SEQUENCE_GAP`): o ficheiro que chegou é processado na mesma; o que falta é pedido ao banco pela seguradora. **Não bloqueia.**
- 18/11/2026 — Decisão (a validar): **um ficheiro com erro de conteúdo não é tentado de novo** com o mesmo SHA-256 (antes: `attempts + 1` a cada leitura). Com SFTP só de leitura, tentar de novo a cada minuto publicaria a mesma rejeição sem fim. **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **base do branch.** O branch nasce do `task/S5-06-infra-pagamentos` (branches empilhados), mas o endpoint interno precisa do S5-01 (`insurer_payment_method`, `PaymentSystemLookups`) e do S5-02 (`payment.reference_payment`), que não estão no S5-06. Juntei o `task/S5-02-nucleo-pagamentos` (que já contém o S5-01) com um *merge* (sem reescrever commits); os conflitos foram só no `backend/pom.xml` (dependências dos dois lados) e no `docs/STATUS.md`. **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **ordem da rejeição.** A tabela diz "`ERROR` … move … publica `PaymentFileRejected`". O worker publica primeiro o `PaymentFileRejected` e só com o `ack` grava `ERROR` e move o ficheiro: se a publicação falhar o ficheiro fica como estava (`RECEIVED`) e a leitura seguinte repete a rejeição (o erro de conteúdo é determinístico), em vez de a rejeição se perder para sempre ("uma vez por SHA-256" mantém-se depois do `ack`). **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **`poll-interval` de 2 s nos testes.** A ficha diz que `poll-interval < PT10S` não arranca "em todos os perfis" e pede um teste com 2 s. O `StartupChecks` só aceita menos de 10 s com o perfil `test` **e** `moseguros.worker.test-allow-short-poll-interval=true` (só os testes de integração a põem); com qualquer outro perfil a propriedade não tem efeito. **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **ficheiro `PUBLISHED` já mudado de pasta.** Se o `PaymentFileProcessed` falhar depois do `rename` (passo h), o ficheiro já não está em `inboundDir` e o passo c nunca o voltaria a ver. No início de cada leitura (com `moveAfterProcessing`), os `PUBLISHED` da fonte que já não estão em `inboundDir` são terminados (`PaymentFileProcessed` com o mesmo `messageId` e `DONE`). **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **códigos de erro não previstos.** Vault em baixo → `INTERNAL_ERROR` (o `PollErrorCode` não tem um código para o cofre; `SECRET_NOT_FOUND` só quando falta o caminho ou o valor); falha a descarregar um ficheiro a meio → a leitura termina `ERROR` `SFTP_UNREACHABLE` mas os ficheiros seguintes são tentados; excepção inesperada num ficheiro → `INTERNAL_ERROR`. Um ficheiro em `RECEIVED` (o worker parou a meio) é lido de novo (`attempts + 1`). **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **`TEST_STUB` e a sequência.** O critério "`H;…;3;1` depois de `1` → `PAYMENT_FILE_SEQUENCE_GAP`" só dá falha com a regra do BMEPS (ID + 1); com a do MEPS (A007 = último) o `1` estaria certo. O `TestStubParser` põe o ID numérico também em `bmepsFileSequence` e o worker aplica as duas regras quando o cabeçalho traz as duas informações (MEPS: só a do A007; BMEPS: só a do ID). Nas mensagens dos testes `fileFormat` é `TEST_STUB` (fora do `enum` do schema, só nos testes). **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **downloads contados no servidor.** O `atmoz/sftp` dos testes usa um `sshd_config` próprio (`src/test/resources/sftp/sshd_config`, `internal-sftp -l INFO`) para o critério "o servidor SFTP de teste regista um só download" (linhas `open "…" flags READ` no log do contentor); o worker conta também `worker.downloads` (métrica a mais, para operação). **Não bloqueia.**
- 18/11/2026 — Decisão do agente (a validar): **pormenores do contrato.** As mensagens não levam o cabeçalho `__TypeId__` do Spring AMQP (o tipo vai na propriedade `type`, `MessageHeaders`); o `JwtProperties` ganhou `internal-audience`; o Spring Modulith trata o pacote `mz.co.moseguros.paymentcontracts` como módulo e o `ModularityTest` passou a aceitá-lo como dependência do `payment` (é a biblioteca partilhada do S5-06, não um módulo). **Não bloqueia.**
