## Contexto

No pagamento por entidade e referência, cada seguradora tem a sua entidade na rede SIMO e cada pagamento tem uma referência própria, gerada por um algoritmo da SIMO. O plano e o ADR-004 dizem que esse algoritmo é fornecido pelo proprietário do produto. **Não se inventa algoritmo** (`AGENTS.md` §9 regra 8; modelo transversal §9).

Esta ficha tem duas partes:

- **§2 e §3 — contrato, gerador fake e recusa de arranque.** Não estão bloqueadas: são implementadas pelo **S5-02**, que remete para aqui. Permitem que o resto do sprint (S5-02, S5-10, S5-11, S5-12) funcione em `local` e `test`.
- **§4 — o gerador real.** É o que esta tarefa entrega quando for desbloqueada.

**Pressupõe:** S5-01 (`settings.entity`, `settings.referenceAlgorithm`, `settings.referenceValidityHours`, `BANK_REFERENCE_NOT_AVAILABLE`); S5-02 (`BankReferenceGateway`, `payment.reference_payment` com `unique (entity, reference) where status = 'ACTIVE'`, `PaymentSystemLookups`).

## Objectivo

Quando desbloqueada: com `referenceAlgorithm` real, `BankReferenceGateway` gera referências exactamente iguais às dos exemplos fornecidos pela SIMO, e a aplicação passa a arrancar em staging e produção com `BANK_REFERENCE` activo.

## 1. O que pedir ao proprietário do produto (antes de escrever código)

Quem chegar a esta tarefa **pára** e envia este pedido ao proprietário do produto (registar a data do pedido em "Questões"):

1. **O algoritmo**, por escrito, de fonte oficial (SIMO ou o banco da seguradora), com:
   - as entradas: número de entidade, montante, data-limite, número sequencial ou identificador do pagamento, outros campos;
   - o comprimento da referência e se tem zeros à esquerda;
   - os dígitos de controlo: como se calculam (pesos, módulo, ordem dos campos) e onde ficam;
   - se a referência codifica o montante e/ou a data-limite (e, se sim, se o banco recusa um montante diferente);
   - se uma referência pode ser reutilizada, e ao fim de quanto tempo;
   - se há versões do algoritmo e como se identificam.
2. **Exemplos de entrada e saída**: pelo menos 10 pares válidos (incluindo montante máximo, montante com cêntimos, sequenciais com zeros à esquerda, mudança de ano) e pelo menos 3 referências **inválidas** (dígito de controlo errado), para os testes.
3. **Regras do banco/SIMO**: validade máxima de uma referência, montantes mínimo e máximo, se aceita pagamentos de montante diferente, se aceita pagamentos depois da data-limite.
4. **Entidade**: número de dígitos do número de entidade; se uma seguradora pode ter várias entidades.
5. Quem na SIMO ou no banco confirma que as referências geradas são aceites (contacto para um teste real em sandbox, se houver).

Até haver resposta, esta parte **não avança**. O resto do sprint continua com o gerador fake.

## 2. Contrato e gerador fake (implementados no S5-02)

Pacote `mz.co.moseguros.payment.application.reference` (interno ao `payment`):

```java
public interface ReferenceGenerator {
  String algorithm();                 // valor de settings.referenceAlgorithm, ex.: "FAKE_V0"
  boolean isFake();                   // true só no gerador fake
  GeneratedReference generate(ReferenceRequest request);
  boolean isValid(String entity, String reference);   // formato e dígitos de controlo
}
public record ReferenceRequest(
    String entity,          // settings.entity
    UUID intentId,
    String intentNumber,    // "PG-2027-0001234"
    Money amount,
    Instant validUntil,
    ZoneId zone,            // settings.timezone
    int attempt) {}         // 0, 1, 2… em caso de colisão com uma referência activa
public record GeneratedReference(String reference) {}
```

- O S5-07 pode **acrescentar** campos ao `ReferenceRequest` se o algoritmo real precisar (ex.: um sequencial por entidade); não muda os existentes.
- `ReferenceGeneratorRegistry`: mapa `algorithm → gerador`; dois com o mesmo nome → falha no arranque.

**`FakeReferenceGenerator`** — `@Profile({"local","test"})`, `algorithm() = "FAKE_V0"`, `isFake() = true`.

> **Formato inventado só para testes e desenvolvimento. Não tem nenhuma relação com o algoritmo SIMO e nunca pode ser usado com dinheiro real.** Escrever este aviso no Javadoc da classe.

- Referência = `"999"` + 6 dígitos, onde os 6 dígitos são `floorMod(intentId.getLeastSignificantBits() + attempt * 7919L, 1_000_000)` com zeros à esquerda. Ex.: `999004217`.
- `isValid` = `^999[0-9]{6}$`.
- Não depende do montante nem da data.
- Na web e na app a referência mostra-se em grupos de 3 dígitos (`999 004 217`), seja qual for o algoritmo.

**`UnavailableReferenceGenerator`** — fora de `local` e `test`, quando não há gerador real: `algorithm() = "UNAVAILABLE"`; `generate` lança `DomainException` `BANK_REFERENCE_NOT_AVAILABLE` (409).

## 3. Recusa de arranque e de activação (implementadas no S5-02)

- **`BankReferenceReadinessCheck`** (`ApplicationRunner`, `payment.application.reference`), só quando os perfis activos não incluem `local` nem `test`:
  - lê com `PaymentSystemLookups` todas as linhas `BANK_REFERENCE` com `enabled = true`;
  - se alguma tiver um `referenceAlgorithm` sem gerador real registado (ausente, `FAKE_*` ou só o `UnavailableReferenceGenerator`), **a aplicação não arranca**: lança uma excepção com a mensagem `BANK_REFERENCE activo para a seguradora <insurerId> sem gerador SIMO real (tarefa S5-07 bloqueada). Desactive o método ou implemente o S5-07.`
- **Activação** (`POST /insurer/payment-methods/BANK_REFERENCE/enable`, S5-01): fora de `local` e `test`, sem gerador real para o `referenceAlgorithm` → 409 `BANK_REFERENCE_NOT_AVAILABLE`.
- **Criação de intenção** `BANK_REFERENCE` com o `UnavailableReferenceGenerator` → 409 `BANK_REFERENCE_NOT_AVAILABLE` (segunda defesa).
- `BankReferenceReadinessCheckTest` (S5-02):
  - perfil `prod`, linha `BANK_REFERENCE` activa com `FAKE_V0` → o arranque falha com a mensagem acima;
  - perfil `prod`, linha inactiva → arranca;
  - perfil `local`, linha activa com `FAKE_V0` → arranca;
  - perfil `prod`, `enable` → 409.

### Especificação

- `SimoReferenceGenerator implements ReferenceGenerator`: `algorithm()` = identificador combinado com o proprietário do produto (ex.: `SIMO_V1`), `isFake() = false`, sem `@Profile` (activo em todos os ambientes).
- Implementa **exactamente** o algoritmo recebido. Qualquer ponto que o documento não esclareça vai para "Questões" e a tarefa pára nesse ponto.
- `isValid` verifica o comprimento e os dígitos de controlo do algoritmo. O S5-10 pode usá-lo para classificar mensagens com referências mal formadas como `UNKNOWN_REFERENCE`.
- Se o algoritmo precisar de um sequencial por entidade, usa `BusinessNumberGenerator` com um prefixo próprio (`SIMO`, ≤ 4 caracteres) ou uma sequência nova no schema `payment` numa migração `V20270115070x__payment_simo_sequence.sql`, conforme o que a resposta exigir (reinício anual ou não).
- Se o algoritmo codificar o montante, a regra `AMOUNT_MISMATCH` do S5-10 continua a aplicar-se (a plataforma não confia no banco para recusar).
