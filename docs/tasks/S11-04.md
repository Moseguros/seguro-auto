## Contexto

Sprint 11, parte "Relatórios e supervisão" (RF-22, RF-24): painéis de produção, sinistralidade, reclamações e cobranças da seguradora. ADR-006 e modelo §1.3: o módulo `reporting` **não usa APIs Java de outros módulos**; lê vistas materializadas no schema `reporting`, criadas pelas suas migrações sobre as tabelas dos outros schemas, renovadas de hora a hora, com um papel de BD só de leitura (`moseguros_reporting`). Esta tarefa cria o papel, as vistas materializadas de base, as vistas por seguradora, a renovação e os quatro painéis. O S11-05 acrescenta as vistas do regulador, os modelos de exportação e a área `/supervisao`.

**O PostgreSQL não aplica RLS a vistas materializadas.** Por isso o isolamento por seguradora faz-se com vistas normais `security_barrier` por cima delas (secção 3), e o papel de leitura só tem acesso a essas vistas. O serviço filtra também pela seguradora do `TenantContext` (ADR-002, duas camadas).

## Especificação

### 1. Papel só de leitura (`V202704150400`)

```sql
do $$ begin
  if not exists (select 1 from pg_roles where rolname = 'moseguros_reporting') then
    create role moseguros_reporting nologin;
  end if;
end $$;
-- a aplicação pode fazer SET ROLE para ele, mas não herda os seus privilégios
grant moseguros_reporting to moseguros_app with inherit false, set true;
revoke all on schema reporting from public;
grant usage on schema reporting to moseguros_reporting, moseguros_app;
```

- `moseguros_reporting` não tem nenhum privilégio noutros schemas, nem nas vistas materializadas `reporting.mv_*`. Só tem `select` nas vistas `reporting.v_*` (secção 3 e S11-05).
- As vistas materializadas e as vistas pertencem ao dono do Flyway. As vistas `v_*` lêem as `mv_*` com os privilégios do dono (comportamento normal das vistas no PostgreSQL).
- Em staging e produção a equipa de operações não tem de criar nada: a migração cria o papel.

### 2. Vistas materializadas de base (`V202704150400`)

Uma linha por entidade, **sem nomes, contactos, documentos, matrículas nem ids de pessoas**. Datas de negócio em `Africa/Maputo`. Cada uma tem `refreshed_at timestamptz` (= `now()` na renovação) e um índice único (obrigatório para `refresh … concurrently`).

| Vista | Chave única | Colunas |
| --- | --- | --- |
| `reporting.mv_insurer` | `insurer_id` | `insurer_id`, `insurer_name` (`coalesce(trade_name, legal_name)`), `insurer_short_code`, `insurer_status` |
| `reporting.mv_policy` | `policy_id` | `policy_id`, `insurer_id`, `product_id`, `product_name`, `product_type` (`policy.product_type`), `vehicle_category`, `vehicle_usage`, `province` (do perfil do titular), `channel` (`policy.channel`), `broker_org_id`, `status`, `payment_plan`, `period_no`, `issued_date` (`issued_at`), `start_date`, `end_date`, `issued_premium_amount` (`proposal.total_amount`: prémio da primeira anuidade), `issued_commercial_premium_amount` (`proposal.premium_breakdown.commercial.amount`), `current_premium_amount` (`policy.total_amount`, anuidade em curso, com endossos) |
| `reporting.mv_renewal` | `renewal_id` | `renewal_id`, `insurer_id`, `policy_id`, `product_type` (da apólice), `period_no`, `status`, `new_start_date`, `paid_date`, `premium_amount` (`total_amount`), `commercial_premium_amount` (`premium_breakdown->>'commercialPremiumAmount'`; `null` se a tarifação não o devolveu) — só `PAID` e `APPLIED` |
| `reporting.mv_instalment` | `instalment_id` | `instalment_id`, `insurer_id`, `due_date`, `amount`, `amount_due` (`amount − credited_amount`), `status` |
| `reporting.mv_payment` | `intent_id` | `intent_id`, `insurer_id`, `method`, `target_type`, `status`, `amount`, `created_at`, `succeeded_at`, `failed_at` |
| `reporting.mv_claim` | `claim_id` | `claim_id`, `insurer_id`, `product_type` (da apólice), `claim_type`, `status`, `late_report`, `occurred_at`, `reported_at`, `registered_at` (`claim.registered_at`), `liability_decided_at` (o primeiro `liability_decision.decided_at`), `paid_at` (o primeiro `indemnity_payment.paid_at` com estado `PAID`), `closed_at` (`claim.closed_at`), `paid_amount` (soma de `indemnity_payment` `PAID`), `reserve_amount` (a última `claim.reserve` por `set_at`; 0 se o estado for `PAID`, `CLOSED` ou `REJECTED`), `total_loss` (existe `settlement_offer` `TOTAL_LOSS` `ACCEPTED`) — só sinistros com estado ≠ `DRAFT` |
| `reporting.mv_complaint` | `complaint_id` | `complaint_id`, `insurer_id`, `category`, `subject_type`, `status`, `outcome` (`answer_outcome`), `submitted_at`, `answered_at`, `answer_due_at`, `sla_met` (`answered_at is not null and answered_at <= answer_due_at`), `escalated` (`escalated_at is not null`) |

Exemplo (as outras seguem o mesmo padrão):

```sql
create materialized view reporting.mv_policy as
select p.id as policy_id, p.insurer_id, pv.product_id, pr.name as product_name, p.product_type,
       p.vehicle_snapshot->>'category' as vehicle_category, p.vehicle_snapshot->>'usage' as vehicle_usage,
       cp.province, p.channel, p.broker_org_id, p.status, p.payment_plan, p.period_no,
       (p.issued_at  at time zone 'Africa/Maputo')::date as issued_date,
       (p.start_at   at time zone 'Africa/Maputo')::date as start_date,
       (p.end_at     at time zone 'Africa/Maputo')::date as end_date,
       pp.total_amount as issued_premium_amount,
       (pp.premium_breakdown->'commercial'->>'amount')::bigint as issued_commercial_premium_amount,
       p.total_amount as current_premium_amount,
       now() as refreshed_at
from policy.policy p
join catalog.product_version pv on pv.id = p.product_version_id
join catalog.product pr on pr.id = pv.product_id
join proposal.proposal pp on pp.id = p.proposal_id
left join identity.customer_profile cp on cp.user_id = p.policyholder_user_id
with data;
create unique index ux_mv_policy on reporting.mv_policy (policy_id);
create index ix_mv_policy_insurer on reporting.mv_policy (insurer_id, issued_date);
```

Cada `mv_*` tem também um índice `(insurer_id, <data principal>)`.

**Renovação:**

```sql
create or replace function reporting.refresh_all() returns void
  language plpgsql security definer set search_path = pg_catalog as $$
begin
  refresh materialized view concurrently reporting.mv_insurer;
  refresh materialized view concurrently reporting.mv_policy;
  refresh materialized view concurrently reporting.mv_renewal;
  refresh materialized view concurrently reporting.mv_instalment;
  refresh materialized view concurrently reporting.mv_payment;
  refresh materialized view concurrently reporting.mv_claim;
  refresh materialized view concurrently reporting.mv_complaint;
end $$;
revoke all on function reporting.refresh_all() from public;
grant execute on function reporting.refresh_all() to moseguros_app;
```

- A função corre como dono (`security definer`), que é o único que pode renovar. O S11-05 substitui-a com `create or replace` para acrescentar as suas vistas, mantendo estas.
- `ReportingRefreshJob`: `@Scheduled(cron = "0 5 * * * *", zone = "Africa/Maputo")`, ShedLock `reporting.refresh` (`lockAtMostFor = PT20M`), executa `select reporting.refresh_all()` e regista a duração em log estruturado. Não precisa de `@RunAsSystem` (a função não depende do âmbito).
- Nota para os sprints seguintes: uma migração que altere uma coluna usada aqui tem de recriar a vista materializada afectada na mesma migração (ADR-006, consequências).

### 3. Vistas por seguradora (`V202704150401`)

Para cada `mv_x` com `insurer_id` (todas excepto `mv_insurer`):

```sql
create view reporting.v_insurer_policy with (security_barrier) as
  select * from reporting.mv_policy
  where insurer_id = nullif(current_setting('app.insurer_id', true), '')::uuid;
grant select on reporting.v_insurer_policy to moseguros_reporting;
```

Vistas: `v_insurer_policy`, `v_insurer_renewal`, `v_insurer_instalment`, `v_insurer_payment`, `v_insurer_claim`, `v_insurer_complaint`. Sem `app.insurer_id` (cliente, mediador, regulador, plataforma) não devolvem nenhuma linha.

### 4. Execução das consultas (`ReportingQueryExecutor`)

- `query(String sql, Map<String,Object> params, RowMapper<T>)` com `NamedParameterJdbcTemplate`, dentro de um `TransactionTemplate` próprio, `readOnly = true`, que começa (pelo `TenantJpaTransactionManager`, S1-01) com o âmbito do pedido e depois executa:

```sql
set local role moseguros_reporting;
set local statement_timeout = '15s';
```

- O `set local` acaba com a transacção. Nunca se escreve nada na mesma transacção.
- É o único caminho do módulo `reporting` para ler dados de outros módulos. O S11-05 reutiliza-o.

### 5. Endpoints (tag `Reporting`)

Todos: `report:read`, âmbito `ORG` de seguradora (outro → 403 `FORBIDDEN`). Parâmetros comuns:

| Parâmetro | Regras |
| --- | --- |
| `from`, `to` | obrigatórios, datas `Africa/Maputo`, inclusivas; `to ≥ from` (`DATE_BEFORE_START`); intervalo ≤ 731 dias (`OUT_OF_RANGE`) |
| `granularity` | `MONTH` (defeito) ou `DAY`; `DAY` só com intervalo ≤ 92 dias (`OUT_OF_RANGE`) |

Erros de parâmetros → 400 `VALIDATION_ERROR` com o campo. Todas as respostas trazem `from`, `to`, `granularity` e `refreshedAt` (o menor `refreshed_at` das vistas usadas). `period` nas séries: `"2027-04"` ou `"2027-04-15"`; períodos sem dados aparecem com zeros. Rácios com 4 casas decimais, `HALF_UP`; `null` quando o denominador é 0. Médias de dias com 1 casa, `HALF_UP`.

### 6. Regras

1. As consultas do `DashboardQueries` só lêem `reporting.v_insurer_*`; o serviço passa também `insurerId = TenantContext.insurerId()` e filtra por ele.
2. Nenhuma resposta tem dados de pessoas: só contagens, valores, tipos e nomes de produtos.
3. Os painéis não são auditados (são agregados sem dados pessoais).
