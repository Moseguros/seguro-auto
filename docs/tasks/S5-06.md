## Contexto

ADR-004: os pagamentos por entidade e referência são confirmados por ficheiros lidos num executável à parte, o `payment-file-worker` (S5-09), que publica cada pagamento no RabbitMQ; o backend consome (S5-10). As mensagens ficam num módulo Maven partilhado, `payment-contracts`. Os segredos ficam no Vault (modelo transversal §7). Esta tarefa cria a infra-estrutura local (RabbitMQ, SFTP, Vault), o projecto `payment-contracts`, a topologia RabbitMQ e o *reactor* Maven na raiz do repositório para que o backend e o worker usem os contratos sem publicar artefactos.

**Pressupõe:** S0-07 (`infra/docker-compose.yml`, `infra/.env.example`, `infra/README.md`, padrão de Dockerfiles, `healthcheck` em todos os serviços); S0-08 (workflow de CI); S0-09 (`scripts/images.txt`, `scripts/doctor.sh`); S1-01 (`TestcontainersConfiguration`). Não usa nada do S4 (depende dele só pela ordem dos sprints).

## Objectivo

`docker compose up` sobe também `rabbitmq`, `sftp` e `vault`, saudáveis; o backend arranca com a topologia RabbitMQ declarada; `./mvnw -B verify` na raiz constrói `payment-contracts` e o backend; as mensagens têm JSON Schema e testes.

### 2. Mensagens (`payment-contracts`, versão de esquema 1)

Records Java imutáveis, JSON em camelCase, datas `Instant` em ISO 8601 UTC (`2027-01-15T09:12:44Z`), dinheiro em `MoneyAmount(long amount, String currency)` com `currency = "MZN"`. Cada mensagem tem o seu JSON Schema (draft 2020-12, `additionalProperties: false`). As duas aplicações usam o `ObjectMapper` do Spring Boot (com `JavaTimeModule` e `WRITE_DATES_AS_TIMESTAMPS = false`).

```java
public record ReferencePaymentReceived(
    String messageId, int schemaVersion /* 1 */, UUID insurerId, UUID sourceId,
    String entity, String reference, MoneyAmount amount, Instant paidAt,
    String channel /* pode ser null */, String bankTransactionId /* pode ser null */,
    String fileName, String fileSha256, int lineNo) {}

public record PaymentFileProcessed(
    String messageId, int schemaVersion, UUID insurerId, UUID sourceId,
    String fileName, String sha256, int recordCount, MoneyAmount totalAmount, Instant processedAt) {}

public record PaymentFileRejected(
    String messageId, int schemaVersion, UUID insurerId, UUID sourceId,
    String fileName, String sha256, FileRejectionReason reason, String detail /* ≤ 200, sem dados pessoais */,
    Integer lineNo /* pode ser null */, Instant rejectedAt) {}

public record PaymentSourcePolled(
    String messageId, int schemaVersion, UUID insurerId, UUID sourceId,
    Instant startedAt, Instant finishedAt, String outcome /* OK | ERROR */, PollErrorCode errorCode /* null se OK */,
    int filesFound, int filesProcessed, int filesRejected) {}
```

- `FileRejectionReason`: `ENTITY_MISMATCH`, `TRAILER_COUNT_MISMATCH`, `TRAILER_TOTAL_MISMATCH`, `INVALID_AMOUNT`, `PARSE_ERROR`, `ENCODING_ERROR`, `MISSING_HEADER`, `MISSING_TRAILER`, `UNSUPPORTED_RECORD`, `FILE_TOO_LARGE`.
- `PollErrorCode`: `SFTP_UNREACHABLE`, `SFTP_AUTH_FAILED`, `SFTP_HOST_KEY_MISMATCH`, `SFTP_DIRECTORY_NOT_FOUND`, `SECRET_NOT_FOUND`, `UNSUPPORTED_FORMAT`, `PUBLISH_FAILED`, `INTERNAL_ERROR`.
- **`messageId`** (`MessageIds`, hexadecimal minúsculo de SHA-256 sobre UTF-8):
  - `ReferencePaymentReceived`: `sha256(sourceId + "|" + bankTransactionId)` quando há `bankTransactionId`; senão `sha256(sourceId + "|" + entity + "|" + reference + "|" + paidAt ISO + "|" + amount)`. O mesmo pagamento repetido noutro ficheiro tem o mesmo `messageId` (e o backend ignora-o, S5-10);
  - `PaymentFileProcessed`: `sha256("processed|" + sourceId + "|" + sha256)`;
  - `PaymentFileRejected`: `sha256("rejected|" + sourceId + "|" + sha256 + "|" + rejectedAt ISO)`;
  - `PaymentSourcePolled`: `UUID` aleatório em texto.
- **Propriedades AMQP** (`MessageHeaders`): `messageId` = o `messageId`; `contentType = application/json`; `type` = nome simples da classe (`ReferencePaymentReceived`); cabeçalho `schemaVersion = 1`; `deliveryMode = PERSISTENT`.
- **Contrato REST interno** do worker (S5-09), também aqui para as duas aplicações usarem o mesmo tipo:

```java
public record FileSourceList(List<FileSourceDescriptor> sources) {}
public record FileSourceDescriptor(
    UUID sourceId, UUID insurerId, long version, String entity,
    Sftp sftp, Map<String, String> secretRefs /* "sftp.password" → "secret/insurers/…" */,
    String pollCron, String fileFormat, String timezone) {
  public record Sftp(String host, int port, String username, String authType /* PASSWORD | KEY */,
                     String inboundDir, String processedDir, String errorDir, String filePattern,
                     String hostKeyFingerprint /* pode ser null em local/test */) {}
}
```

- Evolução: campos novos opcionais mantêm `schemaVersion = 1`; mudanças incompatíveis criam `…V2` e uma fila nova. Escrever isto no Javadoc do pacote.

### 3. Topologia RabbitMQ (`PaymentsTopology`)

| Elemento | Nome | Tipo e argumentos |
| --- | --- | --- |
| Exchange | `payments.events` | `topic`, durável |
| Exchange de mensagens mortas | `payments.dlx` | `direct`, durável |
| Fila | `core.reference-payments` | quorum (`x-queue-type: quorum`), `x-dead-letter-exchange: payments.dlx`, `x-dead-letter-routing-key: core.reference-payments`, `x-delivery-limit: 20` |
| Fila | `core.payment-file-events` | igual, com `x-dead-letter-routing-key: core.payment-file-events` |
| Fila | `core.reference-payments.dlq` | quorum, ligada a `payments.dlx` com a chave `core.reference-payments` |
| Fila | `core.payment-file-events.dlq` | quorum, ligada a `payments.dlx` com a chave `core.payment-file-events` |

Chaves de encaminhamento (publicadas pelo worker, com o `insurerId` no fim):

| Mensagem | Chave | Ligação |
| --- | --- | --- |
| `ReferencePaymentReceived` | `reference.paid.{insurerId}` | `core.reference-payments` ← `reference.paid.*` |
| `PaymentFileProcessed` | `reference.file-processed.{insurerId}` | `core.payment-file-events` ← `reference.file-processed.*` |
| `PaymentFileRejected` | `reference.file-rejected.{insurerId}` | `core.payment-file-events` ← `reference.file-rejected.*` |
| `PaymentSourcePolled` | `reference.source-polled.{insurerId}` | `core.payment-file-events` ← `reference.source-polled.*` |

- **Atenção:** o plano escrevia a ligação `reference.file-*`; num exchange `topic` o `*` só substitui uma palavra inteira entre pontos, por isso `file-*` não funciona como curinga. Usam-se as três ligações explícitas acima.
- **Quem declara:** o backend declara tudo (`PaymentsAmqpConfig`, `Declarables` do Spring AMQP; `RabbitAdmin` declara na primeira ligação). O worker declara só o exchange `payments.events` com os mesmos argumentos e publica com `mandatory = true` (S5-09).
- **Utilizadores:** em `local` um só utilizador (`RABBITMQ_DEFAULT_USER`/`PASS`). Em staging e produção (escrever no `infra/README.md`, secção "RabbitMQ — utilizadores"): `moseguros_backend` com `configure`/`write`/`read` em `^(payments\..*|core\..*)$`; `moseguros_worker` com `configure` e `write` em `^payments\.events$` e `read` vazio.
- Backend:

```yaml
spring:
  rabbitmq:
    host: ${RABBITMQ_HOST:localhost}
    port: ${RABBITMQ_PORT:5672}
    username: ${RABBITMQ_USERNAME:moseguros}
    password: ${RABBITMQ_PASSWORD:moseguros}
```

- Nesta tarefa o backend **só declara** a topologia; os consumidores são do S5-10.
- `TestcontainersConfiguration`: acrescenta um `RabbitMQContainer("rabbitmq:3.13.7-management-alpine")` partilhado, com as propriedades `spring.rabbitmq.*` registadas como o Postgres (S1-01).
