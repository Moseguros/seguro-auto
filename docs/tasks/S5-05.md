## Contexto

RF-04. Além do M-Pesa, a seguradora pode aceitar e-Mola (Movitel) e cartão. Ainda não há documentação nem credenciais do e-Mola nem de um adquirente de cartões (modelo transversal §9: não bloqueia). Esta tarefa cria, para cada um, uma **porta** para o fornecedor com uma implementação **mock**, o adaptador `PaymentGateway` que a usa, e o endpoint de *callbacks* com assinatura validada. Os adaptadores reais entram em fichas próprias quando houver documentação. **O mock nunca pode estar activo em staging ou produção** (cobraria "pagamentos" que não existem).

**Pressupõe:**
- S5-01: configuração `EMOLA` (`merchantCode`, `baseUrl`, `timeoutSeconds`, segredo `merchantSecret`) e `CARD` (`provider` = `MOCK`, `merchantId`, `terminalId`, `checkoutBaseUrl`, `currency`, segredos `secretKey`, `callbackSigningKey`); `PaymentMethodTester`; `PaymentSystemLookups`; `SecretStore`.
- S5-02: `PaymentGateway`, `DispatchMode.SYNC`, `IntentStateService`, `FailureCode`, `nextAction` `AWAIT_CUSTOMER_CONFIRMATION` e `REDIRECT`, `PaymentExpiryJob` (expira cartões).
- S5-04: `PaymentStatusQueryJob` e `PaymentDispatchRecoveryJob` (esta tarefa acrescenta o e-Mola a ambos). Se o S5-04 ainda não estiver no `main`, esta tarefa cria os dois jobs só com as regras do e-Mola e o S5-04 acrescenta as do M-Pesa.

## Objectivo

Em `local` e `test`, o cliente paga com e-Mola (resultado pelo final do número) ou com cartão (página de pagamento simulada, resultado pelo número do cartão); o resultado chega por *callback* assinado e a intenção fica `SUCCEEDED` ou `FAILED`; com o perfil `prod`, os mocks não arrancam.

## Especificação

### 1. Portas para os fornecedores

```java
public interface EmolaProviderPort {
  EmolaRequestResult requestPayment(EmolaPaymentRequest request);   // pede o pagamento no telemóvel do cliente
  EmolaStatus queryStatus(EmolaConfig config, String providerTxId); // APPROVED, DECLINED, CANCELLED, PENDING
}
public record EmolaPaymentRequest(EmolaConfig config, String msisdn /* 258… */, Money amount,
    String intentReference, String callbackUrl) {}
public record EmolaRequestResult(boolean accepted, String providerTxId, String errorCode) {}

public interface CardAcquirerPort {
  CheckoutSession createCheckout(CheckoutRequest request);
  CardStatus queryStatus(CardConfig config, String sessionId);     // APPROVED, DECLINED, CANCELLED, PENDING
}
public record CheckoutRequest(CardConfig config, Money amount, String intentReference,
    String returnUrl, String callbackUrl, Instant expiresAt) {}
public record CheckoutSession(String sessionId, String redirectUrl) {}
```

`EmolaConfig` e `CardConfig` são lidos de `MethodConfig.settings` e dos segredos no momento da chamada.

Escolha da implementação: e-Mola por `moseguros.payment.emola.provider` (só `mock` nesta tarefa); cartão por `settings.provider` da seguradora (só `MOCK`). Callbacks em `{moseguros.payment.callback-base-url}/api/v1/payments/callbacks/{provider}` (`callback-base-url`: `http://localhost:8080` em `local`; no compose `http://backend:8080`).

### 2. e-Mola

**`EmolaGateway`** (`method() = EMOLA`, `dispatchMode() = SYNC`):
- `initiate`: chama `requestPayment`. `accepted` → `PENDING` com `provider_tx_id`; recusado → `FAILED` `PROVIDER_REJECTED`; excepção ou timeout (`settings.timeoutSeconds`) antes da resposta → `FAILED` `PROVIDER_UNAVAILABLE`.
- `nextAction` (S5-02): `AWAIT_CUSTOMER_CONFIRMATION` com `timeoutAt = dispatched_at + settings.timeoutSeconds` (`dispatched_at` = momento do `initiate`).
- `queryStatus`: `APPROVED` → `SUCCEEDED` (`STATUS_QUERY`); `DECLINED` → `FAILED` `PROVIDER_REJECTED`; `CANCELLED` → `FAILED` `CUSTOMER_CANCELLED`; `PENDING` → continua `UNKNOWN`.
- `PaymentDispatchRecoveryJob` (acrescentar): `EMOLA` em `PENDING` com `dispatched_at < agora − (timeoutSeconds + 60 s)` → `UNKNOWN`; daí o `PaymentStatusQueryJob` consulta com o calendário do S5-04.

**`MockEmolaProvider`** (`@Profile({"local","test"})`):
- `requestPayment` aceita sempre, com `providerTxId = "EM" + 10 caracteres [A-Z0-9]`, e agenda (num `TaskScheduler`) o resultado ao fim de `moseguros.payment.emola.mock-delay` (defeito `PT3S`; `PT0.2S` em `test`), pelos três últimos dígitos do número:

| Final | Resultado enviado por *callback* |
| --- | --- |
| `001` | `CANCELLED` |
| `002` | `DECLINED` |
| `009` | nenhum (o pagamento fica sem resposta; serve para testar `UNKNOWN`) |
| outro | `APPROVED` |

- Guarda em memória o resultado de cada `providerTxId` para o `queryStatus` (`009` → `PENDING`; desconhecido → `PENDING`).
- Envia o *callback* com o `MockCallbackSender` (secção 4), assinado com o `merchantSecret` da seguradora.

### 3. Cartão

**`CardGateway`** (`method() = CARD`, `dispatchMode() = SYNC`):
- `initiate`: `createCheckout` com `returnUrl = {moseguros.web.base-url}/cliente/pagamentos/{intentId}` (a app também abre esta página no navegador, S5-11) → `PENDING`, `provider_tx_id = sessionId`, `redirect_url = redirectUrl`. Erro → `FAILED` `PROVIDER_UNAVAILABLE`.
- `nextAction`: `REDIRECT` com `url = redirect_url`.
- Expiração: pelo `PaymentExpiryJob` do S5-02 (`intent_validity_minutes`).
- `queryStatus` como no e-Mola, com `DECLINED` → `FAILED` `DECLINED`.

**`MockCardAcquirer`** (`@Profile({"local","test"})`): `sessionId` = 24 caracteres `[a-z0-9]`; `redirectUrl = settings.checkoutBaseUrl + "/" + sessionId`. Guarda o resultado em memória para o `queryStatus`.

**Página de pagamento simulada** (`DevCardCheckoutController`, `@Profile({"local","test"})`, público só nestes perfis):
- `GET /api/v1/dev/card-checkout/{sessionId}` → HTML (`templates/dev/card-checkout.html`) com o aviso **"Página de pagamento simulada — só para desenvolvimento"**, a seguradora, o montante, um campo "Número do cartão" e os botões "Pagar" e "Cancelar". Sessão desconhecida → 404.
- `POST /api/v1/dev/card-checkout/{sessionId}` (formulário `cardNumber`, `action=pay|cancel`):

| Entrada | Resultado |
| --- | --- |
| `action=cancel` | `CANCELLED` |
| `4111111111111111` | `APPROVED` |
| `4000000000000002` | `DECLINED` |
| outro número | `DECLINED` |

  Envia o *callback* assinado com o `callbackSigningKey` e responde `303` para o `returnUrl`.
- Estes endpoints não entram no `api/openapi.yaml` (`@Hidden`). O número do cartão não é gravado nem registado em log.

### 4. Callbacks

**`POST /api/v1/payments/callbacks/{provider}`** (`receivePaymentCallback`, tag `Payment`, público no `SecurityConfig`), `provider` em `emola-mock`, `card-mock` (outro → 404 `NOT_FOUND`).

Cabeçalho `X-Signature`: hexadecimal minúsculo de `HMAC-SHA256(chave, corpo em bytes)`, com a chave = `merchantSecret` (e-Mola) ou `callbackSigningKey` (cartão) da configuração da intenção. Corpo (formato dos mocks, definido por nós):

```json
{ "intentReference": "PG-2027-0001234", "providerTxId": "EM4K2J9QZ1XW", "status": "APPROVED", "amount": 299900, "occurredAt": "2027-01-15T10:00:05Z" }
```

`PaymentCallbackListener.handle(provider, headers, body)` (`payment.application`, `@RunAsSystem`, porque não há utilizador), por esta ordem:

1. JSON inválido ou campo em falta → 400 `PAYMENT_CALLBACK_INVALID`.
2. Intenção pela `intentReference`. Não existe, ou o método não corresponde ao `provider` → 204 (ignora; `WARN`), para não revelar referências.
3. Assinatura (comparação em tempo constante, `MessageDigest.isEqual`) diferente ou ausente → 401 `UNAUTHORIZED`.
4. `providerTxId ≠ provider_tx_id` ou `amount ≠ amount` da intenção → 400 `PAYMENT_CALLBACK_INVALID`, `payment_event` `CALLBACK` gravado, `ERROR` no log; o estado não muda.
5. Aplica: `APPROVED` → `SUCCEEDED` (`confirmed_by = CALLBACK`); `DECLINED` → `FAILED` (`DECLINED` no cartão, `PROVIDER_REJECTED` no e-Mola); `CANCELLED` → `FAILED` `CUSTOMER_CANCELLED`. Estado de origem conforme a tabela do S5-02 (um `APPROVED` depois de `EXPIRED` confirma: o dinheiro foi cobrado).
6. Intenção já no estado que o *callback* indica → 204 sem alterações (repetição). *Callback* contraditório com um estado final (ex.: `DECLINED` depois de `SUCCEEDED`) → 204, sem alterações, `WARN`.
7. Grava sempre `payment_event` `CALLBACK` com o corpo (não tem dados sensíveis). Resposta 204.

`MockCallbackSender`: `RestClient` `POST` para o URL de *callback* com o corpo e o `X-Signature` calculado pelo `CallbackSigner`, como faria um fornecedor real; erro → 3 tentativas com 1 s de intervalo, depois `WARN`.

### 5. Testes de ligação

`EmolaPaymentMethodTester` e `CardPaymentMethodTester`: com o fornecedor mock → `OK` com `message = MOCK_PROVIDER`; segredo em falta → `FAILED` `SECRET_MISSING`.

### 6. Mocks nunca em produção (`PaymentProviderReadinessCheck`)

Fora dos perfis `local` e `test`:
- linha `EMOLA` activa e `moseguros.payment.emola.provider = mock`, ou linha `CARD` activa com `settings.provider = MOCK` → **a aplicação não arranca** (mensagem: `<método> activo para a seguradora <id> com fornecedor simulado; não há adaptador real`);
- `enable` de `EMOLA` ou `CARD` nessas condições → 409 `PAYMENT_PROVIDER_NOT_AVAILABLE`;
- os beans `MockEmolaProvider` e `MockCardAcquirer` não existem; um `EmolaGateway`/`CardGateway` sem porta disponível não se regista no `GatewayRegistry`, e o método não aparece ao cliente (`PAYMENT_METHOD_NOT_AVAILABLE` se for pedido).

### 7. Códigos de erro novos

`PAYMENT_CALLBACK_INVALID` (400), `PAYMENT_PROVIDER_NOT_AVAILABLE` (409). Traduções na web e na app.
