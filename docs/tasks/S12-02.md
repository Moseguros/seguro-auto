## Contexto

Plano, Sprint 12, "USSD/SMS": "1 Comprar seguro RC (matrícula → categoria → duração 7/30/365 dias → lista de até 3 cotações → confirmar → pagamento M-Pesa/e-Mola por push ou entidade e referência enviadas por SMS), 2 Verificar matrícula"; "o certificado é enviado por SMS com link curto"; "conta criada automaticamente a partir do `msisdn`; KYC simplificado (nome e n.º de documento por USSD) só para RC". Usa o motor, a tabela e os textos do S12-01.

A compra por USSD passa pelos mesmos módulos e regras da app: cotação (`rating`), proposta e aceitação (`proposal`, S4-05), pagamento (`payment`, S5) e emissão (`policy`, S6). Nada é emitido nem aceite por fora dessas regras. Os módulos `vehicle`, `rating`, `identity`, `proposal`, `payment`, `policy` e `verification` ganham métodos públicos novos para o canal (o modelo §3 permite acrescentar métodos, nunca mudar os existentes).

**Pressupõe** (se um nome do sprint de origem for diferente, usa-se o do sprint de origem e regista-se em "Questões"):
- S12-01 completo: `UssdMenuEngine`, `UssdTexts`, `UssdSessionData`, `UssdCustomerContext` (o pedido corre como o cliente, com `chn = USSD`), `integration.ussd_session` com `proposal_id` e `payment_intent_id`.
- `vehicle` (S2-03): enums públicos `VehicleCategory` e `VehicleUsage` no pacote raiz; tabela `vehicle.vehicle` com dono `owner_user_id` e matrícula única **por dono** (não global).
- `rating` (S3-02): serviço que cria um `rating.quote_request` e avalia os produtos publicados em paralelo (o do `POST /quotes`), com `duration_days` e `start_date`; `QuoteView` com `id`, `insurerId`, `insurerName`, `productVersionId`, `status`, `totalAmount` (`Money`), `startAt`, `endAt`, `validUntil`.
- `identity` (S1-06, S4-01): `CustomerProfile` com `full_name`, `id_doc_type`, `id_doc_number_enc`, `nuit_enc`; serviço de perfil com auditoria `CUSTOMER.PROFILE_UPDATE` (valores mascarados).
- `proposal` (S4-02 a S4-05): estados do plano, colunas `channel` (`check in ('APP','WEB','BROKER')`) e `proposal.signature.method` (`check in ('OTP')`); os cinco códigos fixos de `proposal.declaration`; PDF da proposta pelo `DocumentApi.renderPdf`; regras de aceitação automática do S4-05; `ProposalView` com `id`, `number`, `status`, `insurerId`, `insurerName`, `plate`, `totalAmount`, `expiresAt`.
- `payment` (S5-02): `PaymentApi.createIntent(CreateIntentCommand)` com `targetType`, `targetId`, `method` (`PaymentMethod`: `MPESA`, `EMOLA`, `CARD`, `BANK_REFERENCE`), `payerMsisdn`, `idempotencyKey`, `initiatedVia` (`USSD` já existe no plano); o `payment` envia sozinho o SMS com entidade e referência (`ReferenceGenerated`, modelo §1.2) e as mensagens de pagamento falhado (S6-04).
- `policy` (S6-01, S6-02): evento `PolicyIssued` com, pelo menos, `policyId`, `proposalId`, `insurerId`, `policyholderUserId`; `policy.certificate` com `number`, `valid_from`, `valid_to` e o URL de verificação `…/v/{verification_token}` do QR.
- `verification` (S6-03): o serviço da verificação por matrícula que grava `verification.check_log` com `checker_type` `PUBLIC`.
- `notification` (S6-04): tabela `notification.template (code, channel, locale, subject, body, whatsapp_template_name)` com Mustache, `NotificationApi.notify(userId, templateCode, params, NotificationCategory)` e a categoria de mensagens que seguem sempre (chamada aqui `NotificationCategory.TRANSACTIONAL`; usa-se o nome do S6-04).
- Permissões existentes usadas pelo cliente: `self:vehicles`, `self:quotes`, `self:proposals`, `self:payments`, `self:policies` (modelo §5).

## Objectivo

No simulador, um cliente sem conta compra uma RC de 30 dias para a sua matrícula, paga por M-Pesa (simulador `mpesa-mock`), recebe por SMS o certificado com o link de verificação, e qualquer pessoa verifica a matrícula pelo menu 2.

### 3. Configuração

```yaml
moseguros:
  ussd:
    categories:                       # no máximo 5; etiqueta ≤ 20 caracteres, sem acentos
      - key: "1"
        vehicle-category: <código VehicleCategory>   # PROVISÓRIO: preencher com os códigos do S2-02/S2-03
        vehicle-usage: <código VehicleUsage>
        label-pt: Ligeiro particular
        label-en: Private car
      # … até 5 entradas (sugestão provisória: Ligeiro particular, Ligeiro comercial, Motociclo, Pesado, Transporte publico)
    durations:
      - { key: "1", days: 7,   product-type: TEMPORARY, label-pt: "7 dias",  label-en: "7 days" }
      - { key: "2", days: 30,  product-type: TEMPORARY, label-pt: "30 dias", label-en: "30 days" }
      - { key: "3", days: 365, product-type: <código RC anual do S2-04>, label-pt: "1 ano", label-en: "1 year" }
    payment-methods:                  # ordem dos ecrãs; CARD nunca entra no USSD
      - { method: MPESA, msisdn-prefixes: ["84","85"], label-pt: "M-Pesa", label-en: "M-Pesa" }
      - { method: EMOLA, msisdn-prefixes: ["86","87"], label-pt: "e-Mola", label-en: "e-Mola" }
      - { method: BANK_REFERENCE, msisdn-prefixes: [], label-pt: "Referencia por SMS", label-en: "Reference by SMS" }
    max-verifications-per-hour: 30
```

- No arranque: cada `vehicle-category`/`vehicle-usage` tem de existir no enum, senão a aplicação não arranca. `product-type` é validado pelo `rating` na primeira chamada (código desconhecido → `DomainException` registada como `ERROR` e ecrã `ussd.buy.noQuotes`).
- `msisdn-prefixes` vazio = qualquer número. Os prefixos são os dois dígitos a seguir a `258`.

### 5. Assinatura, proposta e aceitação (`BUY_SIGN` → `1`)

1. Se há KYC em `sensitive_data_enc`: `IdentityApi.recordSimplifiedKyc(...)`. Erro de validação (não devia acontecer, já validado) → `End(ussd.end.unavailable)`.
2. Se `ussd_session.proposal_id` está vazio: gravar `data.signRequestedAt = agora` na sessão; chamar `ProposalApi.submitFromUssd(new UssdProposalCommand(quoteId, userId, declarationsConfirmed = true, rcNoticeAcknowledged = true, confirmedAt = agora, aggregatorCode))`.
   - Se responder que a cotação já foi usada (código do S4-02 para cotação usada), procurar `findByQuoteId(quoteId)` e continuar com essa proposta (retoma de um pedido repetido pelo agregador).
3. Gravar `proposal_id` e responder conforme `UssdProposalResult.status`:
   - `ACCEPTED` → `BUY_PAYMENT_METHOD`;
   - `UNDER_REVIEW` → `End(ussd.buy.underReview, number, shortCode)`;
   - `REJECTED` ou `NOT_ELIGIBLE` → `End(ussd.buy.rejected, number|"", supportPhone)`.

**`ProposalApi.submitFromUssd`** (`UssdProposalService`, `self:proposals`, uma transacção):
- Exige `chn = USSD` no token do pedido (`CurrentUser`); de outro canal → `FORBIDDEN`.
- Cria a proposta a partir da cotação com as regras do S4-02 (cotação `OFFERED`, válida, do cliente; `RatingApi.markUsed`), `channel = USSD`, tomador = segurado = cliente.
- O perfil do cliente pode não ter `birth_date` nem `province` **só** quando `channel = USSD`; noutros canais mantém-se a regra do S4-02.
- Declarações: os cinco códigos do S4-02 com resposta negativa (o cliente confirmou as duas perguntas agrupadas do USSD).
- Adequação: grava a confirmação do aviso RC (`question_code = USSD_MTPL_NOTICE_ACK`, `answer = YES`, resultado `SUITABLE`). Se a versão do produto tiver perguntas de adequação obrigatórias que o USSD não faz → não cria nada e devolve `NOT_ELIGIBLE`.
- Gera o PDF da proposta (S4-04) e grava `proposal.signature` com `method = USSD_CONFIRMATION`, `signer_user_id`, `signed_at = confirmedAt`, `document_hash` = SHA-256 do PDF, `ip = null`, `device = "USSD:" + aggregatorCode`.
- Submete com as regras do S4-05 (KYC simplificado, limiar e aceitação automática configuráveis). Nada é aceite fora dessas regras.
- Publica os mesmos eventos do S4 (`ProposalSubmitted`, `ProposalAccepted`…). Auditoria a do S4.
- Devolve `UssdProposalResult(UUID proposalId, String number, String status, Money totalAmount, UUID insurerId, LocalDate expiresAt)`, com `status` `ACCEPTED`, `UNDER_REVIEW`, `REJECTED` ou `NOT_ELIGIBLE` (este último sem `proposalId`).

### 6. Pagamento (`BUY_PAYMENT_METHOD`)

- Opções: `PaymentApi.availableMethods(insurerId, totalAmount)`, intersectadas com `moseguros.ussd.payment-methods` (pela ordem da configuração) e filtradas pelo prefixo do `msisdn` do cliente. Guardar as chaves em `data.paymentOptionKeys`. Sem opções → `End(ussd.buy.noMethods)`.
- Escolha → `PaymentApi.createIntent(new CreateIntentCommand(targetType = "PROPOSAL", targetId = proposalId, method, payerMsisdn = msisdn do cliente, idempotencyKey, initiatedVia = USSD))`.
  - `idempotencyKey = UUID.nameUUIDFromBytes(("ussd:" + sessionId + ":" + proposalId + ":" + method).getBytes(UTF_8))`: um pedido repetido pelo agregador não cria outro intent.
  - Grava `payment_intent_id` e termina **antes** do pedido de PIN chegar ao telemóvel (com a sessão USSD aberta o telemóvel não mostra o pedido M-Pesa): `End(ussd.buy.mpesa | ussd.buy.emola | ussd.buy.reference, valor)`.
- O resto é do `payment` (S5): o C2B corre de forma assíncrona; `UNKNOWN` com consultas; o SMS da referência é enviado pelo `payment`; a falha de pagamento é avisada pelas notificações do S6-04. A proposta continua `ACCEPTED`: o cliente volta a marcar o código e paga pelo `BUY_PENDING` (um novo intent, com nova chave porque a sessão é outra).
- Nunca se repete o C2B dentro da mesma sessão.

### 7. Certificado por SMS

- `UssdPolicyIssuedListener` (`@ApplicationModuleListener` de `PolicyIssued`, `@RunAsSystem`):
  - procura `ussd_session` com `proposal_id = event.proposalId`; não há → não faz nada (compras da app e da web);
  - `PolicyApi.certificateSummary(policyId)` → `UssdCertificateSender.send(userId, summary, language da sessão)`.
- `UssdCertificateSender`: `NotificationApi.notify(userId, "USSD_CERTIFICATE", { plate, from, to, policyNumber, verifyUrl }, TRANSACTIONAL)`; datas `dd/MM/yyyy`.
- Em "Os meus seguros" (S12-01), o detalhe ganha a linha `{5}` = `ussd.policies.certificateOption` (`1 Certificado por SMS\n`); `1` → `UssdCertificateSender.send` e `End(ussd.policies.certificateSent, msisdn mascarado)`. Apólice sem certificado `VALID` → a linha não aparece.
- O link é o da verificação pública do certificado (página `/v/:token`, sem dados pessoais). O PDF completo fica na área do cliente na web e na app, depois de entrar por OTP (ver "Questões").

### 8. Verificação (`VERIFY_PLATE`)

1. `checksSince(userId, agora − 1 h) ≥ max-verifications-per-hour` → `End(ussd.verify.rateLimited)`.
2. `PlateParser.parse`; inválida → `Stay(ussd.error.invalidPlate)`.
3. `VerificationApi.verifyPlate(plate, userId)` → `End` com o texto do estado:

| `status` | Chave |
| --- | --- |
| `VALID` | `ussd.verify.valid` (máscara, seguradora, cobertura `ussd.coverage.<coverageType>`, `validTo`) |
| `NOT_FOUND` | `ussd.verify.notFound` |
| `EXPIRED` | `ussd.verify.expired` (máscara, `validTo`, seguradora) |
| `SUSPENDED` | `ussd.verify.suspended` |
| `CANCELLED` | `ussd.verify.cancelled` |

`ussd.coverage.MTPL_ONLY` `RC`; `COMPREHENSIVE` `RC + danos proprios`; `TEMPORARY` `RC temporario`.
