## Contexto

RF-15 (aceitação). O cliente (ou o mediador) submete a proposta completa e assinada. As regras de aceitação do produto (`product_version.rules.underwriting`) decidem logo se a proposta é aceite automaticamente ou vai para análise do subscritor. O subscritor aceita, recusa com motivo ou pede informação. A seguradora tem 15 dias para decidir; o sistema alerta aos 10. **Não há aceitação tácita**: o fim do prazo é só um alerta (plano, até validação jurídica). Os pagamentos chegam no S5: aqui a proposta pára em `ACCEPTED`.

**Pressupõe:**
- S4-01: `IdentityApi.kycStatus(UUID) → KycStatus` (`NONE|PENDING|VERIFIED|REJECTED|OUTDATED`), `IdentityApi.customer(UUID)`; permissões `proposal:read`, `proposal:decide`.
- S4-02: tabelas e estados da proposta, `content_revision`, `expires_at`, `ProposalResponse` (blocos `kyc`, `decision`), `ProposalExpired`, `SystemLookups` do `proposal`, `ProposalProperties`.
- S4-03: vistoria (`approveInspection`, estados), `PROPOSAL_NOT_UNDER_REVIEW`.
- S4-04: `ProposalCompleteness` (com o item `SIGNATURE`), `Proposal.contentChanged()`, `PROPOSAL_INCOMPLETE`.
- S1-04: `NotificationApi.sendEmail`, `moseguros.web.base-url`.
- S2-04: `catalog.product_version.rules jsonb`; `CatalogApi.version(UUID)` expõe `rules` (pressupõe-se um `JsonNode`; se o S2-04 expuser outro tipo, converte-se sem mudar o conteúdo); estado da versão (`DRAFT`/publicada) e o código de erro que o S2-04 usa para "versão publicada não é editável" (409). Os produtos são da seguradora do utilizador (`insurer_id`, RLS do S2-04).

## Objectivo

`POST /proposals/{id}/submit` passa uma proposta completa a `ACCEPTED` (aceitação automática) ou a `UNDER_REVIEW`, com o registo das regras avaliadas. O subscritor vê a fila com o SLA, aceita, recusa ou pede informação; o cliente é avisado por e-mail; aos 10 dias sem decisão os subscritores recebem um alerta. O gestor de produto configura as regras de aceitação de uma versão em rascunho.

## Especificação

### 1. Regras de aceitação (`rules.underwriting`, versão 1)

JSON guardado na chave `underwriting` do `rules` da versão do produto, validado por `schemas/underwriting-v1.json` (`additionalProperties: false` em todos os objectos):

```json
{
  "schemaVersion": 1,
  "autoAccept": {
    "enabled": true,
    "simplifiedKycMaxPremium": { "amount": 1000000, "currency": "MZN" },
    "liability": { "requireAllDeclarationsNegative": false },
    "ownDamage": {
      "maxVehicleValue": { "amount": 150000000, "currency": "MZN" },
      "requireAllDeclarationsNegative": true
    }
  }
}
```

| Campo | Tipo | Regra |
| --- | --- | --- |
| `schemaVersion` | inteiro | sempre `1` |
| `autoAccept.enabled` | booleano | `false` → todas as propostas vão para análise |
| `autoAccept.simplifiedKycMaxPremium` | `Money` | > 0; KYC simplificado (nome, documento e NUIT do tomador, sempre presentes na proposta) basta quando o total é **estritamente menor** |
| `autoAccept.liability.requireAllDeclarationsNegative` | booleano | para propostas sem coberturas `OD_*` |
| `autoAccept.ownDamage.maxVehicleValue` | `Money` | > 0; valor comercial máximo para aceitação automática com danos próprios |
| `autoAccept.ownDamage.requireAllDeclarationsNegative` | booleano | para propostas com coberturas `OD_*` |

**Valores por defeito** (usados quando a versão não tem `underwriting`): os do exemplo acima — 10 000 MT de limiar do KYC simplificado e 1 500 000 MT de valor máximo do veículo. São **provisórios** (ver "Questões"). Ficam em `UnderwritingRules.DEFAULTS`.

### 2. Configurar as regras (módulo `catalog`, tag `Catalog`)

- **`GET /api/v1/insurer/product-versions/{id}/underwriting-rules`** (`getUnderwritingRules`, `product:read`) → 200 `{ "rules": { … }, "isDefault": true }` (com `isDefault = true` devolve os valores por defeito).
- **`PUT /api/v1/insurer/product-versions/{id}/underwriting-rules`** (`updateUnderwritingRules`, `product:manage`) `{ "rules": { … }, "version": 4 }` (`version` da versão do produto) → 200 com a mesma resposta (`isDefault = false`).
  - Versão de outra seguradora → 404 com o código do S2-04 para versão não encontrada.
  - Versão já publicada → 409 com o código do S2-04 para versão não editável (as versões publicadas são imutáveis).
  - JSON inválido pelo schema → 400 `VALIDATION_ERROR` com `errors[] = [{ field: "rules.<caminho>", code: "INVALID_RULES" }]`, um por erro do validador (`com.networknt:json-schema-validator`, já usado no S3-01 para `rating-v1.json`; se o S3-01 tiver usado outro validador, usa-se o mesmo).
  - Grava `rules = jsonb_set(rules, '{underwriting}', …)`; auditoria `PRODUCT_VERSION.UNDERWRITING_UPDATE` (antes e depois).
- O `catalog` não conhece o `proposal`: só valida e guarda o JSON. O `proposal` lê-o com `CatalogApi.version(productVersionId).rules()`.

### 3. Avaliação (`UnderwritingEvaluator`, função pura)

Entradas: as regras (ou os valores por defeito), `hasOD` (alguma cobertura `OD_*`), `total_amount`, `kycState`, as respostas das declarações, o estado da vistoria e `vehicle_snapshot.commercialValue`. Avaliam-se **todas** as condições, por esta ordem, e juntam-se as falhas (`UnderwritingFailure`):

| # | Falha | Condição de falha |
| --- | --- | --- |
| 1 | `AUTO_ACCEPT_DISABLED` | `enabled = false` (as restantes não se avaliam) |
| 2 | `KYC_REQUIRED` | `kycState ≠ VERIFIED` **e** `total_amount ≥ simplifiedKycMaxPremium.amount` |
| 3 | `DECLARATION_POSITIVE` | sem `OD_*`: `liability.requireAllDeclarationsNegative` e alguma resposta "sim"; com `OD_*`: idem com `ownDamage.requireAllDeclarationsNegative` |
| 4 | `INSPECTION_NOT_APPROVED` | `hasOD` e vistoria ≠ `APPROVED` |
| 5 | `VEHICLE_VALUE_MISSING` | `hasOD` e `commercialValue` nulo |
| 6 | `VEHICLE_VALUE_ABOVE_LIMIT` | `hasOD` e `commercialValue > ownDamage.maxVehicleValue.amount` |

Resultado `AUTOMATIC` (aceite) sem falhas; senão `MANUAL_REVIEW` com a lista. `OUTDATED`, `PENDING`, `REJECTED` e `NONE` contam como "não `VERIFIED`".

O registo vai para `underwriting_result`:

```json
{ "rulesSchemaVersion": 1, "rulesSource": "PRODUCT", "evaluatedAt": "2027-01-06T08:40:00Z",
  "outcome": "MANUAL_REVIEW", "failures": ["KYC_REQUIRED"],
  "inputs": { "hasOwnDamage": false, "totalAmount": 1200000, "kycState": "PENDING",
              "simplifiedKycMaxPremium": 1000000, "positiveDeclarations": [],
              "inspectionStatus": null, "vehicleValue": 80000000, "maxVehicleValue": 150000000 } }
```

(`rulesSource`: `PRODUCT` ou `DEFAULT`.)

**Casos de referência** (`UnderwritingEvaluatorTest`, valores por defeito salvo indicação; montantes em centavos):

| # | Produto / coberturas | Total | KYC | Declarações | Vistoria | Valor veículo | Resultado |

| 3 | MTPL_ONLY | 1 200 000 | `VERIFIED` | todas "não" | — | — | `AUTOMATIC` |
| 4 | MTPL_ONLY | 1 200 000 | `OUTDATED` | todas "não" | — | — | `MANUAL_REVIEW` `[KYC_REQUIRED]` |

### 5. Configuração

```yaml
moseguros:
  proposal:
    decision-sla-days: 15
    decision-alert-days: 10     # tem de ser menor que decision-sla-days (validado no arranque)
```

Dias de calendário, contados em instantes: submetida em `2027-01-05T09:30:00Z` → `sla_alert_at = 2027-01-15T09:30:00Z`, `sla_due_at = 2027-01-20T09:30:00Z`. `SlaStatus` (calculado na leitura): `ON_TIME` se agora < `sla_alert_at`; `ALERT` se `sla_alert_at ≤ agora < sla_due_at`; `OVERDUE` se agora ≥ `sla_due_at`; `null` fora de `UNDER_REVIEW`.

### 6. Submissão

**`POST /api/v1/proposals/{id}/submit`** (`submitProposal`, tag `Proposal`, `hasAnyAuthority('self:proposals','proposal:create-for-client')`) `{ "version": 9 }` → 200 `ProposalResponse`.

1. Estado `DRAFT` ou `INFO_REQUESTED` → senão 409 `INVALID_STATE_TRANSITION`; `version` → 409 `CONCURRENT_MODIFICATION`.
2. `ProposalCompleteness` (com `SIGNATURE`); não vazio → 409 `PROPOSAL_INCOMPLETE` com `missing`.
3. Seguradora activa (`SystemLookups.insurer`, S4-02) → senão 409 `INSURER_NOT_ACTIVE`.
4. `submitted_at` = agora se ainda nulo (guarda a primeira submissão); limpa `info_request_*`; publica `ProposalSubmitted`.
5. Avalia as regras (secção 3) e grava `underwriting_result`.
   - `AUTOMATIC` → `ACCEPTED`, `acceptance_mode = AUTOMATIC`, `decided_by = "system"`, `decided_at`, `expires_at = agora + expiry-days` (prazo para pagar, S5); publica `ProposalAccepted`; auditoria `PROPOSAL.ACCEPT` (`actorType = SYSTEM`).
   - `MANUAL_REVIEW` → `UNDER_REVIEW`, `review_started_at = agora`, `sla_alert_at`, `sla_due_at`, `sla_alerted_at = null`, `expires_at = null`.
6. Auditoria `PROPOSAL.SUBMIT` (depois: `status`, `outcome`, `failures`). Tudo na mesma transacção; os eventos saem depois do commit (outbox).
7. E-mail ao cliente (secção 9): `proposal.accepted` se aceite automaticamente; `proposal.submitted` se em análise.

### 7. Endpoints da seguradora (tag `Proposal`, âmbito `ORG` de seguradora)

Só propostas com `submitted_at is not null`; as outras → 404 `PROPOSAL_NOT_FOUND`.

**`GET /api/v1/insurer/proposals`** (`listInsurerProposals`, `proposal:read`) — filtros `status` (repetível; por defeito `UNDER_REVIEW`), `slaStatus` (`ON_TIME|ALERT|OVERDUE`), `productType`, `channel`, `q` (número exacto, ou nome do tomador com `policyholder->>'fullName' ilike`), `submittedFrom`, `submittedTo` (datas, Maputo); paginação; ordenação `submittedAt` (por defeito `asc`) ou `slaDueAt` → página de:

```json
{ "id": "…", "number": "PR-2027-000123", "status": "UNDER_REVIEW", "customerName": "Ana Maria Mussa",
  "productName": "Auto Base", "productType": "COMPREHENSIVE", "vehiclePlate": "ABC-123-MC",
  "total": { "amount": 3500000, "currency": "MZN" }, "channel": "BROKER", "brokerName": "Corretora Demo",
  "submittedAt": "…", "slaDueAt": "…", "slaStatus": "ALERT", "kycState": "PENDING",
  "inspectionStatus": "SUBMITTED", "acceptanceMode": null }
```

**`GET /api/v1/insurer/proposals/{id}`** (`getInsurerProposal`, `proposal:read`) → 200 `InsurerProposalResponse` = `ProposalResponse` mais:
- `driver` com `licenceNumber`, `licenceCategory`, `birthDate`; `vehicle` com `chassisNumber`, `seats`;
- `underwriting`: o `underwriting_result`;
- `sla`: `{ "reviewStartedAt", "alertAt", "dueAt", "alertedAt", "status" }`;
- `kyc`: `{ "state", "requiredForAutomaticAcceptance", "checkId", "verifiedAt", "verifiedByThisInsurer" }` (o bloco do `ProposalResponse` com mais três campos; `checkId` é o da verificação mais recente só se for desta seguradora, senão `null`, ver S4-01 "Questões");
- `signatures`: histórico (`signedAt`, `channel`, `destinationMasked`, `documentFileId`, `documentHash`, `assisted`, `invalidatedAt`, `invalidatedReason`).

**`POST /api/v1/insurer/proposals/{id}/accept`** (`acceptProposal`, `proposal:decide`) `{ "note": "…", "version": 10 }` → 200 `InsurerProposalResponse`.
- Só `UNDER_REVIEW` → senão 409 `PROPOSAL_NOT_UNDER_REVIEW`.
- Com `inspection_required`, vistoria `APPROVED` → senão 409 `INSPECTION_NOT_APPROVED`.
- KYC `VERIFIED`, ou `total_amount < simplifiedKycMaxPremium` → senão 409 `KYC_NOT_VERIFIED` (o subscritor verifica primeiro o KYC na fila, S4-01).
- `note` opcional, ≤ 1000.
- `ACCEPTED`, `acceptance_mode = MANUAL`, `decided_by`, `decided_at`, `decision_reason = note`, `expires_at = agora + expiry-days`, SLA limpo; `ProposalAccepted`; auditoria `PROPOSAL.ACCEPT`; e-mail `proposal.accepted`.

**`POST /api/v1/insurer/proposals/{id}/reject`** (`rejectProposal`, `proposal:decide`) `{ "reasonCode": "RISK_NOT_ACCEPTED", "reason": "Histórico de sinistros acima do aceitável.", "version": 10 }` → 200.
- Só `UNDER_REVIEW` → 409 `PROPOSAL_NOT_UNDER_REVIEW`.
- `reasonCode` obrigatório (`REQUIRED`); `reason` obrigatório, 10–1000 (`REQUIRED`, `TOO_SHORT`, `TOO_LONG`) → 400 `VALIDATION_ERROR` (plano: "recusa sem motivo devolve 400").
- `REJECTED`, `rejection_reason_code`, `decision_reason`, `decided_*`, `expires_at = null`; `ProposalRejected`; auditoria `PROPOSAL.REJECT`; e-mail `proposal.rejected` com o `reason`.

**`POST /api/v1/insurer/proposals/{id}/request-info`** (`requestProposalInfo`, `proposal:decide`) `{ "message": "Envie de novo a fotografia do chassis.", "items": ["INSPECTION"], "version": 10 }` → 200.
- Só `UNDER_REVIEW`; `message` 10–1000 obrigatório; `items` 1+ sem repetidos de `DECLARATIONS`, `SUITABILITY`, `INSPECTION`, `KYC`, `POLICYHOLDER`, `OTHER` (`REQUIRED`, `ANSWER_DUPLICATED`).
- `INFO_REQUESTED`, `info_request_*`, `expires_at = agora + expiry-days`, SLA limpo; `Proposal.contentChanged()` com o motivo `INFO_REQUESTED` (a assinatura deixa de valer: o cliente assina de novo depois de corrigir); com o item `INSPECTION`, a vistoria volta a `PENDING` (S4-03, secção 4).
- `ProposalInfoRequested`; auditoria `PROPOSAL.REQUEST_INFO`; e-mail `proposal.info-requested`.

### 8. Reavaliação ao aprovar a vistoria

No fim de `approveInspection` (S4-03), na mesma transacção: se a proposta está `UNDER_REVIEW`, avalia de novo as regras; se o resultado for `AUTOMATIC`, faz a aceitação automática da secção 6 (passo 5). Se não, grava só o novo `underwriting_result`. (A verificação do KYC no `identity` não dispara reavaliação: o `identity` não conhece o `proposal`; o subscritor aceita manualmente.)

### 10. Alerta de SLA (`ProposalSlaJob`)

- `@Scheduled(cron = "0 10 * * * *", zone = "Africa/Maputo")`, `@RunAsSystem`, idempotente, sem ShedLock até ao S6.
- Para cada proposta `UNDER_REVIEW` com `sla_alert_at ≤ agora` e `sla_alerted_at is null`: obtém os subscritores com `IdentityApi.staffContacts(insurerId, "proposal:decide")`, envia `proposal.sla-alert` a cada um, e grava `sla_alerted_at`. Sem destinatários: grava na mesma e regista `WARN` com o id da seguradora.
- **Não muda o estado da proposta.** Depois de `sla_due_at` a proposta continua `UNDER_REVIEW` com `slaStatus = OVERDUE`.
- `IdentityApi` (acrescentar, `@RunAsSystem`): `List<StaffContact> staffContacts(UUID organizationId, String permission)` com `StaffContact(UUID userId, String email, String displayName, String preferredLanguage)` — contas `STAFF` `ACTIVE` da organização com algum perfil que tenha a permissão.

### 12. Blocos `kyc` e `decision` no `ProposalResponse`

- `kyc.requiredForAutomaticAcceptance`: `true` se `kycState ≠ VERIFIED` e `total_amount ≥ simplifiedKycMaxPremium` das regras do produto (ou por defeito). Os ecrãs usam-no para recomendar a verificação de identidade antes de submeter.
- `decision`:

```json
"decision": { "mode": "MANUAL", "decidedAt": "…", "rejectionReasonCode": null, "reason": "…",
              "infoRequest": { "message": "Envie de novo a fotografia do chassis.", "items": ["INSPECTION"], "requestedAt": "…" },
              "insurerDueAt": "2027-01-20T09:30:00Z" }
```

`null` em `DRAFT` antes da primeira submissão. `insurerDueAt` = `sla_due_at` (só em `UNDER_REVIEW`). O `decided_by` não sai para o cliente nem para o mediador.

### 13. Códigos de erro novos

Topo: `KYC_NOT_VERIFIED` (409), `INSPECTION_NOT_APPROVED` (409). Campo: `INVALID_RULES`. Traduções na web e na app:

| Código | pt-MZ | en |
| --- | --- | --- |
| `KYC_NOT_VERIFIED` | A identidade do cliente ainda não foi verificada. | The customer's identity has not been verified yet. |
| `INSPECTION_NOT_APPROVED` | A vistoria ainda não foi aprovada. | The inspection has not been approved yet. |
| `INVALID_RULES` | Regra inválida. | Invalid rule. |

Textos de apoio (chaves `proposal.*`, usados no S4-07 a S4-09):
- `underwriting.failure.<CODE>`: `AUTO_ACCEPT_DISABLED` Aceitação automática desligada no produto; `KYC_REQUIRED` Identidade por verificar e prémio acima do limite do KYC simplificado; `DECLARATION_POSITIVE` Há declarações de risco com resposta "sim"; `INSPECTION_NOT_APPROVED` Vistoria por aprovar; `VEHICLE_VALUE_MISSING` Valor do veículo não declarado; `VEHICLE_VALUE_ABOVE_LIMIT` Valor do veículo acima do limite de aceitação automática.
- `rejectionReason.<CODE>`: `RISK_NOT_ACCEPTED` Risco não aceite; `KYC_FAILED` Identidade não confirmada; `INSPECTION_FAILED` Vistoria não aprovada; `FALSE_DECLARATION` Declarações incorrectas; `DOCUMENTS_INVALID` Documentos inválidos; `OTHER` Outro motivo.
- `infoRequestItem.<CODE>`: `DECLARATIONS` Declarações de risco; `SUITABILITY` Questionário de adequação; `INSPECTION` Vistoria; `KYC` Verificação de identidade; `POLICYHOLDER` Dados do tomador; `OTHER` Outro.
- `slaStatus.<CODE>`: `ON_TIME` No prazo; `ALERT` Prazo a terminar; `OVERDUE` Prazo ultrapassado.
- `proposalStatus.<CODE>`: `DRAFT` Rascunho; `UNDER_REVIEW` Em análise; `INFO_REQUESTED` Informação pedida; `ACCEPTED` Aceite; `REJECTED` Não aceite; `EXPIRED` Expirada; `PAID` Paga; `CONVERTED` Apólice emitida.
- Versões `en` equivalentes.

## Critérios de aceitação

- [ ] `UnderwritingEvaluatorTest` passa com os 12 casos da secção 3.
- [ ] `UnderwritingRulesValidationTest`: os valores por defeito são válidos pelo schema; campo desconhecido, `schemaVersion = 2` ou montante negativo são inválidos.
- [ ] `UnderwritingRulesIT`: o gestor de produto grava regras numa versão em rascunho; versão publicada → 409; JSON inválido → 400 com `INVALID_RULES` e o caminho; seguradora B não lê nem grava as regras da A (404); `UNDERWRITER` (sem `product:manage`) → 403 no `PUT`.
- [ ] `ProposalSubmitIT`:
  - proposta incompleta → 409 `PROPOSAL_INCOMPLETE` com `missing`; sem assinatura → `["SIGNATURE"]`;
  - caso 1 → `ACCEPTED` com `acceptanceMode = AUTOMATIC`, `ProposalSubmitted` e `ProposalAccepted` publicados, `expiresAt` = agora + 15 dias;
  - caso 8 → `UNDER_REVIEW` com o SLA calculado; o subscritor aprova a vistoria → `ACCEPTED` automática (caso 9);
  - submeter de novo uma proposta `UNDER_REVIEW` → 409 `INVALID_STATE_TRANSITION`; alterá-la → 409 `PROPOSAL_NOT_EDITABLE` (plano: "proposta não editável após submissão");
  - danos próprios sem vistoria → `missing = ["INSPECTION"]` (plano: "danos próprios sem vistoria não submetem").
- [ ] `ProposalDecisionIT`:
  - aceitar com KYC por verificar e total acima do limiar → 409 `KYC_NOT_VERIFIED`; depois de verificar o KYC (S4-01) → 200 `ACCEPTED`, `MANUAL`;
  - recusar sem `reason` → 400 (plano); com motivo → `REJECTED`, e-mail ao cliente com o motivo (canal falso);
  - pedir informação → `INFO_REQUESTED`, assinatura invalidada (`INFO_REQUESTED`), vistoria `PENDING` com o item `INSPECTION`; o cliente corrige, assina e submete → nova avaliação, `review_started_at` reiniciado;
  - decidir uma proposta `ACCEPTED` → 409 `PROPOSAL_NOT_UNDER_REVIEW`; `version` antiga → 409;
  - cliente e mediador → 403 nos endpoints `/insurer/proposals`; `FINANCE` → 403; sem token → 401;
  - auditoria de cada decisão.
- [ ] `InsurerProposalIsolationIT`: a seguradora B não lista nem abre nem decide (404) propostas da A; nenhuma seguradora vê propostas nunca submetidas (`DRAFT`).
- [ ] `ProposalSlaJobIT` (relógio controlado): com o relógio em `review_started_at + 10 dias`, o job envia um e-mail a cada utilizador com `proposal:decide` dessa seguradora (e a nenhum de outra), grava `sla_alerted_at`, e uma segunda execução não envia de novo; com o relógio em `+ 15 dias` a proposta continua `UNDER_REVIEW` e a lista mostra `slaStatus = OVERDUE`.
- [ ] `api/openapi.yaml`, `api/error-codes.json` e clientes regenerados; traduções presentes; `ModularityTest` passa (o `catalog` não depende do `proposal`).
