## Contexto

O cliente recebe os avisos importantes (proposta decidida, pagamento, referência, apólice emitida, simulação a expirar) por SMS, WhatsApp, e-mail e push, com alternativa de canal quando um falha, e consulta-os num centro de notificações. O administrador da plataforma edita os textos por canal e língua. Cobre RF-16 (avisos) e a parte de notificações do Sprint 6 do plano. Modelo transversal §1.1 ("Notificações": quem quer notificar chama `NotificationApi.notify`; o `notification` nunca ouve eventos de outros módulos), §2, §3, §5, §7 (push, jobs); ADR-003 e ADR-006.

**Pressupõe:**
- S1-03/S1-04: `NotificationApi` com `sendOtp` e `sendEmail`; `notification.outbound_message`; os adaptadores `OtpDeliveryChannel` (`MockSmsSender`, `MockWhatsAppSender`, `EmailSender`); `DeliveryReceiptService` e `POST /api/v1/integrations/delivery-receipts/{provider}`; `messages/notifications_{pt,en}.properties`; o `sms-mock` com SMS, WhatsApp e recibos.
- S1-01: `@RunAsSystem` permitido em todo o pacote `notification`; `identity.user_account` com `msisdn`, `msisdn_verified`, `email`, `email_verified`, `preferred_language`, `status`.

## Objectivo

Qualquer módulo chama `NotificationApi.notify(userId, templateCode, params, category)`; a mensagem fica no centro de notificações do cliente e é enviada pelo primeiro canal disponível e permitido, com 3 tentativas e alternativa para o canal seguinte; o cliente gere as preferências (as categorias obrigatórias não se desligam) e regista os dispositivos para push; o administrador edita, pré-visualiza e testa os modelos.

## Especificação

### 1. Contrato público (`notification`, pacote raiz)

```java
public enum NotificationCategory {
  PAYMENT(true), POLICY(true), LEGAL(true),   // obrigatórias
  PROPOSAL(false), QUOTE(false);              // os sprints seguintes acrescentam (CLAIM, COMPLAINT, …)
  private final boolean mandatory;
}

public class NotificationApi {
  // já existentes: sendOtp (S1-03), sendEmail (S1-04)
  /** Regista a notificação e agenda o envio. Nunca lança por falha de um fornecedor. */
  public UUID notify(UUID userId, String templateCode, Map<String, Object> params,
                     NotificationCategory category);
}

/** Implementada pelo identity (identity → notification; o inverso não existe). Modelo §1.1, decisão D6. */
public interface NotificationRecipientResolver {
  Optional<NotificationRecipient> resolve(UUID userId);
}
public record NotificationRecipient(UUID userId, Msisdn msisdn, boolean msisdnVerified,
    String email, boolean emailVerified, String language, boolean active) {}
```

- `notify` corre com `@RunAsSystem` e junta-se à transacção de quem chama (`Propagation.REQUIRED`): se quem chama fizer *rollback*, a notificação desaparece. O envio só começa depois do *commit*.
- Devolve o `notificationId` (igual para todas as mensagens desta chamada).
- `IdentityRecipientResolver` (`identity.application`, `@RunAsSystem`) lê `user_account` pelo id. `active = (status = 'ACTIVE')`. Tem de existir exactamente um bean desta interface.
- Erros de programação (código de modelo desconhecido, parâmetro em falta) → `IllegalArgumentException`; os testes de cada módulo que notifica apanham-nos.

**Parâmetros reservados** (opcionais; nunca aparecem na lista de variáveis do modelo):
- `webPath` — caminho na web (ex.: `/cliente/apolices/{id}`) → variável `link = {moseguros.web.base-url}{webPath}`; sem `webPath`, `link = {base-url}/cliente/notificacoes`.
- `deepLink` — URI da app (ex.: `moseguros://policy/{id}`), enviado nos dados do push e guardado no centro de notificações.
- `siteUrl` é sempre `{moseguros.web.base-url}` (não se passa).

**Formatação dos valores** (`ParamFormatter`, na língua do destinatário): `Money` → `shared.domain.MoneyFormatter` (S5-02); `Instant` → `DateFormatter` `dd/MM/yyyy HH:mm` em `Africa/Maputo`; `LocalDate` → `dd/MM/yyyy`; o resto → `toString()`. `DateFormatterTest`: `2027-02-10T08:31Z` → `10/02/2027 10:31` em pt e en; `LocalDate` 2027-02-10 → `10/02/2027`. Quem chama **nunca** passa documentos, NUIT, códigos OTP, tokens nem segredos.

### 4. Envio: escolha de canais, tentativas e alternativa

**Em `notify`** (`NotificationService`):
1. `NotificationRecipientResolver.resolve(userId)`. Sem destinatário ou `active = false` → não grava nada, `INFO` com o `userId`, devolve um id novo.
2. Língua = `recipient.language` (`pt` ou `en`; outra → `pt`).
3. O código tem de ter modelos na BD; todas as `variables` (menos `link` e `siteUrl`) têm de estar em `params`.
4. Formata os parâmetros (secção 1) e acrescenta `link` e `siteUrl`.
5. Grava a linha `INBOX`: `title`/`body` renderizados com o modelo `PUSH` da língua (mesmo se inactivo), `status = DELIVERED`, `data`.
6. Planeia os canais (`ChannelPlanner`) e grava as linhas `QUEUED` (`next_attempt_at = agora`).
7. Regista um `TransactionSynchronization.afterCommit` que entrega os ids `QUEUED` ao executor `notificationExecutor` (4 *threads*). Sem transacção activa, entrega logo.

**Disponível e permitido** (`ChannelPlanner`):
- Canal **disponível**: existe modelo activo (código, canal, língua) **e**: `PUSH` → pelo menos um dispositivo activo; `SMS`, `WHATSAPP` → `msisdn` verificado; `EMAIL` → e-mail verificado; `WHATSAPP` → `whatsapp_template_name` preenchido.
- Canal **permitido**: preferência do cliente para (categoria, canal) activa (sem linha = activa).
- Ordem: `moseguros.notification.channel-order: [PUSH, WHATSAPP, SMS, EMAIL]`. As propriedades novas (`channel-order`, `sms.ascii-fold`, `push.provider`, `push.mock-url`) entram no record `NotificationProperties` existente (`moseguros.notification`: `webhookSecret`, `timeout`, `sms`/`whatsapp` = `Provider(provider, mockUrl)`, `email` = `Email(provider, from)`), sem mudar os nomes que já existem.

| Categoria | Linhas `QUEUED` criadas em `notify` |
| --- | --- |
| não obrigatória | o primeiro canal disponível e permitido, pela ordem; se for `PUSH`, uma linha por dispositivo activo; nenhum → só `INBOX` |
| obrigatória | (a) `PUSH` (uma linha por dispositivo) se disponível e permitido; **e** (b) o primeiro canal disponível e permitido entre `WHATSAPP`, `SMS`, `EMAIL`; se nenhum for permitido, o primeiro disponível **ignorando as preferências** (os avisos legais e de pagamento chegam sempre); nenhum disponível → métrica `moseguros_notification_undeliverable_total{category}` e `WARN` |

**Envio de uma linha** (`MessageSender.send(messageId)`, `@RunAsSystem`, transacção própria):
1. `select … for update skip locked` da linha `QUEUED` com `next_attempt_at <= agora`; senão termina. Passa a `SENDING`, `attempts + 1`.
2. Lê o destinatário de novo (contactos actuais), renderiza com o modelo **actual**, grava `destination_masked` e `destination_hash`.
3. Chama o `ChannelSender` do canal (secção 6) com timeout de 5 s.
4. Sucesso → `SENT`, `provider`, `provider_message_id`, `sent_at`.
5. Falha temporária e `attempts < 3` → `QUEUED`, `next_attempt_at = agora + 30 s × 4^(attempts − 1)` (30 s depois da 1.ª falha, 2 min depois da 2.ª).
6. Falha definitiva (destino inválido, token push inválido) ou 3.ª falha → `FAILED`, `last_error`, e **alternativa**:
   - `PUSH`: o dispositivo com token inválido fica `active = false` (`INVALID_TOKEN`); a alternativa só acontece se todas as linhas `PUSH` da notificação falharam e a categoria não é obrigatória (nas obrigatórias o canal externo já está em curso);
   - outros: cria uma linha `QUEUED` para o canal seguinte da ordem, disponível e permitido (nas obrigatórias, com a mesma regra de ignorar preferências), que ainda não tenha sido tentado nesta notificação; métrica `moseguros_notification_fallback_total{from, to}`.
7. Métrica `moseguros_notification_messages_total{channel, status}` em cada mudança de estado final.

**Recibos de entrega** (`DeliveryReceiptService`, S1-03, alterar): procura primeiro em `outbound_message`; se não encontrar, em `notification.message` por (`provider`, `provider_message_id`).
- `DELIVERED` → `DELIVERED`, `delivered_at`.
- `FAILED` → `FAILED`; se `sent_at` foi há ≤ 10 minutos, aplica a alternativa do passo 6.

**`NotificationDispatchJob`** (`@RunAsSystem`): cron `*/15 * * * * *` (`Africa/Maputo`), lock `notification.dispatch`, `lockAtMostFor = PT1M`.
- Envia até 200 linhas `QUEUED` com `next_attempt_at <= agora`, por `next_attempt_at`.
- Linhas `SENDING` há mais de 2 minutos (a aplicação caiu a meio) → `QUEUED` com `next_attempt_at = agora` (contam como tentativa).
- Garante o envio mesmo que o `afterCommit` se perca. Meta: primeira tentativa em menos de 1 minuto.

### 5. SMS: normalização e tamanho (`SmsText`)

1. Troca caracteres tipográficos: `“ ” „` → `"`, `‘ ’` → `'`, `– —` → `-`, `…` → `...`, espaço não separável → espaço, `º` → `o`, `ª` → `a`.
2. Com `moseguros.notification.sms.ascii-fold: true` (por defeito): decomposição NFD e remoção das marcas (`\p{M}`): `Apólice` → `Apolice`, `ç` → `c`, `ã` → `a`.
3. Limite: 160 se todos os caracteres forem do alfabeto GSM-7 (os caracteres de extensão `^ { } \ [ ~ ] | €` contam 2); senão 70.
4. No envio, um texto acima do limite é cortado para `limite − 3` caracteres + `...`, com `WARN` e métrica `moseguros_notification_sms_truncated_total{templateCode}`. A validação da secção 3 impede que os modelos cheguem a isto com os valores de exemplo.
- `SmsTextTest`: `"Apólice emitida — válida até 10/02/2028"` → `"Apolice emitida - valida ate 10/02/2028"`; um texto de 160 caracteres GSM-7 passa; 161 é cortado para 157 + `...`; com `ascii-fold: false`, um texto com `ç` tem limite 70.

### 6. Adaptadores (reutilizam os do S1-03)

### 9.1 Aviso de simulação a expirar (`QuoteExpiryNotifierJob`, decisão D16)

Job diário no módulo `rating` (dependência `rating → notification`, acrescentada ao grafo do modelo §1 pela decisão D16). **Não há evento `QuoteExpiring`**: o `notification` não ouve eventos e o `rating` chama `notify` directamente.

- **Migração `V202702010401__rating_quote_expiry_notified.sql`**: `alter table rating.quote_request add column expiry_notified_at timestamptz null` (idempotência do aviso; uma vez por pedido).
- `rating.application.QuoteExpiryNotifierJob` (`@RunAsSystem`): `@Scheduled(cron = "0 0 9 * * *", zone = "Africa/Maputo")` (todos os dias às 09:00), `@SchedulerLock(name = "rating.quote-expiry-notifier", lockAtMostFor = "PT15M")`; respeita `moseguros.jobs.enabled` (S6-01).
- Selecciona, por lotes de 200, os pedidos `rating.quote_request` com:
  - `origin = 'CUSTOMER'` (as cotações feitas por um mediador não as pode usar o cliente numa proposta sua, S3-02 §6; não se avisa);
  - `expiry_notified_at is null`;
  - nenhuma cotação do pedido com `status = 'USED'` (o cliente já avançou para proposta);
  - pelo menos uma cotação `status = 'OFFERED'` com estado efectivo `OFFERED` (S3-02 regra 10.1: `valid_until > agora` e `start_date ≥ hoje` em Maputo) e cuja data de `valid_until` em `Africa/Maputo` é **hoje + 2 dias** (`moseguros.rating.quote-expiry-notice-days: 2`).
- Para cada pedido, numa transacção: `notify(customer_user_id, "QUOTE_EXPIRING", { "amount": <menor total_amount das cotações OFFERED efectivas, Money>, "validUntil": <maior valid_until dessas cotações, Instant>, "webPath": "/cliente/simular/" + requestId, "deepLink": "moseguros://quote/" + requestId }, NotificationCategory.QUOTE)` e `expiry_notified_at = agora`. Uma falha num pedido não pára os outros (`ERROR` com o `requestId`).
- Log estruturado de início, fim e contagens (`job=rating.quote-expiry-notifier`, `processed`, `failed`). Correr duas vezes no mesmo dia não avisa duas vezes.
