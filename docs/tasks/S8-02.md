## Contexto

Histórias 2 e 3 do Sprint 8: no local do acidente, os dois condutores preenchem a declaração amigável no telemóvel de um deles, mesmo sem rede, e assinam (assinatura desenhada + OTP de cada um; sem rede, desenho com carimbo de hora e GPS e OTP confirmado depois). Na web, um condutor preenche e o outro assina por link (paridade do plano: única diferença permitida). A declaração existe antes do sinistro e pode servir a dois sinistros (um em cada seguradora), por isso é o sinistro que aponta para ela (`claim.claim.accident_statement_id`) e não o contrário. ADR-002, ADR-005.

**Pressupõe:**

- S8-01: schema `claim`, `claim.claim`, `ClaimProperties`, permissão `self:claims`, `ClaimFileAccessPolicy`.
- OTP de assinatura do S4-04 (`identity`, secção 4): `SignOtpChallenge`, `SignOtpVerification`, `IdentityApi.verifySignOtp(UUID signerUserId, UUID challengeId, String code, String documentHash)`; o código fica ligado ao hash do documento; o destino é o `msisdn` da conta do signatário; canais, alternativa, limites e tentativas do S1-03; com sucesso o `msisdn` passa a verificado. O `requestSignOtp` do S4-04 tem textos de proposta ("assina a proposta … prémio …"), por isso esta tarefa acrescenta (acrescentar é permitido, modelo §3) uma variante para a declaração, que reutiliza o mesmo `OtpService` e muda só o texto (secção 6.2).
- `PolicyApi` (S6-01, secção 9): `view(UUID) → PolicyView` (corre no âmbito de quem chama; inexistente ou invisível → `DomainException` `POLICY_NOT_FOUND`), `findActiveByPlate(String plate, Instant at)` e `findByCertificateToken(String token) → Optional<PolicyCoverView>` (correm em `PolicySystemLookups`, em qualquer âmbito). Usa de `PolicyCoverView` só `policyId`, `insurerId` e `plate`.
- `OrganizationApi.findSummary(UUID)` para o nome da seguradora.
- `DocumentApi.store` e limites do S2-01 (10 MB, tipos permitidos, `FILE_TYPE_NOT_ALLOWED`, `FILE_TOO_LARGE`).
- `NotificationApi.notify(userId, templateCode, params, NotificationCategory)` e `notification.template` (S6-04): parâmetros reservados `webPath` (dá a variável `{{link}}`) e `deepLink`; categoria `NotificationCategory.CLAIM` (acrescentada no S8-01). `NotificationApi.sendSignOtp` (S4-04) como modelo para o envio síncrono do código.
- `IdentityApi.findOrCreateCustomerByMsisdn(Msisdn) → UUID` (criado no S3-02, secção 6.1; decisão D2), usado na secção 6 para o signatário.
- `moseguros.web.base-url` (S1-04).
- ShedLock (S6).

## Objectivo

A app e a web enviam a declaração com o mesmo `localUuid` as vezes que for preciso sem criar duplicados; cada condutor assina com o desenho e um código OTP enviado para o seu telemóvel, no momento ou mais tarde; o outro condutor pode assinar por um link recebido por SMS; a declaração fica bloqueada à primeira assinatura confirmada e marca `bothSigned` quando as duas estão confirmadas sobre o mesmo conteúdo.

#### 3.4 Regras, por ordem

1. Validar o pedido (secções 3.2 e 3.3). Erros → 400 `VALIDATION_ERROR`.
2. Calcular `content_sha256` (secção 5).
3. Procurar a declaração pelo `localUuid` no âmbito do cliente:
   - **não existe** → inserir (`revision`, `first_synced_at = last_synced_at = agora`); se o `insert` violar `unique (local_uuid)` (outro cliente usou o mesmo UUID) → 409 `STATEMENT_LOCAL_UUID_CONFLICT`. Resposta **201**.
   - **existe e o cliente é B** (não é dono) → 409 `STATEMENT_LOCAL_UUID_CONFLICT`.
   - **existe, dono, `revision` do pedido < gravada** → 200 com a versão gravada, sem alterar nada (repetição atrasada da fila).
   - **igual e `content_sha256` igual** → 200 com a versão gravada; só actualiza `last_synced_at` (repetição).
   - **igual e conteúdo diferente** → 409 `STATEMENT_REVISION_CONFLICT`.
   - **maior** → se `locked_at` não for nulo → 409 `STATEMENT_LOCKED`; senão grava o conteúdo novo e a revisão, e as assinaturas `PENDING_OTP` com `revision` < nova passam a `INVALIDATED`. Resposta 200.
4. Veículo A: `insurance.policyId` tem de ser do dono (`PolicyApi.view`); `insurerName`, `policyNumber` passam a ser os reais.
5. Veículo B (só com `registrationCountry = MZ`): com `certificateToken`, `PolicyApi.findByCertificateToken(token)`, aceite só se a `plate` da apólice for igual à de B (normalizadas); senão, ou sem token, `PolicyApi.findActiveByPlate(plate, occurredAt)`. Encontrada → `resolved_policy_id_b`, `resolved_insurer_id_b`; a resposta mostra `insurance.matched = true` e `insurance.resolvedInsurerName` (nome público da seguradora, o mesmo que a verificação pública mostra). Não encontrada → `matched = false`. Nunca se devolve o `policyId` de B.
6. Auditoria `ACCIDENT_STATEMENT.SYNC` (`entityType = "AccidentStatement"`, `insurerId = null`), antes/depois `{ revision, plates (mascaradas com Matricula.masked()), bothSigned, locked }`.

**Idempotência:** a mesma chamada repetida (mesmo `localUuid`, mesma `revision`, mesmo conteúdo) devolve sempre 200 com a mesma declaração, quantas vezes for. A primeira devolve 201.

### 4. Croquis — formato `moseguros-sketch` v1

O croquis é guardado em vectorial (`accident_statement.sketch`, para se poder editar e redesenhar igual na web e na app) **e** em PNG (`sketch_file_id`, para o PDF e a galeria). O `document` só aceita imagens e PDF (ADR-005), por isso o vectorial não é um ficheiro.

#### 4.1 Estrutura

```json
{
  "format": "moseguros-sketch",
  "version": 1,
  "canvas": { "width": 1200, "height": 800 },
  "background": "CROSSROADS",
  "items": [
    { "id": "va", "type": "VEHICLE", "vehicle": "A", "x": 420, "y": 440, "rotationDeg": 0 },
    { "id": "vb", "type": "VEHICLE", "vehicle": "B", "x": 620, "y": 360, "rotationDeg": 180 },
    { "id": "a1", "type": "ARROW", "vehicle": "A", "points": [[300, 440], [420, 440]] },
    { "id": "a2", "type": "ARROW", "vehicle": "B", "points": [[760, 360], [640, 360], [600, 420]] },
    { "id": "i1", "type": "IMPACT", "x": 520, "y": 410 },
    { "id": "l1", "type": "LABEL", "x": 80, "y": 280, "text": "Av. Eduardo Mondlane" }
  ]
}
```

- Coordenadas em unidades do `canvas` (1200 × 800, fixo), origem no canto superior esquerdo, `y` para baixo; inteiros de 0 a 1200 (`x`) e de 0 a 800 (`y`).
- `rotationDeg`: inteiro 0–359, sentido dos ponteiros do relógio; 0 = frente do veículo virada para a direita.
- Regras (todas → `INVALID_SKETCH`, campo `sketch`; a mensagem de detalhe diz qual): `format` e `version` exactos; `background` em `BLANK`, `STRAIGHT_ROAD`, `CROSSROADS`, `T_JUNCTION`, `ROUNDABOUT`; `id` únicos, `^[a-z0-9]{1,8}$`; exactamente um `VEHICLE` A e no máximo um `VEHICLE` B; `ARROW` com 2 a 20 pontos e `vehicle` A ou B; `LABEL` com `text` de 1 a 60 caracteres; no máximo 50 itens; JSON serializado ≤ 64 KB.

#### 4.2 Fundos (desenhados por código, iguais na web e na app; cor da estrada `#B0BEC5`, linhas brancas `#FFFFFF` de 4 unidades, tracejado 30/20; fundo do canvas `#E8EFF6`)

| `background` | Desenho |
| --- | --- |
| `BLANK` | só o fundo |
| `STRAIGHT_ROAD` | faixa horizontal `y` 300–500 em toda a largura; tracejado em `y` = 400 |
| `CROSSROADS` | faixa horizontal `y` 300–500 e faixa vertical `x` 500–700 em toda a altura; tracejados em `y` = 400 e `x` = 600, interrompidos no cruzamento |
| `T_JUNCTION` | faixa horizontal `y` 300–500; faixa vertical `x` 500–700 de `y` 500 a 800; tracejados em `y` = 400 e em `x` = 600 (de 500 a 800) |
| `ROUNDABOUT` | as duas faixas do `CROSSROADS` e um anel centrado em (600, 400): círculo de raio 220 cor da estrada e ilha central de raio 120 `#A5D6A7` |

#### 4.3 Itens

| Tipo | Desenho |
| --- | --- |
| `VEHICLE` | rectângulo 120 × 60 centrado em (`x`, `y`), rodado por `rotationDeg`, cantos 10; A `#142D4E`, B `#4A5D75`; letra "A"/"B" branca, 32, no centro; triângulo branco na frente |
| `ARROW` | linha poligonal de 6 unidades na cor do veículo, com ponta triangular de 24 no último ponto |
| `IMPACT` | estrela de 8 pontas, raio 22, `#C62828` |
| `LABEL` | texto `#142D4E`, 24, Inter 600, à esquerda em (`x`, `y`) |

#### 4.4 PNG

- Gerado pelo cliente (web: `canvas` 1200 × 800 → `toBlob('image/png')`; app: `PictureRecorder` → `toImage(1200, 800)` → PNG), com o mesmo desenho.
- `uploadStatementSketch`: multipart `file` (`image/png`, ≤ 1 MB, senão `FILE_TOO_LARGE`) e `revision` (inteiro, igual à gravada; senão 409 `STATEMENT_REVISION_CONFLICT`). Declaração bloqueada → 409 `STATEMENT_LOCKED`. Guarda com `DocumentApi.store` (`ownerType = "ACCIDENT_STATEMENT"`, `ownerId` = id da declaração, classificação `PERSONAL`, sem `insurerId`) e substitui `sketch_file_id`.
- O PNG não entra no `content_sha256` (é uma representação do vectorial, que entra).

### 5. Conteúdo assinado (`StatementContentHasher`)

- `content_sha256` = SHA-256 hexadecimal (minúsculas) do JSON de `StatementContent(occurredAt, location, injuries, otherDamage, vehicles (com os números das cartas e sem os campos `matched`/`resolvedInsurerName`), circumstances, witnesses, remarks, sketch)`.
- Serialização: `ObjectMapper` próprio com `MapperFeature.SORT_PROPERTIES_ALPHABETICALLY`, `SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS`, sem indentação, `Instant` em ISO-8601 UTC com segundos (`2027-03-05T11:45:00Z`), coordenadas como `BigDecimal` com 6 casas, nulos incluídos.
- Só o servidor calcula o hash. O cliente identifica o que assinou pela `revision`.
- `StatementContentHasherTest`: o mesmo conteúdo com campos em ordem diferente dá o mesmo hash; mudar uma circunstância muda o hash; o PNG do croquis não muda o hash.

### 6. Assinaturas

#### 6.1 Desenho no dispositivo do dono (`putStatementSignature`)

Multipart: `drawing` (`image/png`, ≤ 512 KB) e `metadata` (JSON):

```json
{ "localUuid": "c3a1…", "signerName": "Carlos Nhantumbo", "signerMsisdn": "+258847654321", "drawnAt": "2027-03-05T12:06:02Z",
  "lat": -25.969190, "lng": 32.573210, "accuracyM": 15, "revision": 3, "capturedOffline": true }
```

1. Declaração do dono, senão 404 `STATEMENT_NOT_FOUND`.
2. `revision` ≠ gravada → 409 `SIGNATURE_REVISION_MISMATCH`.
3. Já existe linha activa do veículo:
   - com o mesmo `localUuid` → 200 sem alterar (repetição da fila);
   - `CONFIRMED` → 409 `SIGNATURE_ALREADY_CONFIRMED`;
   - `PENDING_OTP` → passa a `INVALIDATED` e cria-se a nova.
4. `signerMsisdn` obrigatório e `Msisdn` válido (`SIGNER_MSISDN_REQUIRED` se faltar; `INVALID_MSISDN` em campo); o de A e o de B têm de ser diferentes (`SIGNERS_MUST_DIFFER`).
5. Grava o PNG (`DocumentApi.store`, dono `ACCIDENT_STATEMENT`) e a linha `ON_DEVICE`, `PENDING_OTP`, `expires_at = agora + 7 dias`.
6. Auditoria `STATEMENT_SIGNATURE.DRAW`.

#### 6.2 Confirmação por OTP (`requestStatementSignatureOtp`, `confirmStatementSignature`)

**Contrato acrescentado ao `identity` e ao `notification`:**

```java
// identity (pacote raiz); @RunAsSystem; mesmas regras 1–6 do S4-04 secção 4, com outro texto
public record StatementSignOtpRequest(UUID signerUserId, UUID statementId, String contentSha256,
                                      LocalDate occurredDate, Channel preferredChannel) {}
public SignOtpChallenge requestStatementSignOtp(StatementSignOtpRequest request);
// a verificação é o verifySignOtp do S4-04, com documentHash = contentSha256

// notification (pacote raiz); igual ao sendSignOtp: síncrono, 5 s, nunca lança, devolve FAILED
public DeliveryResult sendStatementSignOtp(Channel channel, String destination, String code, int validityMinutes,
                                           String occurredDate, String language, UUID correlationId);
```

Textos (`notifications_pt.properties`; `outbound_message.purpose = 'SIGN_OTP'`; **provisórios, a validar juridicamente** como os do S4-04). O código pode ter de ser dito ao dono do telemóvel onde se assinou, por isso o texto não diz "não o partilhe":

```properties
otp.sign-statement.sms=MoSeguros: o código {0} confirma a sua assinatura da declaração amigável do acidente de {1}. Válido {2} min. Só o use se concordar com a declaração.
otp.sign-statement.email.subject=Código para assinar a declaração amigável
otp.sign-statement.email.body=Olá,\n\no código {0} confirma a sua assinatura da declaração amigável do acidente de {1}. É válido durante {2} minutos.\n\nSó o use se concordar com a declaração. Se não esteve neste acidente, ignore esta mensagem.
```

- `{0}` código, `{1}` data do acidente `dd/MM/yyyy` (Maputo), `{2}` minutos. Versões `en`: "MoSeguros: code {0} confirms your signature of the accident statement of {1}. Valid {2} min. Only use it if you agree with the statement."; e-mail "Code to sign the accident statement" / equivalente.
- WhatsApp: modelo `moseguros_sign_statement_otp` com os parâmetros `code`, `date` (aprovação da Meta pendente; até lá, a falha do canal leva à alternativa por SMS do S1-03). O `sms-mock` passa a aceitá-lo.

**Pedir** (`requestStatementSignatureOtp`, sem corpo):

1. Linha `PENDING_OTP` do veículo (senão 404 `SIGNATURE_NOT_FOUND`), com desenho (senão 400 `SIGNATURE_DRAWING_REQUIRED`).
2. `revision` da assinatura ≠ revisão da declaração → a assinatura passa a `INVALIDATED` e 409 `SIGNATURE_REVISION_MISMATCH`.
3. `signer_user_id = IdentityApi.findOrCreateCustomerByMsisdn(signer_msisdn)` (o OTP do S4-04 envia para a conta do signatário, e a conta encontrada por número tem esse número); se o veículo for B, `counterpart_user_id` = esse id.
4. `IdentityApi.requestStatementSignOtp(signerUserId, statementId, content_sha256, data do acidente, null)`; grava `otp_challenge_id`.
5. Resposta 202 `SignatureOtpResponse { challengeId, channel, expiresAt, resendAfterSeconds, fallbackUsed, destinationMasked }`. Limites, reenvio e alternativa de canal do S1-03 (erros `OTP_RATE_LIMITED`, `OTP_RESEND_TOO_SOON`, `OTP_DELIVERY_FAILED` passam tal como são).

**Confirmar** (`confirmStatementSignature`) `{ "challengeId": "…", "code": "123456" }`, por esta ordem:

1. linha `PENDING_OTP` do veículo com desenho; `challengeId` = `otp_challenge_id` (senão 404 `OTP_CHALLENGE_NOT_FOUND`);
2. `revision` da assinatura ≠ revisão da declaração → a assinatura passa a `INVALIDATED` e 409 `SIGNATURE_REVISION_MISMATCH`;
3. `IdentityApi.verifySignOtp(signer_user_id, challengeId, code, content_sha256)` — os erros de OTP passam tal como são (`OTP_INVALID` com `attemptsRemaining`, `OTP_EXPIRED`, …); como o código está ligado ao hash, um código pedido antes de uma alteração do conteúdo já não serve;
4. `status = CONFIRMED`, `otp_verified_at`, `confirmed_content_sha256 = content_sha256`;
5. `locked_at = agora` se for nulo;
6. `both_signed = (A e B CONFIRMED e os dois confirmed_content_sha256 = content_sha256)`;
7. auditoria `STATEMENT_SIGNATURE.CONFIRM` (`{ vehicle, method, capturedOffline, signerMsisdn: mascarado }`).
- Sem rede, a app grava o desenho com hora e GPS e envia-o mais tarde (6.1, `capturedOffline = true`). O OTP pede-se quando houver rede: o dono confirma o seu na app; para B, a app oferece "Pedir o código ao outro condutor" (se ainda estiverem juntos) ou envia o link (6.3).

#### 6.3 Link para o outro condutor (`sendStatementSignatureLink`)

Só para o veículo `B`. Pedido opcional `{ "signerName": "…", "signerMsisdn": "+258…" }`; por defeito usa `vehicles[B].driver.name` e `driver.msisdn` (ou `policyholder.msisdn`). Sem número → 400 `SIGNER_MSISDN_REQUIRED`.

1. B já `CONFIRMED` → 409 `SIGNATURE_ALREADY_CONFIRMED`.
2. Se não houver linha activa de B, cria uma `LINK`, `PENDING_OTP`, sem desenho, `revision` = actual, `expires_at = agora + 7 dias`. Se houver uma `PENDING_OTP` (desenho feito sem rede), usa-a (B pode confirmar esse desenho ou desenhar outro).
3. `link_send_count ≥ signature-link-max-sends` (3) → 429 `SIGNATURE_LINK_LIMIT`.
4. `signer_user_id = findOrCreateCustomerByMsisdn(signer_msisdn)` e `counterpart_user_id` = esse id. É preciso aqui porque o `NotificationApi.notify` envia para um utilizador.
5. Token novo: 16 bytes de `SecureRandom` em Base64 URL sem `=` (22 caracteres); grava o SHA-256 em `link_token_hash` (o anterior deixa de valer), `link_expires_at = agora + 72 h`, `link_send_count + 1`, `link_last_sent_at`.
6. `NotificationApi.notify(signerUserId, "STATEMENT_SIGNATURE_LINK", { requesterName: primeiro nome do dono, occurredDate: LocalDate do acidente, expiresAt: link_expires_at, webPath: "/cliente/assinar/{token}" }, NotificationCategory.CLAIM)`. **Excepção à regra do S6-04 "quem chama nunca passa tokens":** este token vai no link por natureza; fica registado no `notification.message` do próprio B, só vale 72 h, é substituído em cada reenvio e não serve sem o login por OTP de B (secção 6.4).
7. Auditoria `STATEMENT_SIGNATURE.LINK_SEND` (sem o token).
8. Resposta 202 `{ "vehicle": "B", "destinationMasked": "+258*****4321", "linkExpiresAt": "…", "sendCount": 1, "maxSends": 3 }`.

#### 6.4 Assinatura pelo link (condutor B, autenticado)

O condutor B abre o link, entra com o login por OTP do S1-03 com o número que recebeu a mensagem (a conta já existe pelo passo 6.3.4) e fica com âmbito `CUSTOMER`, que o RLS deixa ver a declaração por `counterpart_user_id`.

- Todos os endpoints `…/statement-signature-links/{token}` procuram a assinatura por `SHA-256(token)` no âmbito do cliente. Não encontrada, `link_expires_at` passado, `status ≠ PENDING_OTP` ou `signer_user_id ≠ sub` → 404 `SIGNATURE_LINK_INVALID` (a mesma resposta em todos os casos).
- `GET` → `SignatureLinkView { statement: AccidentStatementResponse (role COUNTERPART), signature: { …como em 3.5 }, linkExpiresAt }`.
- `PUT …/drawing` multipart `drawing` (PNG ≤ 512 KB) e `metadata` `{ drawnAt, lat?, lng?, accuracyM? }` → grava o desenho na mesma linha (substitui um anterior), `revision` = actual.
- `POST …/otp` e `POST …/confirm` → como 6.2 (mesmas validações e passos). Depois de confirmar: `NotificationApi.notify(dono, "STATEMENT_SIGNATURE_CONFIRMED", { signerName, occurredDate, webPath: "/cliente/sinistros" }, NotificationCategory.CLAIM)`.
- `POST …/decline` `{ "reason": "…" }` (obrigatório, 3–500) → `DECLINED`, `declined_at`, `decline_reason`; notifica o dono com `STATEMENT_SIGNATURE_DECLINED`; auditoria `STATEMENT_SIGNATURE.DECLINE`. A declaração fica sem a assinatura de B; o sinistro pode ser participado na mesma.

#### 6.5 Expiração (`StatementSignatureExpiryJob`)

- `@Scheduled(cron = "0 20 1 * * *", zone = "Africa/Maputo")`, ShedLock `claim.statement-signature-expiry` (`lockAtMostFor = PT10M`), `@RunAsSystem` (classe `…Job` no pacote `application`).
- Passa a `EXPIRED` as assinaturas `PENDING_OTP` com `expires_at < agora`. Regista início, fim e contagem.

### 7. `IdentityApi.findOrCreateCustomerByMsisdn(Msisdn) → UUID`

- **Já existe: criado no S3-02 (secção 6.1)**, com a assinatura do modelo §3 (decisão D2). Esta tarefa não o recria nem muda o seu comportamento; usa-o tal como está (também o usam o S4-06 e o S12 pelo USSD). Corre em `SYSTEM` dentro do `identity` (`IdentitySystemLookups`/`@RunAsSystem`), por isso quem chama não precisa de âmbito especial.
- Comportamento de que esta tarefa depende (definido no S3-02): conta `CUSTOMER` existente com esse `msisdn` (qualquer estado) → devolve o id; não existe → cria pela `CustomerAccountFactory` (`ACTIVE`, `msisdn_verified = false`, `preferred_language = 'pt'`, auditoria `CUSTOMER.REGISTER` com `{ "source": "FIND_OR_CREATE" }`); quando a pessoa entrar pelo OTP do S1-03, o número passa a verificado; duas chamadas simultâneas para o mesmo número não criam duas contas.
- O comportamento do método é testado no S3-02 (`BrokerQuoteIT`: conta nova, conta existente, chamadas simultâneas); os testes desta ficha (`StatementSignatureIT`, `SignatureLinkIT`) cobrem só o uso: um signatário B com número novo fica com conta criada e a declaração aparece-lhe quando entra por OTP.

- [ ] `AccidentStatementSyncIT`:
