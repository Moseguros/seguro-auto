## Contexto

## Especificação

### 1. Sessão (`src/auth`)

- Uma sessão de cada vez: `{ type: 'CUSTOMER' | 'STAFF', accessToken, refreshToken, expiresAt }`.
- O token de acesso fica só em memória.
- O refresh token fica em `localStorage` (`moseguros.customer.rt`) para clientes e em `sessionStorage` (`moseguros.staff.rt`) para staff, para o staff perder a sessão ao fechar o separador. Ao arrancar, se houver um refresh token, chama `refreshToken` para obter o token de acesso.
- `AuthProvider` expõe: `session`, `me` (resultado de `getMe`, em cache no TanStack Query com a chave `['me']`), `login(tokens, type)`, `logout()`, `status: 'loading' | 'anonymous' | 'authenticated'`.
- `logout()` chama `logoutSession` na API com o refresh token (ignora erros), limpa o armazenamento e a cache do TanStack Query, e vai para `/cliente/entrar` ou `/entrar`, conforme o tipo.
- **Interceptores (`http.ts`)**:
  - acrescentam `Authorization: Bearer`, **excepto** nos pedidos a `/api/v1/auth/**` (públicos; um token expirado nesses pedidos não pode estragar a renovação);
  - numa resposta 401 com sessão activa, renovam **uma única vez em simultâneo** (os pedidos que falham ao mesmo tempo esperam pela mesma renovação) e repetem o pedido;
  - se a renovação falhar, fazem `logout()`;
  - acrescentam `Accept-Language` com a língua actual.
- `areas.ts` — `areaFor(me)` devolve a área inicial:

| Utilizador | Área | Página inicial |
| --- | --- | --- |
| cliente | `cliente` | `/cliente` |
| staff com `PLATFORM_ADMIN` | `admin` | `/admin` |
| `orgType` `INSURER` | `seguradora` | `/seguradora` |
| `BROKER`, `AGENT` | `mediador` | `/mediador` |
| `ASSESSOR` | `perito` | `/perito` |
| `WORKSHOP` | `oficina` | `/oficina` |
| `ASSISTANCE` | `assistencia` | `/assistencia` |
| `OMBUDSMAN` | `provedor` | `/provedor` |
| `REGULATOR` | `supervisao` | `/supervisao` |
| `CORPORATE_CLIENT` | `frota` | `/frota` |
| `POLICE` | — | `/verificar` |

- `RequireAuth({ type, area? })`:
  - sem sessão → `/cliente/entrar?voltar=<caminho>` (cliente) ou `/entrar?voltar=<caminho>` (staff);
  - sessão do tipo errado, ou área diferente de `areaFor(me)` → página `/sem-acesso` ("Não tem acesso a esta área", com um botão para a sua área).
- `problem.ts`: `getProblem(error)` devolve `{ status, code, detail, errors[], retryAfterSeconds?, attemptsRemaining? }`. A mensagem mostrada é `t('errors.' + code)`, com `errors.UNKNOWN` quando a chave não existe. Erros de campo vão para os campos do formulário com `t('validation.' + errors[].code)`.
- Todas as chaves `errors.<CODE>` e `validation.<CODE>` dos códigos em `api/error-codes.json` (S1-02) existem em `pt-MZ.json` e `en.json`; um teste Vitest lê esse ficheiro e compara. Os códigos que as tarefas de backend seguintes acrescentarem trazem as traduções no mesmo PR.

### 2. Login por OTP (`/cliente/entrar`, `PublicLayout`)

**Passo 1 — identificador**

- Carrega `getOtpOptions`.
- Selector "Telemóvel / E-mail", só com os tipos de `identifierTypes`; se houver só um, não mostra o selector.
- Telemóvel: campo com o prefixo fixo `+258` e 9 dígitos, `inputMode="numeric"`, validação `^8[2-7]\d{7}$` (`validation.INVALID_MSISDN`). E-mail: `type="email"`.
- Se `customerCanChoose` e houver mais de um canal para o tipo: escolha do canal (botões de opção "SMS" / "WhatsApp"), com `defaultChannels[tipo]` seleccionado.
- Botão primário (azul) "Receber código" → `requestOtp`.
  - `OTP_CHANNEL_NOT_AVAILABLE` → mensagem e muda para o outro tipo de identificador, se existir.
  - 429 → mensagem com a contagem `retryAfterSeconds`.

**Passo 2 — código**

- Texto "Enviámos um código por {canal} para {destino mascarado}", com a máscara feita no browser:
  - telemóvel `+258*****4567`;
  - e-mail com a primeira letra e o domínio.
- Ligação "Alterar" volta ao passo 1.
- `OtpCodeInput`:
  - `codeLength` caixas;
  - `autoComplete="one-time-code"`, `inputMode="numeric"`;
  - colar o código preenche todas;
  - submete sozinho quando estiver completo.
- `fallbackUsed = true` na resposta → aviso informativo "Não conseguimos enviar por {canal pedido}. Enviámos o código por {canal usado}."
- Durante 30 s, `getOtpChallenge` a cada 5 s; se o canal mudar, actualiza o texto e mostra o mesmo aviso.
- "Reenviar código" desactivado com contagem decrescente de `resendAfterSeconds`; depois chama `requestOtp` de novo com o mesmo identificador e canal.
- Erros:
  - `OTP_INVALID` → "Código errado. Restam {attemptsRemaining} tentativas.";
  - `OTP_EXPIRED`, `OTP_ATTEMPTS_EXCEEDED`, `OTP_SUPERSEDED` → mensagem e o botão de reenvio fica logo activo;
  - `ACCOUNT_DISABLED` → mensagem para contactar o apoio.
- Sucesso → `login(tokens, 'CUSTOMER')`. Se `isNewUser` ou `me.profileComplete = false`, vai para `/cliente/perfil?completar=1`; senão para `voltar` ou `/cliente`.

### 3. Início do cliente (`/cliente`)

- "Olá, {primeiro nome}" (ou "Olá" sem nome).
- Perfil incompleto → cartão "Complete o seu perfil para poder comprar um seguro", com botão primário azul "Completar perfil".
- Botão `variant="cta"` (laranja) **"Simular seguro"** → `/cliente/simular` (ainda "Em construção"). É o único botão laranja do ecrã.

### 4. Perfil (`/cliente/perfil`)

**Formulário** (`react-hook-form` + `zod`, com as mesmas regras do S1-06):

| Campo | Componente |
| --- | --- |
| Nome completo | texto |
| Data de nascimento | `TextField type="date"` |
| Tipo de documento | select: BI, Passaporte, DIRE |
| Número do documento | texto |
| NUIT | 9 dígitos, `inputMode="numeric"` |
| Morada | texto, opcional |
| Província | select com os 11 códigos, texto de `province.<CODE>` |

- Quando o documento ou o NUIT já existem, mostra o valor mascarado só para leitura, com um botão "Alterar" que abre o campo vazio. O pedido envia `null` se não forem alterados.
- Com `?completar=1`, mostra no topo "Precisamos destes dados para emitir as suas apólices."
- Ao gravar com sucesso: aviso "Perfil guardado"; se o perfil ficar completo e veio de `completar`, vai para `/cliente`.
- 409 `CONCURRENT_MODIFICATION` → mensagem e recarrega os dados.

**Secção "Contactos"** (`ContactsSection`):
- Lista os contactos com a etiqueta "Verificado".
- Botões "Acrescentar e-mail" / "Acrescentar telemóvel" para o tipo que falta, e "Alterar" no que existe.
- O `ContactDialog` reutiliza o `IdentifierStep`/`CodeStep` com `startContactVerification` e `verifyContact`. Os dois passos recebem as funções de pedir e validar por propriedade, para que o reenvio no diálogo chame `startContactVerification` (e não `requestOtp`).
- "Remover" pede confirmação; `LAST_CONTACT` → mensagem.

**Menu do utilizador** (barra superior do `AppLayout`): nome e "Terminar sessão".
